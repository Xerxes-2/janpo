# 跑批判据清单

**这份清单从本项目 M0–M2 的跑批里提取，每一条都被一个真实案例咬过一次。** 它是
`.scratch/llm-riichi-arena/run/DECISIONS.md`（按时间追加的日志，三千多行）的**索引与提炼**，
不是替代：判据在这里，来龙去脉在那里。

**怎么用**：派工单可以只写「照 `docs/agents/judgments.md` 的判据做」。开工时把 §1–§3 逐条过一遍，
与你这票不相干的跳过；§4 是给调度器的。**收工前再过一遍你动过的那几条**——多数判据是在收尾
（写报告、加闸门、往术语表里写一句话）那一刻被违反的。

**往里加一条的门槛**：一句判据 + 一个真实案例的一句话与出处。**没有案例支撑的漂亮话不进。**

本项目最常犯的一类错，把它当一个词记住：**记录声称了一件事，而那件事的执行体不存在。**
已抓到六例——代码里有断言但闸门里不跑、票标着「派工中」但没有 agent、README 说有自动检查但 CI 里跳过、
术语表写下不变量但没人执行、票文件写好但不在工作区里、**属性测试是恒真式（两侧同一个表达式）**。
判据 1 / 2 / 3 / 18 都是它的分支。

**第六例最难发现，因为它在测试列表里是绿的。** 判法：**把被测的那一处真弄坏，看它红不红**
（票 60；它还顺手发现同一族的另外两条）。凡是断言「两种算法给出同一结果」的属性，
先问**两侧是不是同一个实现**；是的话就要引入**第三个锚点**（例如引擎的权威状态），
而不是拿另一份同源结果当右侧。

## 一、证据（谁在守，它守得住吗）

### 1. 闸门的证据是「它失败过」

一道闸门算数的证据是**它红过一次**，不是「代码里有这一行」；新增断言要当场反向自证，红的输出进报告。

_案例_：README 写着「导出的牌谱里不含 key，有一道自动检查守着」，那行断言确实存在，
却只在要真 key 的手验模式下跑、CI 里整条跳过（票 34；DECISIONS「调度器核对 README 的安全声称」）。

### 2. 写下一条不变量，先问「谁来执行它」

往术语表、ADR、报告里写下任何「X 恒成立」之前，指出执行它的那段代码或那道闸门；
指不出就说明它只是期望——**只活在文档里的不变量比没有更糟，后人会以为它成立**。

_案例_：术语表刚裁定「Persona 一局内不变」，核代码才发现 `loop.ts` 每手重解模板、
面板在对局中随时可编辑，没有任何东西执行它（票 48 收词 → 票 46 把它做成真的；
DECISIONS「调度器裁决：`Persona` 的『一局内不变』要做成真的」）。

### 3. 闸门还要问「它在真语料上执行过几次」

一条永远执行不到的断言，与一条从不失败的断言，危害相同：闸门要逐条报执行次数，**为 0 的当场喊停**。
反向自证只证明「这条断言写对了」，不证明「它有机会开口」。

_案例_：票 41 的「立直后全摸切」扫了 120 颗种子、21,306 份 prompt，执行 **0 次**——当时只有均匀随机选手，
而 2000 颗种子里只有 15 场立直成立（票 49 掺进有主见选手的语料后它才真的开口；
DECISIONS「票 41 与 42 撞出一件事」）。

### 4. 覆盖不到的，做成代码里的一个值

语料到不了的那几种情形要**显式写出「谁也到不了」**，别留在注释里当旁白，也别塞进必覆盖名单凑数。

_案例_：票 50 把 `Soak.rare` 按「谁到得了」拆成三份，四风连打 / 三家和了 / 流し満貫落进 `unguarded`——
两种选手各 6000 场、共 60,689 局一次都没碰到（`reports/50-rare-forms-need-a-player-that-reaches-them.md`）。

### 5. 断言红了，只许往补强的方向改

删测试、加 skip、放宽断言、改期望值迎合实现，一律不许；要改就改成更硬的输入或再补一条用例。
**改期望值只有一种正当理由：那份期望本身在规则下不成立**，并且要在报告里说清为什么。

_案例_：票 47 的「401 不重试」把票 36 那条「打码的三个出口」用例按红了，它的处置是改喂一条回显 key 的 429、
另新增一条 401 用例，三个出口仍旧逐个被证明（DECISIONS「票 47 的两条挂账」末段）。

### 6. 新断言第一次报红，先怀疑断言自己

手捏三五个局面推出来的式子，作者会一直以为它是对的。新闸门在真语料上第一次大面积报红，
**先验算自己的式子，再怀疑被测物**。

_案例_：票 41 的「河 = 巡目 + 碰吃组数 − 暗杠组数」漏了「杠之后还要摸一张岭上牌」，
扫真实对局当场 146 句红——是闸门错，不是渲染器错（同批还有一次：加杠亮出的头一张仍在别人河里，
378 句红；DECISIONS「41-3」）。

### 7. 「看得见」这类验收，要有人真的把图打开看

DOM 里有 ≠ 人看得见。以截图 / DOM 摘要为证据的票，集成时**必须把图打开看**并写下看到了什么，
同时把「看得见」钉成 DOM 上可断言的标记。

_案例_：牌桌上他家的手牌整片是空的（`.tile.back` 的 `color: transparent` 让边框与底色一起透明），
而 22 号票交了 3 张无头截图与 2 份 DOM 摘要、测试全绿，调度器只读报告文字就放行了
（票 32；DECISIONS「教训：视觉证据必须真的用眼睛看」）。

### 8. 渲染出来的自然语言要有语义闸门

结构化数据对，不代表渲染出来的**话**对。给自然语言产物立「这句话在规则下可不可能」的断言，
期望值取自**规则**，不取自被检查那句话的来源（拿来源当期望值等于用同一份数据证明它自己）。

_案例_：prompt 里印出「吃（来自对家）」这句日麻里不可能的话，而它躲过了全部十道闸门——
黄金用例钉的是决策包里的绝对座位号，前缀属性测试钉的是字节单调，两者都不问「这句中文说的是不是真的」
（票 40 → 票 41 立 11 条语义不变量；DECISIONS「票 38 在票外挖出：prompt 里他家副露用了观测者参照系」）。

## 二、形态（是不是一开始就建错了）

### 9. 一个投影里出现第二个「只能从历史算」的字段，就是形态错了

要给同一个投影补**第二个**「发生过的事」的字段时，停下来问「是不是该给它历史」，别再加一个字段。
一次是巧合，两次是症状。

_案例_：给座席的快照投影先要补 `PendingKan`，又要补立直宣言牌与巡目；最终 `Observation` 降为
掩蔽事件流的 fold（票 20/28 → 29a；DECISIONS「教训：什么时候该停下来问『是不是形态错了』」）。

### 10. 相对方位必须显式声明参照系

一个函数同时渲染「自家」与「他家」而方位是相对的，参照系就要**当参数传进来**，不靠调用点隐含；
换参照系时，连同「读者以为的参照系」一起换。

_案例_：`prompt.ts` 的 `naki()` 按观测者算他家副露的来源，印出「吃 来自对家」；改成按副露方算之后
还得就地写「来自**他的**上家」——因为可缓存前缀里的 preamble 早已宣告默认参照系是观测者
（票 40；DECISIONS「40-1 / 40-2」）。

### 11. 要读规则才做得出的决定，归引擎

跨层只搬事实与 id；凡是「得知道日麻规则才答得出」的判断留在引擎里，别在渲染层或 Agent 层重新长一份。

_案例_：兜底动作放在引擎的 `Fallback.action`——让 TS 自己从决策包里挑一条摸切看着可行，
可 Assisted 档的兜底要算向听与危险度，24 号票就得把它整个搬回来（DECISIONS「23-1」）。

### 12. 拒绝理由各有各的 case，别落进兜底分支

引擎拒绝一个动作返回的是值（`CONTEXT.md` 的 `IllegalAction`）。走不到的理由不立（那是死代码），
走得到的别混进万能分支——**错的诊断比没有诊断更贵**。

_案例_：立直之后打错牌时那张牌就在手里，落到原来的兜底分支会被报成 `Kuikae`（食替），
因此另立 `RiichiRestricted`（DECISIONS「09-I」）。

## 三、事实与因果

### 13. 查「当下事实」问权威源

版本号、API 形状这类当下事实，问**仓库 / 包的 API 或官方 changelog**，不用搜索结果的转述。
搜索适合回答「有没有这个东西、怎么用」，不适合回答「现在最新是几」。

_案例_：升级 GitHub actions 时照搜索结果写成「checkout 最新 v5.1.0」，
`gh api repos/<owner>/<repo>/releases/latest` 一问是 v7.0.1——差两个大版本
（DECISIONS「教训：查『最新版本』要问权威源」）。

### 14. 说「因为 X 所以慢」之前，先量 X

写进票面或报告的因果判断，要有一次分步计时 / 分段测量垫底，别把差额直接归因给最可疑的那一项。

_案例_：票 45 的前提「远端 CI 差的五分钟基本是每次重新拉整套工具链」没量过就写进了票面；
远端实测冷拉工具链只 18 秒，而缓存 restore 花 20 秒、只省回 16 秒，净亏，缓存整条拆掉
（DECISIONS「票 45 的远端实测推翻了它的前提」）。

**补强一（内层循环）**：先问「这件事一趟做几次」，再问「一趟多贵」。外层动作（起进程、拉工具链）
只发生个位数次，再贵也有限；内层循环（每手、每张牌、每次调用）是三四位数次，单次再便宜也是大头。
_案例_：票 56 的票面把 38 秒归给「每道闸门各起一个浏览器」，实测起浏览器每趟只 0.15–0.35s，
大头是每走一手四次 playwright 往返（200 手 6680ms → 页面内轮询 279ms）。

**补强二（并行外推不是除法）**：「CPU 时 ÷ 处理器数 = 墙钟」只在完美线性扩展时成立，而完美扩展
基本不存在：`nproc` 报的是**逻辑线程不是物理核**（SMT 的第二线程共享执行单元，通常只多 20–30%），
内存带宽、缓存与 GC 争用都会先饱和。并行预估要么给**实测数据点的外推**（标明测的是几进程），
要么明说「假设线性、上界」。
_案例_：调度器把 11.3 核时直接 ÷「32 核」得出 21 分钟——机器实际是 16 核 32 线程（9950X3D），
且已有的实测点只有 12 进程 876 场/s（≈ 44 分钟纯扫描）；从 12 进程到「全开」的增益从未测过
（DECISIONS「认账：核不是线程，除法不是预估」）。

### 15. 前提被后续票拆掉时，回头重问那条决策

集成一张票时除了核「旧东西有没有坏」，还要核**「旧决定的前提还在不在」**——
理由消失了而结论还在，没有任何工具查得出来。

_案例_：票 38 否决副露位置编码的理由是「四家竖排面板没有方位可锚」，票 44 把牌桌改成三×三、
每家有了朝向之后那条理由当场过期，却没人回头重问（主人指出后立票 51；
DECISIONS「主人指出：副露该用位置编码来源（立票 51）」）。

## 四、给调度器（派工与集成）

### 16. 并行跑批时看到红，先怀疑基础设施

多个工作区同时跑 CI 时的红，先查端口 / 临时目录 / 共享文件这类基础设施，再查代码。
**假红比真红危险**——它训练人「重跑一遍就好」，而那正是掩盖真失败的习惯。

_案例_：集成票 30 时另一个工作区也在跑 CI，四个 `verify-*.mjs` 写死的端口（4179–4182）撞车，
失败冒在 `verify-golden.mjs` 里，长得像黄金用例挂了（DECISIONS「集成 30 号票时的一次假红」）。

### 17. 票号由调度器分配

agent 发现问题**只描述、不编号**（写进简报与报告即可）。票号是共享的可变状态，只有调度器有全局视图。

_案例_：主人指出副露缺来源时调度器立了 38 号并派了工，同一时间另一个工作区的验收也立了 38 号，
两张撞号，验收那张事后重编成 39（DECISIONS「记账冲突：38 号被用了两次」）。

### 18. 票文件先提交，再开工作区、再派工

派工前确认票文件在 agent 打得开的那个基点上（`jj file list -r <基点> | grep issues/<票号>`）；
排班表的「派工中」只能在**派工调用成功返回之后**写。

_案例_：票 50 的票文件写完没提交就建工作区派工，agent 打开是空的，只好照派工单原文重建了一份
（同形的另一次：票 35 的排班表写着「派工中」而根本没调过 agent；
DECISIONS「调度器失误：票 50 的文件没提交就派工了」）。
