# 调度器操作手册

**给谁看**：在这个仓库里当调度器的那个 agent（不实现、不 review，只写票、派工、集成、记账）。
接票干活的人读 `docs/agents/workbook.md`，判据读 `docs/agents/judgments.md`。

**这份文件只收「已经被真实事故校准过」的协议。** 没踩过的坑不写——写了也会和代码各自过期
（判据 15）。每条后面括号里是校准它的那次事故。

## 你的位置

- **实现与 review 都交给 subagent**，在各自的 jj workspace 里。你只写票、派工、集成、记账。
- **仓库里的票据才是权威副本**，派工单是副本。派工单信息全但仓库里没有，agent 只能凭派工单重建
  （票 50：票文件没提交就派工，agent 照原文重建了一份）。

## 一、写票

- **垂直切片**：每票能在一个新鲜上下文里做完，能单独验收。
- **票号只由你分配。** agent 只描述问题、不编号（票 38 被两个 agent 同时用过）。
- **票文件写完立刻 `jj commit`**，然后才开工作区、才派工。派工前检查：
  `jj file list -r <工作区基点> | grep issues/<票号>` 必须有（票 50）。
- 票面写**要什么行为**，不写怎么改；但**边界要写死**：不许碰哪些文件、并行者的地盘在哪。
- **票面里的因果判断先量再写。** 「慢在拉工具链」那句是没量过的假设，害 agent 白做一半（票 45）。
- **属性/不变量类的票面**：先自问「这条断言的反例长什么样」。写成不可能的断言，
  实现者得先证伪你才能干活（票 29b：「第 n 手的 prompt 是第 n+1 手的字节前缀」按字面不可能）。
- 前一票交付的**既成事实照抄进票面或派工单**——省 agent 半天，也防它重造一份。

## 二、编波

- **并行的唯一判据：地盘不交叉，按文件算，不按模块名算。**
  派工前 `grep -rln <要改的符号>` 看它散在哪几个文件
  （`renderVersion` 横跨五个文件，据此把 43 从 46 那一波挪开，避免撞车）。
- 交叉就**串行或错开**；两票都要碰同一个文件的不同区域时，写明「改动尽量集中，方便 rebase」。
- **上限四路**（本机 32 核 / 91 G；四个 agent 各跑 `ci.sh` 约 1m40s 不打架）。
- 一个 agent 一个工作区；派工前把工作区对齐到集成头：
  `cd <ws> && jj workspace update-stale; jj new <集成头 change>`。

## 三、派工单的固定骨架

1. **工作区硬约束**：绝对路径、「每条 bash 先 cd」、**别碰哪些工作区与文件**（点名并行者的地盘）、
   只用 jj、禁远端操作与交互式 flag、已对齐到哪个集成头。
2. **票路径**与 **fixed point**（code-review 的基线 commit）。
3. **必读顺序**：`workbook.md` 硬约束 → `judgments.md` → 票 → 相关报告（点名哪几份、为什么）→ 术语表。
4. **要害 3–6 条**：写「最容易做错的地方」，不是复述票面。
5. **边界**：不做什么（尤其别人的地盘、后续票的活）。
6. **交付物五件**：CI 全绿并 `jj commit`；票勾框改 `Status:`；报告；`DECISIONS.md` **末尾**追加一段；
   **简报 ≤N 行**（首行 `STATUS:`、次行 `CHANGE:`）。
7. **简报要求写「下一票必须知道的接口事实」**，而不是复述做了什么——它是下一张票的输入。
8. 真 key 的位置 + **绝不进代码/测试/fixture/提交**；CI 里不许调真实 API。

## 四、集成（每票一遍，顺序别改）

```
jj rebase -r <change> -d <当前集成头>
jj resolve --list -r <change>                     # 看冲突在哪
jj new <change> -m "tmp resolve"
python3 .scratch/llm-riichi-arena/run/resolve-append-conflicts.py <冲突文件>
jj squash -u                                       # -u 免得开编辑器
./scripts/ci.sh                                    # 全绿才算集成完
jj commit -m "chore(mN): <票号> 集成——<一句话>"
jj bookmark set main -r @- --allow-backwards && jj git push --bookmark main
```

- `DECISIONS.md` 几乎每次都冲突（两个 agent 同时往末尾追加）。那个脚本**只处理「两侧各自新增」**，
  一见删改就报错交人——**不许让它猜**。
- **语义撞车比文本冲突危险**：两票各自绿、合流即红（票 22 加了 `tehai_count`，打红票 21 钉死的用例）。
  `ci.sh` 是唯一裁判，别凭「看起来不相干」跳过。
- **假红先怀疑基础设施**：并行跑批时四个工作区抢同一个写死端口，报错长得像用例挂了（票 45 前的事故）。
- **以图为证的票：把图打开看**，并在集成记录里写你看到了什么
  （票 22 交了三张截图，我只读报告就放行，漏掉牌背隐形整整两周）。
- **对外声称与安全声称：自己核，不信报告。** README 那句「有自动检查守着」为真的一半——
  断言存在但 CI 里跳过（票 34）。

## 五、记账

- `DECISIONS.md` 是**日志**：追加，不重写。判据进 `judgments.md`，待裁项进它开头那张索引表。
- **agent 报的「越界发现」由你决定**：并进哪张票 / 新立一票 / 只记档。别让 agent 自己扩边界——
  **边界该由调度器松**（票 39 挂账 README 那句，是对的做法）。
- 自己裁的要写**理由与被否决项**；留给主人的要写**「不裁的后果」**。
- **集成时除了核「旧东西有没有坏」，还要核「旧决定的前提有没有变」**
  （票 38 否决位置编码的理由被票 44 拆掉，我集成 44 时没回头重问，主人指出才发现）。
- 排班表的「派工中」只在**派工调用成功返回之后**写；简报里写「已派」必须能对上一个 agent id
  （票 35 曾被标成派工中却没有 agent）。

## 六、停手 / 交接前的收尾检查

- 全部工作区对齐到集成头：`jj workspace list` + 每个 `jj st`
- **无未解冲突**：`jj log -r 'conflicts()'` 为空（重启撞上半途 rebase 最难收拾）
- `main` 与远端一致、远端 CI 与 Pages 绿、`./scripts/ci.sh` 全绿
- **没有 agent 在跑**
- 排班表留一段「**从这里接**」：下一波派谁、为什么这么排、哪几票会撞
