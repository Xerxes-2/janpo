# ADR-0004：规则集是引擎的一等输入，默认值对齐天凤

**日期**：2026-08-16
**状态**：已接受

## 背景

第一版 spec 把规则差异当成零散的开关（红宝牌、食断、切上满贯、头跳），默认值凭直觉写成「头跳开启」。为 M0 的第 13 票（真实牌谱对拍）调研数据源时，发现两件事：

**一、默认值与现实平台相反。** 天凤官方手册（`tenhou.net/man/`）写明「ダブロンあり」，雀魂段位战规则表同样允许双响；两家都**不采用**切上满贯。而 spec 的默认配置是「头跳开、切上可选」。后续用 60 局天凤鳳凰卓（`鳳南喰赤`）牌谱实测印证：

- 双响成立：3 处 `hora` 事件相邻
- 无切上满贯：`30符4飜7700点` 出现 30 次、`60符3飜7700点` 1 次

**二、规则差异远不止那几个开关。** 同一批调研还查出：三家和了在天凤是途中流局、在雀魂是三响成立；流局满贯两家都有而 spec 完全没提；连风牌雀头在天凤是 4 符；国士无双对暗杠的抢杠天凤禁止、雀魂允许。再加上三麻（3 家 / 108 张 / 禁吃 / 拔北 / 自摸损 / 半庄 6 局）——规则变体会改动牌山构成、动作空间、局数、点数，甚至向听数的合法牌种。

也就是说：**规则不是引擎的配置项，是引擎的输入。**

## 决定

1. **`Ruleset` 是引擎的一等输入。** 引擎中不得出现散落的规则字面量（`4` / `136` / `1000` / `25000`），一律从 `Ruleset` 读。M0 已做到：这些字面量只出现在预设定义那一处。
2. **预设按现实平台命名**（天凤 / 雀魂 / 项目默认），而不是按「标准 / 变体」。规则没有「标准」，只有「某个平台的那一套」。
3. **默认值对齐天凤鳳凰卓**：`Atamahane = false`（双响成立）、`KiriageMangan = false`。理由见背景中的实测证据。
4. **`Ruleset` 拥有牌种全集。** 「这个规则集里存在哪些牌种」只有一个表示（`TileKindSet`），由 `Ruleset` 携带；不再让 `Ruleset.TileKinds : Tile list` 与 `TileKindSet` 各存一份。
5. **立直棒在宣言牌落定时才计入供托**，而非宣言时刻。固件实测：`reach` 145 次对 `reach_accepted` 143 次，差的 2 次正是宣言牌被荣和的局——天凤的立直棒确实在落定时才出。

6. **「5枚目を待つ聴牌」的口径按天凤：只看暗牌。** 天凤把暗杠也算作副露手牌，因此杠掉 `8888m` 后 `7m9m` 仍算听 `8m`（牌谱 2 例都付了听牌料）。EMA 竞技规则 §3.3.8 取另一边——看整手牌含副露，同一手判不听。**这条目前无法配置**：`HandShape` 只有 `nakiCount`、不带副露牌面，结构上给不出另一侧的答案。实测影响 4/72,204 座位（0.006%）。雀魂取哪边未找到一手资料。若将来要支持 EMA，`HandShape` 需要携带副露牌面——那是个宽改动，届时立新 ADR。

## 取舍

被否掉的选项是**「以竞技麻将规则为默认，平台规则作为变体」**。它更「纯」，但代价具体：13 票的对拍是 M0 唯一能校验符与点数长尾的手段，而对拍必须用牌谱来源的规则集跑。若默认值不对齐天凤，则「跑默认配置」与「能对拍」永远是两件事，任何人拿默认值跑出来的点数都不能用真实牌谱验证。

另一个被否掉的是**为三麻提前抽象**（预留 Nukidora 事件、抽象点数表）。F# 的 DU 加 case 时编译器会把所有 match 点找出来，这是优点而非负担——今晚有四次跨票加 case 都是这样被当面抓住的。只做了三处零成本参数化（座位数与牌山构成、向听的合法牌种入参、局数序列），不做投机性泛化。

## 后果

- 加一个规则变体 = 加一个 `Ruleset` 字段与一个预设，而不是在判定逻辑里插 `if`。
- 每条涉及符与点数的黄金用例**必须注明所依据的规则集**，否则对拍出现差异时无法区分「实现错」与「规则集配错」。
- 三麻这道门留着但不做：M0 只跑四麻，`Ruleset` 的形状已能表达三麻，且有一条测试走完整条三麻开局路径守着。
- 现实平台的规则会变（雀魂改过规则）。预设按平台命名意味着它们是**快照**，改动时应新增预设或标注版本，而不是悄悄改旧预设——否则历史 Paifu 的重放会静默失真。
