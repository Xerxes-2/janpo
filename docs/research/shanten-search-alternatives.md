## 1. 方法

### 1.1 基准输入：真实牌局里的手牌，不是均匀随机手牌

备注 N-19 已经踩过一次「随机手牌的数字不具代表性」。本文的主基准是**从真实牌谱里抽的进行中手牌**：

- 语料：`/tmp/janpo-research/corpus/`（12 188 局天凤鳳凰卓 mjai 牌谱，13 票取样脚本拉的）
- 抽法：重放每局，在**每次摸牌后**（3n+2）与**每次打牌/副露后**（3n+1）各存一份快照，
  连副露数一起记（`extract-hands.py`，纯解析，无引擎逻辑）
- 基准集 `structured-hands.txt`：60 个牌谱文件 → 50 000 手；
  对拍集 `structured-corpus.txt`：200 个文件 → 204 661 手

四组辅助输入用来压边界：`random-hands.txt`（20 万，均匀随机 + 随机副露数）、
`quad-hands.txt`（10 万，刻意让 2-3 个牌种握满 4 张，压 `isQuad` / `unpairable` / `deadQuadKinds`）、
`sanma-hands.txt`（10 万，只用三麻牌种集合，压 `legal` 分支）、`/tmp/bench-hands.txt`（5 万，历史随机集）。

**注意不要把本文的 8.7 µs 与风格文档里的 11.98–12.42 µs 直接相减**：那是另一组手牌
（`calculate` 在某个固定结构化手牌上的数字），本文的基线是真实牌谱快照的**混合分布**
（开局那几巡的手牌很散、很便宜，把均值拉下来了）。同一台机器、同一份输入、交错跑，才有可比性。

### 1.2 怎么量

`dotnet fsi` 引编译好的 DLL 直调真实 API（`scripts/fsi/README.md` 的做法）。要改引擎源码做实验，
**把整棵树复制到 `/tmp` 改副本**，每个变体独立 `dotnet build -c Release`，
基准脚本 `bench.fsx` 放进各自的 `scripts/fsi/`（`#r` 的相对路径解析到脚本所在目录，于是各量各的 DLL）。

- 每个变体至少跑 3 轮，**变体之间交错跑**（base → bnb → suit → base → …），抵消机器漂移；
  本次调研期间另一个 agent 在跑 dotnet 构建，load average 8–12，交错是必须的
- 每轮 = 50 000 手 × 10 遍 ≈ 0.3–4.7 s，**计时前先整跑 3 遍预热**
- 报区间不报单值

### 1.3 一个真实的坑：快版本会被分层 JIT 骗

第一版基准每轮只跑 50 000 手一遍。基线要 0.43 s 没问题，剪枝版只要 0.06 s——
**tier-1 还没升上去就量完了**，于是同一版本量出 `4.210 / 1.218 / 1.266 µs` 这种第一轮离谱的三连。
改成「预热 3 整遍 + 每轮 10 遍」之后同版本三轮落在 0.02 µs 以内。

单手重复的基准（`n19-hand.txt`）更敏感：同一进程里 `1.902 / 0.390 / 0.426 / 0.371 µs`，
**第一轮要丢掉**。本文所有单手数字取稳态。

### 1.4 正确性验证矩阵

| 手段 | 覆盖 | 方向 1 | 方向 2 | 方向 3 原型 |
|---|---|---|---|---|

## 2. 方向 1：分支限界剪枝 —— **采纳**

### 2.1 现状为什么慢

`best` 只在叶子处取 min，**完全不参与剪枝**。搜索因此把整棵分解树走完。实测（在副本里加计数器）：

| | 节点数/手 | 叶子数/手 |
|---|---|---|
| 现状 | 均值 10 259，p50 5 284，p99 69 367，max 351 872 | 均值 647 |
| 剪枝后 | **均值 238，p50 133，p99 1 463，max 5 593** | **均值 0.2** |

节点数降 43×，时间只降 6.6×——因为剩下的节点都是「真在分叉」的贵节点，被砍掉的多是廉价的空牌种跳跃
（34 个牌种里手牌只占 ≤14 种，`counts.[index] = 0` 那条分支占了原来节点数的九成，每个约 0.85 ns）。

叶子数降到 0.2 是因为「提前收敛」那一支（见下）在到达 `index = 34` 之前就把答案记完了。

### 2.2 下界怎么来

叶子的值是

```
8 - 2*melds - partials - (hasHead ? 1 : 0) + (unpairable ? 1 : 0)
```

从任一中间状态往下走，只可能做三件事：加面子（收益 +2，吃 3 张）、加搭子（+1，吃 2 张）、
加雀头（+1，吃 2 张）。于是未来收益有两条独立上界：

- **组数**：面子 + 搭子 ≤ 4（雀头另算），所以 ≤ `2 * (4 - melds - partials) + (hasHead ? 0 : 1)`
- **张数**：每张牌最多贡献 2/3 的收益（面子是 2/3，搭子与雀头是 1/2），所以 ≤ `2 * rem / 3`，
  `rem` 是 `counts.[index..]` 还剩的张数

两者取 min 仍是上界。`unpairable` 只会把叶子值**抬高**，忽略它对下界是安全的。所以

```fsharp
let maxGain = min (2 * (4 - melds - partials) + 1 - headBonus) (2 * rem / 3)
if current - maxGain >= best then ()      // 子树里不可能出现比 best 更小的值，剪掉
```

剪枝只在「整棵子树都 ≥ best」时发生，最终的 min 因此一字不变。`rem` 顺着递归传，
每个分支按吃掉的张数减（面子 -3、雀头/搭子 -2、孤张 -1、跳空牌种不变），入口是 `Array.sum counts`。

### 2.3 提前收敛：`maxGain = 0 && hasHead` 那一支，**`hasHead` 不能省**

`maxGain = 0` 且 `hasHead` 时未来收益为 0，且 `unpairable` 要求 `not hasHead`，
所以子树里每片叶子都**恰等于** `current`——直接 `best <- current` 收工，不必走到 `index = 34`。
叶子数从 647 掉到 0.2 全靠这一支。

**但 `hasHead` 这个条件不能省**：无雀头时 `rem ≤ 1` 也会让 `2 * rem / 3 = 0`，
那时叶子可能是 `current + 1`（孤张全是满张、凑不出雀头），少记这个 1 就是错的。
设计时先写错了一版，是「满张偏置」那 10 万手对拍把它顶出来的——
**`quad-hands.txt` 这组输入值得留着**。

### 2.4 改动本身

42 行 diff，其中 14 行是机械地在递归调用上多传一个 `rem`。核心只有开头这一段：

```fsharp
            (rem: int)
            =
            let headBonus = if hasHead then 1 else 0
            let current = 8 - 2 * melds - partials - headBonus
            // 还能长出多少收益：面子每组 2（吃 3 张）、搭子与雀头各 1（吃 2 张）。
            // 组数上限 4（雀头另算），每张牌最多贡献 2/3 的收益。
            let maxGain = min (2 * (4 - melds - partials) + 1 - headBonus) (2 * rem / 3)

            if current - maxGain >= best then
                ()
            elif maxGain = 0 && hasHead then
                // 再也长不出东西，且有雀头（unpairable 不可能成立），子树里每片叶子都等于 current
                best <- current
            elif index >= Tile.KindCount then
                ...
```

不新增 `let mutable`（引擎预算仍是 2），不改公开签名，不碰 `standard` / `calculate` / `deadQuadKinds`。

### 2.5 实测

同机、交错、各 4 轮（`standard`，`calculate` 只多 0.1 µs 的闭式部分）：

| 输入 | 现状 | 方向 1 |
|---|---|---|
| 结构化 5 万手 | 8.667 / 8.992 / 8.817 / 9.358 µs | **1.327 / 1.361 / 1.320 / 1.277 µs** |
| 均匀随机 5 万手 | 1.669 / 1.719 µs | **1.042 / 1.035 µs** |
| 最难 2000 手 | 60.386 / 60.568 µs | **1.349 / 1.356 µs** |
| N-19 那一手（稳态） | 72.663 / 73.336 µs | **0.371 / 0.390 / 0.426 µs** |

**手牌越结构化、越贵，剪枝赚得越多**——正好是真实对局中盘的分布，也正好是 `tenpaiDahai` 的形状。
均匀随机手牌上只有 1.6×，再次印证「随机手牌当基准会低估收益」。

### 2.6 顺带一条：风格文档规则 5 的那行注释要改

`searchStandard` 里现在写着「它不参与剪枝，只在叶子取 min」。剪枝落地后这句话变成假的，
而且 `let mutable best` 的理由从「量过，函数式 +10%」升级成「**它是剪枝上界，跨分支活着**」——
更强的理由。开票时**必须一起改注释与 `docs/agents/fsharp-style.md` 规则 5 的对照表**
（那张表自己写着「会腐烂」）。

至于「纯函数写法 +10%」那个结论：剪枝之后要重测才有意义（纯版本得把上界当参数传下去），
本次没测，不要直接沿用旧数。

## 3. 方向 2：按花色分解 —— 否决

### 3.1 原理与原型

顺子不跨花色，万/筒/索/字四段互不影响。原型对每段独立搜出

```
(用掉几组 blocks 0-4, 有无雀头, 孤张类别 0-2) -> 最大收益 gain = 2*面子 + 搭子
```

的 30 槽可达表（`-1` 表示不可达），再跨段做一次 DP 组合（组数 ≤ 4、雀头 ≤ 1、
孤张类别取 max —— 因为 `anyFloater` 是 OR、`allFloatersAreQuads` 是 AND，编码成 0/1/2 之后正好是 max）。
副露作为起点：`dp[(nakiCount, 无雀头, 无孤张)] = 2 * nakiCount`。

三个约束都是**段内局部**的，所以分解是干净的：`isQuad` 读的是本段自己的原始计数；
`legal.[index-1]` / `legal.[index+2]` 在 `number` 的守卫下不会跨段；`unpairable` 靠孤张类别汇总。

### 3.2 实测与结论

| 输入 | 现状 | 方向 2 | 方向 1 |
|---|---|---|---|
| 结构化 5 万手 | 8.67–9.36 µs | 1.595–1.777 µs | **1.277–1.361 µs** |
| 均匀随机 5 万手 | 1.67–1.72 µs | **0.727–0.903 µs** | 1.035–1.042 µs |
| 最难 2000 手 | 60.4–60.6 µs | 7.725–7.859 µs | **1.349–1.356 µs** |
| N-19 那一手 | 72.7–73.3 µs | 21.099–21.341 µs | **0.371–0.426 µs** |

正确性没问题（60.4 万手 0 差异、固件 0 差异、`differential.sh 30000` 0 差异），但：

- 结构化手牌上比方向 1 **慢 25%**，最难手牌上慢 5.8×，N-19 那手慢 50×
- 原因很直白：**分解只消掉「跨花色的组合爆炸」，消不掉「单花色内部的组合爆炸」**。
  真实牌局里最贵的手牌恰恰是一色化的（最难 2000 手里满眼是清一色型），那正是分解不起作用的地方
- 代码从 260 行涨到 310 行，且引入了 30 槽状态编码这种「读代码要先解码」的东西

**否决。** 它作为方向 3 的中间站是成立的（方向 3 的原型就是在它上面加缓存），但**自身不够快**。

## 4. 方向 3：预计算表（tomohxx 式）—— 否决（可行，但不值）

### 4.1 Fable 那一关：能过

用 Fable **5.13.0** 实测（`dotnet tool install fable`，装得上、跑得通）：

- 把表生成器（方向 2 的段内 DFS + 枚举）单独做成一个 F# 工程，`dotnet fable` 编译成 JS，
  node 26 直接跑，**校验和与 .NET 侧逐位相同**（`entries=192950 checksum=3455703` 两边一致）
- 也就是说：**这条路线在 Fable 侧不存在语言层障碍**，不像 `InlineArray` / `Span<T>`
  （风格文档规则 9 记的那一条）那样一开始就死

一个值得记下的观察：Fable 生成的 JS **不用原生下标**，数组读写走 `item(i, arr)` / `setItem(arr, i, v)`
函数调用（带边界检查）。这对**任何**热循环都有影响，不只是表方案——M1 真上浏览器时，
引擎的热路径在 JS 侧会比 .NET 侧吃更多常数。

### 4.2 表有多大：6.08 MB 原始 / **251 KB gzip**

一段 9 张牌的花色，配置数（每种 0-4、总和 ≤ 14）= **405 350**（字牌 7 种是 43 130）；
tomohxx 用的密集索引空间是 `5^9 = 1 953 125`。我们这套公式每条目要 30 个槽、每槽值域 -1..8，
按 nibble 打包 = 15 字节：

| 形态 | 体积 |
|---|---|
| 稀疏（405 350 条 × 15 B），实测 dump | 6 080 250 B = **6.08 MB** |
| 同一份 `gzip -9`，实测 | **256 965 B = 251 KB** |
| 密集索引（`5^9` × 15 B） | 29.3 MB（浏览器内存里放得下，但没必要） |

稀疏表要一个「五进制码 → 条目号」的排名函数（混合基数 ranking，小表 + 十来次乘加，便宜）。
浏览器侧可以用 `DecompressionStream` 在启动时解 251 KB → 6 MB `Uint8Array`。
**所以「JS 包体积」这一关也能过**：+251 KB 传输、+6 MB 运行时内存。

### 4.3 「启动时算」这条路：naive 版本不行

同一份 F# 代码两边跑（每个配置独立 DFS，**没做前缀共享**）：

| 配置上限 | 条目数 | .NET | node 26 | JS/.NET |
|---|---|---|---|---|
| ≤ 10 张 | 74 396 | 416 ms | 787 ms | 1.9× |
| ≤ 12 张 | 192 950 | 2 873 ms | 8 343 ms | 2.9× |
| ≤ 14 张（真表） | 405 350 | **20 430 ms** | 未跑（按比例约 60 s） | — |

**20 秒（.NET）/ 约 1 分钟（JS）的启动开销显然不能要。** 但要说清楚：tomohxx 是**增量**建表
（沿 9 个位置共享前缀，一次 DP 出全表），比这个 naive 版本快好几个数量级——
本文**没有实现增量建表**，所以上表只是「naive 建表」的上界，不是「建表必然这么贵」。
之所以没继续做：既然 251 KB 的 gzip 资产可以直接发，建表就该是**离线构建步骤**，不是启动步骤。

### 4.4 那为什么还是否决

用「惰性表」原型量了这条路线的**性能上界**：方向 2 的段内搜索结果按五进制码缓存进 `Dictionary`，
命中就跳过搜索（真正的查表版只会更快一点点——把字典换成数组索引）：

| 输入 | 方向 1 | 方向 3（惰性表上界） |
|---|---|---|
| 结构化 5 万手 | 1.277–1.361 µs | **0.642–0.822 µs** |

即：**方向 3 最多比方向 1 再快 2 倍**，把 1.3 µs 变成 0.7 µs。为这 0.6 µs 要付：

1. 251 KB 的构建产物 + 构建步骤 + 校验（表错了没有任何测试会以人能读懂的方式失败）
2. **表是按规则集分的**：`legal` 影响搭子能不能补齐，三麻缺 2m-8m 的万子段要另一张表。
   原型的缓存键只有五进制码，**同一进程里混用两个 `TileKindSet` 会给出错答案**——
   真做必须把段内 legal mask 编进键，或者按规则集各存一份
3. 段内 DP 组合那一层（30 槽状态编码）要长期留在代码里，读起来比现在的 7 个分支难得多
4. 全局可变缓存（惰性版）与引擎「公开函数是纯的、可并发调用」的承诺冲突（见 §5）

真实工作集顺带量了：204 661 手真实手牌只碰到 **22 040** 个花色配置（全表的 5.4%）。
惰性版内存占用不成问题——但这也说明「全表 405 350 条」里九成多是白发的。

**否决**，理由是投入产出比，不是不可行。若将来 profiling 又指到这个函数（例如 M1 在浏览器里
每步要算成百上千次 Ukeire），这条路线**还在**，且本文已经把 Fable 那一关和体积数字钉死了。

## 5. 方向 4：记忆化 —— 否决

### 5.1 一局之内重复得厉害吗

按引擎真实调用形态，在 40 局真实牌谱上统计（缓存作用域取一个 kyoku，键 = 副露数 + 34 长计数）：

| 调用形态 | 查询数 | 命中率 | 每 kyoku 缓存条目 |
|---|---|---|---|
| P1 `tenpaiDahai`：自己摸牌后枚举 14 张打法 | 217 143 | **11.4%** | 均值 449 / 最大 750 |
| P2 `Ukeire`：打牌后对每个可摸牌种查一次 | 705 371 | **39.9%** | 均值 988 / 最大 1744 |
| P3 `isTenpai` / 流局判定：每次手牌变化查一次 | 41 708 | **20.7%** | 均值 77 / 最大 124 |

P2 的 39.9% 来自相邻两巡手牌只差一两张：这一巡「摸 X 打 X」之后的形态，上一巡已经算过。

### 5.2 一次查表要多少

`HandShape` 的 34 长计数编码 + `Dictionary` 查（全命中、5 万手、含数组遍历开销）：

| 键的形状 | 单次 |
|---|---|
| 两个 int64（每种 3 bit） | **52 ns** |
| 35 字符的字符串（Fable 侧最自然） | **65 ns** |

对比：剪枝后一次 `calculate` 是 1 385 ns。所以命中一次省 96%。

### 5.3 为什么还是否决

按 P2 的 39.9% 算，净收益 ≈ `0.399 × 1.33 - 0.06 ≈ 0.47 µs/次`；按 P1 的 11.4% 算只有 0.09 µs。
代价是：

- **全局可变缓存与「公开函数是纯的、可并发调用」直接冲突**（`Shanten.fs` 的模块注释就是这么写的）。
  测试侧四个属性模块开着 `Parallelism = 8`，`Dictionary` 并发写会损坏内部结构——不是理论风险
- 作用域与清空谁负责？一局结束不清就无界增长（每 kyoku 近千条 × 一场 8-12 局 × 一晚 soak）
- 唯一不破坏纯度的形状是**调用方持有缓存并显式传入**（例如 `Ukeire.calculate` 自己开一个），
  但同一次 `Ukeire.calculate` 内部的 34 次查询彼此都不同，**一次调用内命中率是 0**，
  跨调用共享又把缓存推回调用方的状态里

**否决。** 剪枝之后单次只剩 1.3 µs，为 0.1–0.5 µs 破坏引擎最硬的一条性质，不划算。

## 6. 方向 5：微优化 —— 否决（单独不值一张票）

都在方向 1 之上叠加、交错各 3 轮量：

| 变体 | 结构化 5 万手 | 相对方向 1 |
|---|---|---|
| 方向 1 | 1.270 / 1.285 / 1.293 µs | — |
| \+ 空牌种一次跳到底（`skipEmpty`，少算几次下界） | 1.201 / 1.233 / 1.249 µs | **-3%** |
| \+ `numberInSuit` 改查表（省一次 `%`） | 1.217 / 1.226 / 1.229 µs | 与上一行无可测差异 |

`skipEmpty` 的 3% 是真的（在各自的 0.02–0.05 µs 噪声带之外），但**绝对值只有 0.05 µs**，
而它要多一个递归辅助函数。`numberInSuit` 查表**完全没有可测收益**——
34 元素的 `index % 9` 现代 CPU 上比一次数组读还便宜。

分支顺序没单独量：现有顺序（刻子 → 顺子 → 雀头 → 对子搭子 → 两面 → 嵌张 → 孤张）
已经是「收益大的先试」，正是分支限界想要的顺序；剪枝生效后前几支就把 `best` 压下去了。

**否决**：若做方向 1 的票，`skipEmpty` 可以顺手带上（3%），但不值得单开一张票，也不值得为它加代码。
