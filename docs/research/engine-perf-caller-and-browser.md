# 引擎性能第二轮 —— 差距不在函数里，在调用形状和浏览器里

**调研日期**：2026-08-17
**调研者**：研究 agent（**不改引擎源码**，本文是全部产出）
**前置**：`docs/research/shanten-search-alternatives.md`（五个方向的实测）与
`docs/research/shanten-vs-libriichi.md`（苹果对苹果的 15×）。**本文不重复它们的结论，只补它们自己列在
「没做 / 没量的」里的两项**，并据此给出一份可证伪的下一步。

**本轮环境的硬约束（先说清，免得把推算当实测读）**：这台机器上**没有 dotnet、没有 nix**
（`dotnet-install.sh` 走代理拉不下来，exit 56），所以**一个 .NET 侧的数都没有重量**——
本文引用的 `1.37 µs`、`90 ns`、`112 ns` 全部转引自前两轮，出处逐条标注。
**本轮唯一的新实测在 node 侧**（§3），那正好是前一轮标着「没量」的那一格。
源码计数（§2）是数出来的，不是量出来的，表头都写了。

## 0. 结论摘要

前一轮把「差距」钉在 `Shanten.calculate` 这一个函数上，量得很干净：15×，其中算法只占 1.6–1.9×，
语言占 1.6–2.3×，剩下 4–5× 是「每次调用的脚手架 + 查表路径本身极短」的残差。
**本轮的主张是：那 4–5× 的残差不是一个需要解释的谜，是一个口径问题。**

| # | 主张 | 依据 | 强度 |
|---|---|---|---|
| 1 | **产品从来不「调一次」向听，它按批调**。一次信息辅助档的决策要 **≈397 次 `Shanten.calculate`**，不是 1 次，也不是前一轮说的 11 次 | §2，源码计数 | 数出来的 |
| 2 | 前一轮认定的「最密调用点」`tenpaiDahai`（13 µs/回合）**不是最密的**，`Scaffold.calculate` 比它贵 **约 40 倍** | §2.2 | 数出来的 × 前一轮单价 |
| 3 | **浏览器上有一道 .NET 上不存在的悬崖**：V8 里新建一个 `Int32Array(34)` 要 **0.7–1.4 µs**，比普通 `Array` 的 slice 贵 **20–25×**，比复用缓冲贵 **45×**。而引擎每次决策要新建 **≈770 个** 这样的数组 | §3，**本轮实测** | 实测（node 侧） |
| 4 | 前一轮担心的 `item(i,arr)` 下标函数调用**没那么重要**：只值 1.5–2×，量级远小于第 3 条 | §3.2，**本轮实测** | 实测 |
| 5 | 方向 2 / 3 / 4 各自的否决理由**都是在「单次调用」这个粒度上成立的**；换到「一批」这个粒度，三条理由同时失效 | §4.3 | 论证 + 前一轮实测的重新解释 |
| 6 | libriichi 真正的结构优势不是那张表，是**状态增量维护**：它的 `tehai: [u8; 34]` 在事件上原地改，我们每次查询都从 `Tile list` 重建 `HandShape` | §4.4 | 读两边源码 |

**判据没有变**：产品路径上仍然够用（一次决策 0.5–2 ms，夹在 1–30 秒的 LLM 调用之间）。
**变的是「若要动，先动哪里」**：前一轮的答案是「不动，等 MCTS 立项时换基底」；
本轮的答案是「**在动算法之前，先把调用形状和浏览器分配这两件事量掉**——它们比算法便宜得多，
而且是换基底也带不走的那部分」。

## 1. 前一轮的口径漏掉了什么

两份前置调研都是**对着一个纯函数**做的，输入是预先建好的 `HandShape`，计时区里只有
`Shanten.calculate` 自己。这个口径对「这个函数有多快」是正确的，对「引擎有多快」有两个盲区：

### 1.1 计时区之外的东西，产品里在计时区之内

基准是「先把整份输入解析成内存里的手牌数组，再进计时区」（`shanten-vs-libriichi.md` §2.2）。
产品里没有这一步：手牌是 `Tile list`，每次查询都要 `HandShape.create`（`Array.zeroCreate` + 遍历 +
全量合法性校验），每试打一张要 `HandShape.remove`（`Array.copy` + **再来一次全量校验**）。
这些在基准里全被排除在计时区之外了。

### 1.2 量的是 .NET，跑的是浏览器

`shanten-search-alternatives.md` §9 自己写着：「浏览器（Fable 编出来的引擎整体）没量，
只量了表生成器这一个模块的 JS/.NET 比（1.9–2.9×）」。产品是纯静态页面，引擎**只以 JS 形态运行**。
1.9–2.9× 这个常数是从**建表**这一种负载上量的；建表是「顺序写一个大数组」，
而引擎热路径是「小数组反复分配 + 随机下标读写」——这两种负载在 V8 上的行为差得很远（§3 会看到差 20 倍）。

## 2. 一次决策到底调多少次（源码计数）

以下全部由源码数出，**不是实测**。行号是本轮读的版本。

### 2.1 信息辅助档：`Scaffold.calculate`

`src/Janpo.Engine/Scaffold.fs:99` 起。一次决策：

```
Scaffold.calculate
├─ HandShape.create                                  1 次 zeroCreate(34)
├─ Shanten.calculate（当前手牌）                        1 次
├─ Danger.rank                                        1 次（不含向听）
└─ trials：对 D 个去重后的打牌候选各一遍               D ≈ 11
   ├─ HandShape.remove pai                            1 次 Array.copy(34) + 全量校验
   ├─ Shanten.calculate after                         1 次
   └─ tryUkeire (pai :: seen) after   →  Ukeire.calculate:
      ├─ Array.copy(seen)                             1 次 Array.copy(34)
      ├─ Shanten.calculate hand      ← **与上一行刚算过的是同一副手牌**
      ├─ TileKindSet.kinds            每次重建一个 34 元素 Tile list
      └─ 对每个牌种 K（≤34，手里满 4 张的跳过）
         ├─ HandShape.add tile        1 次 Array.copy(34) + 全量校验
         └─ Shanten.calculate drawn   1 次
```

代进 D=11、K=33：

| 量 | 每次决策 |
|---|---|
| `Shanten.calculate` 调用 | **≈ 397** 次 |
| 34 长 int 数组的新建（`Array.copy` / `zeroCreate`） | **≈ 772** 个 |
| `HandShape` 全量校验（`Array.tryFindIndex` 闭包 + `Array.sum` + `Result` 分配） | **≈ 385** 次 |
| 34 元素 `Tile list` 重建（`TileKindSet.kinds`） | 11 次 |

**其中纯属重复的**：`Ukeire.calculate` 内部第一件事是 `Shanten.calculate kindSet hand`，
算的正是 `trials` 上一行刚算完的那副手牌——**每次决策白算 11 次**（2.8%）。这条不需要任何新概念就能去掉，
只要 `Ukeire` 收一个可选的「已知的当前向听」。

### 2.2 「最密的调用点」认错了

`shanten-vs-libriichi.md` §6.1 写：「向听函数被调用得最密的地方是 `RiichiState.tenpaiDahai`，
实测 13.0–13.6 µs/回合」，并据此算出 10⁻⁶–10⁻⁵ 的占比。

但 `tenpaiDahai` 只在**立直合法性判定**那一支上跑（`GameState.fs:529` 与 `RiichiState.canDeclare`），
一回合最多 11 次向听；而**信息辅助档每一手都要跑一次 `Scaffold.calculate`**，397 次。

| 调用点 | 每次决策的 `Shanten.calculate` 次数 | 按前一轮 1.37 µs/次外推（.NET） |
|---|---|---|
| `RiichiState.tenpaiDahai` | ≈ 11 | 13 µs（**前一轮实测 13.0–13.6，与外推吻合**） |
| `RandomPlayer.shantenByKind` | ≈ 11 | ≈ 15 µs |
| **`Scaffold.calculate`（信息辅助档）** | **≈ 397** | **≈ 0.54 ms** |

差 40 倍。**结论的方向没变**（0.54 ms 比 1–30 s 的 LLM 调用仍然小 3–4 个数量级，
「够用」这条站得住），但前一轮那个 10⁻⁶ 的占比数字应该是 10⁻⁵–10⁻⁴，
而且**将来任何 rollout 的成本估计都要按这个数重算**：
前一轮 §6.2 用 13 µs/决策推出「一万次 rollout = 20–30 秒纯向听」；
若 rollout 需要脚手架级别的特征（任何真 MCTS 都需要），同一算式给出的是 **350 秒以上**。

## 3. 浏览器侧：本轮的新实测

### 3.1 方法

`node v22.22.2`，`nice -n 19`，每个变体先整跑预热让 V8 升到优化层，变体之间**交错**跑 5 轮，
**报区间不报单值**（方法照抄前两轮）。三档 reps（10 万 / 100 万 / 500 万）各跑一遍，
结论在三档上一致——所以下面的数不是 GC 抖出来的。

**这里量的不是引擎，是原语**：与前一轮 `prims.fsx` 在 .NET 侧做的事情同构，
只是换到 Fable 的目标平台上。脚本在 `~/janpo-prototypes/js-prims/`（`jsprims.mjs` / `jsalloc.mjs`），
不含任何引擎逻辑，因此不违反「不许把引擎移植到别的语言」。

### 3.2 结果

| 形状 | 谁在用 | node 22 |
|---|---|---|
| `Int32Array[i]` 原生下标读 ×34 | 搜索内循环 | **25.2 – 25.9 ns** |
| `Array[i]` 原生下标读 ×34 | 同上（若关掉 typedArrays） | 30.6 – 31.8 ns |
| `item(i, a)` 带边界检查的函数调用 ×34（Int32Array） | Fable 的下标存取（前一轮的观察） | **52.3 – 56.5 ns** |
| `item(i, a)`（普通 Array） | 同上 | 77.2 – 78.7 ns |
| 搜索内核 5×(读+写) 原生 | `searchStandard` 一个节点的量级 | 12.2 – 14.0 ns |
| 搜索内核 5×(读+写) `item`/`setItem` | 同上 | 18.9 – 20.5 ns |
| **`new Int32Array(34)`** | `HandShape.create` | **661 – 1437 ns** |
| **`src.slice()`（Int32Array）** | `Array.copy`：`standard` / `add` / `remove` / `Ukeire` | **807 – 1968 ns** |
| `Int32Array.from(src)` | —— | 948 – 1425 ns |
| `new Array(34).fill(0)` | 关掉 typedArrays 之后的 `zeroCreate` | 92 – 141 ns |
| **`srcPlain.slice()`（普通 Array）** | 关掉 typedArrays 之后的 `Array.copy` | **35 – 49 ns** |
| **复用: `scratch.set(src)`** | 提议的改法 | **17.0 – 18.8 ns** |
| 复用: 手写 for 拷进 Array | 同上 | 25.8 – 31.8 ns |
| `sumBy` 闭包 ×34 | `chiitoitsu` | 45.0 – 46.5 ns |
| `for` 循环 ×34（同一件事） | —— | 37.2 – 39.3 ns |
| **四遍扫描**（七对子 + 国士 + 死张各自一遍） | 现状 `calculate` | **127 – 134 ns** |
| **融合成一遍**（同样四个量） | 提议的改法 | **68 – 74 ns** |

### 3.3 三条读法

**（a）分配悬崖，这是本轮最重要的一格。** `Int32Array(34)` 的新建/拷贝在 V8 上要 **0.8–1.4 µs**，
而同尺寸的普通 `Array` 只要 **40 ns**，复用一个缓冲只要 **17 ns**。倍率 **20–25× / 45×**。
原因是结构性的：`JSTypedArray` 要连 `ArrayBuffer` 与 backing store 一起分配，
不像普通 JSArray 那样在新生代里 bump 一下就完了。

对照前一轮 .NET 侧实测的 `Array.copy`（34 个 int）= **90.5 ns**：
**同一行代码，浏览器上贵 9–15 倍。**

代进 §2.1 的 772 个/决策：

| | 每次决策的数组分配开销 |
|---|---|
| .NET（前一轮实测单价 90.5 ns） | ≈ 70 µs |
| 浏览器（本轮实测单价 ~900 ns，若 Fable 发 `Int32Array`） | **≈ 0.7 ms** |
| 浏览器（若发普通 `Array`，单价 ~40 ns） | ≈ 31 µs |
| 浏览器（改成复用缓冲，单价 ~17 ns） | ≈ 13 µs |

**也就是说：在浏览器上，「每次调用复制一份 counts」这一件事，很可能比整个向听搜索还贵。**

**（b）`item()` 没那么重要。** 前一轮把 Fable 的 `item(i,arr)` 下标函数调用记为「对任何热循环都有影响」，
是对的，但量级只有 **1.5–2×**（搜索内核 12.2→18.9 ns）。它比第 (a) 条小一个数量级。
**优先级要对调。**

**（c）闭包 vs for 在 JS 上只值 1.2×**，远小于 .NET 侧量到的 3.5×（112.2 → 31.6 ns）——
V8 把单态回调内联得很好。但**四遍扫描融合成一遍值 1.8×**（127→70 ns），这一条两个平台都成立，
因为它省的是遍历本身不是闭包。

### 3.4 一条必须先验证的前提

上面 (a) 的全部分量压在一个假设上：**Fable 把 F# 的 `int array` 编成 `Int32Array`**。
这是 Fable 历史上的默认行为（`--typedArrays`，默认 true），但 **5.13.0 上是不是仍然如此，本轮没有验证**
（这台机器上没有 dotnet，跑不了 `dotnet fable`）。

验证只要两条命令，**这是本文建议的第一件事**：

```bash
cd web && pnpm run fable
grep -n "Int32Array" src/generated/Shanten.js src/generated/HandShape.js | head
dotnet fable --help | grep -i typedarray     # 开关还在不在
```

- 若确实是 `Int32Array`：`--typedArrays false` 是**一个开关**换 20× 的分配成本，
  代价是下标读慢 21%（25.2 → 30.6 ns）。按 §2.1 的调用形状（772 次分配 vs 数千次下标读），
  这笔交易大概率是赚的——但**要实测，不要按本文的比例推**。
- 若已经是普通 `Array`：(a) 那一格的绝对值降到 31 µs/决策，仍然值得改成复用缓冲，但不再是悬崖。

## 4. 若要动，按这个顺序

四级，按「投入 / 产出 / 会不会被将来换基底带走」排序。

### 4.1 A 级：不改任何公开签名的清扫

| 改法 | 依据 | 预计收益 |
|---|---|---|
| `chiitoitsu` / `kokushi` / `deadQuadKinds` 的四遍扫描**融合成一遍** | §3.2 实测 127→70 ns（JS）；前一轮 .NET 侧同类 112→32 ns | .NET ≈ -0.15 µs/次，JS ≈ -0.06 µs/次 |
| `Ukeire.calculate` 收一个「已知的当前向听」，去掉那次重算 | §2.1 | -2.8% 的调用数，零风险 |
| `TileKindSet.kinds` 的结果在 `TileKindSet` 上存一份（它是不可变的） | §2.1，每决策重建 11 次 | 小，但顺手 |
| `canJoinRun` 里那个 `[ a .. b ]` 小 list 换成 for | 读源码 `Shanten.fs:60` | 小；`deadQuadKinds` 命中时才付 |

**这一级不改调用形状，因此收益上限就是前一轮量到的那 0.39–0.43 µs/次脚手架的一部分**：
乐观估计把 `calculate` 从 1.37 µs 压到 **1.15–1.20 µs**，即 15× → 13×。**单独做不值一张票**——
它的价值是和 B 级一起做。

### 4.2 B 级：调用方持有暂存缓冲（**本文推荐的第一张票**）

问题不是 `Array.copy` 慢，是**每次调用都复制**。`searchStandard` 的每一个分支都把 `counts` 原样恢复了
（`Shanten.fs:146-210` 逐条对得上），所以那份副本存在的唯一理由是「公开函数是纯的、可并发调用」
这条承诺——测试侧四个属性模块开着 `Parallelism = 8`，共享一个数组会真的坏掉。

**不必用全局可变缓存来解决它**（那正是方向 4 被否决的理由）。让**调用方**持有缓冲即可：

```
Shanten.calculateWith (scratch: ShantenScratch) kindSet hand
```

`ShantenScratch` 由 `Scaffold.calculate` / `Ukeire.calculate` / `tenpaiDahai` 在**进入批之前**建一个，
批内 397 次调用共用。纯度不变（缓冲是显式入参，不是全局状态），并发不变（各线程各自的批各自的缓冲），
Fable 侧也不需要任何新特性。同一个口子还能把 `HandShape.add` / `remove` 的**全量重校验**免掉：
批内的「试打一张 / 试摸一张」在构造上不可能违反张数与 4 张上限，那次校验是给库外调用者的。

**预计收益（外推，未实测）**：

| | 现状 | B 级之后 |
|---|---|---|
| 每决策 34 长数组新建 | ≈ 772 | **≈ 3** |
| .NET 上这一项的开销 | ≈ 70 µs | ≈ 0.3 µs |
| 浏览器上这一项的开销（若 `Int32Array`） | ≈ 0.7 ms | ≈ 13 µs（改成 `scratch.set`） |

**这是本文认为投入产出比最高的一步**：它不碰算法、不碰语义、不需要任何构建产物、
对拍语料现成（前两轮留下的 45 万手可以原样复用），而且**浏览器上收益比 .NET 上大一个数量级**——
正好补上前一轮完全没看的那一侧。

### 4.3 C 级：把方向 2 / 3 / 4 在「批」这个粒度上合起来

前一轮把五个方向当作**单次调用的互斥替代**来比，于是：

- **方向 2（按花色分解）否决**，因为单次比方向 1 慢 25%；
- **方向 3（预计算表）否决**，因为要构建产物、要按规则集分表；
- **方向 4（记忆化）否决**，因为要全局可变缓存，且「一次 `Ukeire.calculate` 内部的 34 次查询彼此都不同，
  一次调用内命中率是 0」。

**这三条理由都只在「单次调用」这个粒度上成立。** 换到批：

1. 一次批里的 34 个候选手牌，**两两之间只差一张牌**，因此**只差一个花色段**。
   方向 2 把手牌分解成万 / 筒 / 索 / 字四段，那么每个候选**只有 1 段是脏的，3 段可以直接复用**。
2. 于是方向 4 的记忆化换个键就活了：**键不是整副手牌，是（花色段、段内五进制码）**。
   前一轮量到的「一次调用内命中率 0」是**因为键取的是整副手牌**——
   换成段键，一次 `Ukeire.calculate` 内部的命中率是 **~75%**（4 段里 3 段不变）。
   **这是本文认为前一轮最值得回头看的一条。**
3. 缓存**随批创建、随批销毁**，因此：不是全局可变状态（方向 4 的否决理由消失）；
   建立在唯一一个 `kindSet` 之下（方向 3 的「按规则集分表」否决理由消失）；
   不需要任何构建产物（方向 3 的另一条否决理由消失）。

**粗算（外推，全部基于前一轮的实测单价，未实测）**：方向 2 单次 1.60–1.78 µs 里，
若四段搜索与跨段 DP 大致对半，一批 11 个候选的成本约
`4 段基线 + 11 段脏段 + 11 次 DP ≈ 8.4 µs`，对比方向 1 的 `11 × 1.32 ≈ 14.5 µs`，
**约 1.7×**。在真实牌谱最难的那批（一色化手牌）上方向 2 单次要 7.7 µs，批摊薄之后仍可能**输给**方向 1——
所以这条**必须按批实测，不能按本文的比例推**。

**建议**：C 级不立票，先立一个**测量票**（§6 的实验 3）。若批级实测拿不到 ≥2×，就永久钉死这条路，
把结论写回 `shanten-search-alternatives.md`，让下一轮不必再想一遍。

### 4.4 D 级：增量状态 —— libriichi 真正的做法

前一轮花了大力气查清 libriichi 的表（离线生成、200 KB 入库、19.3 MiB 常驻、16 ms 解压），
并正确地指出「查表只值 1.6–1.9×」。**但那张表不是它最重要的结构差别。**

| | janpo | libriichi |
|---|---|---|
| 手牌的常驻表示 | `PlayerState.Hand : Tile list`（`PlayerState.fs:8`） | `tehai: [u8; 34]` |
| 每次查询前 | `HandShape.create` 重建 34 长计数 + 全量校验 | 无——数组一直在那 |
| 摸 / 打之后 | 重建整个 `PlayerState` 记录 | `tehai[i] += 1` |
| 向听 | 每次查询现算 | 事件驱动地算一次，缓存在 state 上 |

也就是说：**libriichi 每个事件算一次向听，我们每次询问算一次。**
这两者之间的比值不是 15×，是「询问次数」——按 §2.1 就是 397。

这条对我们的意义**不是「照抄」**（那会把引擎的不可变性拆掉，而不可变性正是
「同一种子跑两次结果相同」在类型层面成立的原因）。它的意义是划出一条边界：

> **纯度要守在 `GameState` / `PlayerState` 这一层；`Scaffold` / `Ukeire` / `tenpaiDahai`
> 这些「一次决策内的批处理」是引擎内部的局部计算，它们完全可以在批内用可变缓冲，
> 只要缓冲不越出批的边界。**

B 级和 C 级都落在这条边界之内，D 级（把计数常驻进 `PlayerState`、事件驱动地维护）落在边界之外，
是一次**架构决策**，不该在性能票里顺手做。

## 5. 重新看那个 15×

把前一轮的分解和本轮的发现放在一起：

| 成分 | 前一轮的量 | 本轮的补充 |
|---|---|---|
| 算法（查表 vs 剪枝搜索） | 1.6–1.9×（实测） | 不变。**换基底也带得走的只有这一项** |
| 语言 / 运行时 | 1.6–2.3×（实测，`chiitoitsu` 对照） | 不变。浏览器上还要再乘一个未知常数 |
| 残差：每次调用的脚手架 | ~4–5×（残差，其中 0.20 µs 可直接指认） | **这一项大部分是口径造成的**：它按「每次调用」摊，而产品按批调用。B 级把它的分母从 1 变成 397 |
| **浏览器上多出来的一层** | **没量** | **本轮实测：单是 `Int32Array` 分配就 0.8–1.4 µs/次**，可能比搜索本身还大 |

**一句话**：前一轮的「15×」是对的，但它是**单次调用口径**下的 15×。
在产品真正使用的**批口径**下，属于「脚手架」的那 4–5× 里有很大一部分是可以被摊掉的，
而在**浏览器口径**下，还有一项前一轮看不见的、可能更大的开销。
**两个新口径都指向同一个改法（B 级），而且都不需要碰算法。**

### 实验 2（一天）：先量「整局吞吐」，再谈优化

**前两轮都只量了一个函数，从来没量过一局打完要多久。**
若目标真的是「缩小与 libriichi 的差距」，那么可比的单位是 libriichi 的用途——**自对弈吞吐**，

- 我方：`Soak`（`src/Janpo.Engine/Soak.fs`）跑 N 局随机对局，记 局/秒 与 事件/秒，

**本文猜前者**，但这是猜，所以它是实验不是结论。
