# `Shanten.calculate` vs libriichi —— 一次苹果对苹果的对比

**调研日期**：2026-08-16
**调研者**：研究 agent（**不改引擎源码**，本文是全部产出）
**被测的我方版本**：change `noluowslmosn` / commit `467e2215c179`
（`perf(engine): searchStandard 加分支限界剪枝`，即 17 票落地那一版）
**被测的对方版本**：`Equim-chan/Mortal` @ `0cff2b52982be5b1163aa9a62fb01f03ce91e0d2`（2025-09-28），
`libriichi/src/algo/shanten.rs` —— 它自己的文件头写着是
[tomohxx/shanten-number-calculator](https://github.com/tomohxx/shanten-number-calculator) 的 Rust port
**归档**：harness、输入、原始日志、逐手数值全在 `~/janpo-prototypes/libriichi-bench/`（含 `README.md` 的复现步骤）

## 0. 结论摘要

| 口径（真实牌谱抽的结构化手牌 5 万手，交错跑 4 轮 × 2 次） | janpo | libriichi | 倍率 |
|---|---|---|---|
| **三型取最小**（`Shanten.calculate` / `calc_all`） | **1.356–1.389 µs/手**（720–737 K 手/秒） | **0.091–0.093 µs/手**（10.8–11.0 M 手/秒） | **14.6–15.3×** |
| 一般型（`Shanten.standard` / `calc_normal`） | 1.206–1.248 µs（801–829 K 手/秒） | 0.039–0.040 µs（25.0–25.6 M 手/秒） | 30–32× |

**语义对齐**：45 万手逐手对拍，**0 差异**（一般型与三型取最小两列都比，共 90 万个数值）。
和了 = **-1** 两边一致，副露的映射是 `libriichi.len_div3 = 4 - nakiCount`。细节见 §1。

**倍率从哪来**（每一项都是实测，最后一项是残差）：

| 成分 | 量级 | 怎么测的 |
|---|---|---|
| 算法：查表 vs 分支限界搜索 | **1.6–1.9×** | 同在 .NET 上，把 `standard` 换成惰性表原型 |
| 语言/运行时：同一段闭式扫描 | **1.6–2.3×** | `Shanten.chiitoitsu` vs `calc_chitoi`（同一个公式、同一批手牌） |
| 残差：每次调用的脚手架 + libriichi 查表路径本身极短 | **~4–5×** | 见 §4.3，其中 0.20 µs 是可直接指认的 FSharp.Core 常数 |

**一句结论**：**够用，不必优化。** 产品路径上向听函数被调用得最密的地方是
`RiichiState.tenpaiDahai`（每回合枚举打法各算一次），实测 **13.0–13.6 µs/回合**——
夹在 1–30 秒的 LLM 调用之间，占比 10⁻⁶–10⁻⁵ 量级。这 15× 只在**将来的 in-browser MCTS rollout**
里才会变成真问题，而那时该换的不是查表（只值 1.6–1.9×），是执行基底。展开见 §6。

## 1. 先对语义，再谈速度

### 1.1 两边算的是不是同一个东西

逐条对照 `libriichi/src/algo/shanten.rs` 与 `src/Janpo.Engine/Shanten.fs`：

| | janpo | libriichi | 一致？ |
|---|---|---|---|
| 和了的数值 | `agari = -1` | `calc_normal` 末尾 `- 1`，`calc_all` 可返回 `-1` | ✅ |
| 听牌的数值 | `0` | `0` | ✅ |
| 副露怎么进来 | `HandShape.nakiCount`，当作已成面子记进搜索起点 | `len_div3` 参数（13 张 = 4，10 张 = 3……） | ✅ `len_div3 = 4 - nakiCount` |
| 3n+2（已摸牌）能不能算 | 能，`HandShape` 收 `14 - 3n` 张 | 能，`len_div3` 不变（它自己的 `calc_3n_plus_2` 测试就是这么用的） | ✅ |
| 三型取最小 | `standard` / `chiitoitsu` / `kokushi` 三者 min | `calc_normal` / `calc_chitoi` / `calc_kokushi` 三者 min | ✅ |
| 七对子公式 | `6 - pairs + max 0 (7 - kinds)` | `7 - pairs + saturating(7 - kinds) - 1` | ✅ 逐项等价 |
| 国士公式 | `13 - kinds - (hasPair ? 1 : 0)` | `14 - kinds - (pairs>0) - 1` | ✅ 逐项等价 |
| 副露后禁七对子/国士 | `nakiCount > 0` 返回 `None` | `len_div3 < 4` 直接返回一般型 | ✅ |

两处**不影响结果**的差异，测速时要知道它们存在：

- libriichi 会**短路**：一般型 ≤ 0 就不算七对子/国士，七对子把值压到 ≤ 0 就不算国士。
  结构化语料里 16.3%（8 147/50 000）的手牌吃到这条短路。我们三型无条件全算。
- 我们的 `standard` 多两条修正（`deadQuadKinds` 与 `unpairable`），处理「4 张全在自己手里、
  摸不到第 5 张」。libriichi 没有对应代码——**但它的表是穷举出来的，同样的情形表里已经含着**。
  这正是下面那 10 万手「满张偏置」输入要压的地方。

### 1.2 逐手对拍：45 万手 0 差异

同一份输入文件喂两边，各自 dump 出「`<一般型>\t<三型取最小>`」两列，**逐行 diff**（不是校验和——
校验和会掩盖成对抵消的错误）。输入沿用 `searchstandard` 那次调研留下的四组：

| 输入 | 手数 | 一般型差异 | 三型取最小差异 |
|---|---|---|---|
| `structured-hands.txt`（真实牌谱快照，含 0–4 副露、3n+1 与 3n+2 各半） | 50 000 | **0** | **0** |
| `quad-hands.txt`（刻意让 2–3 个牌种握满 4 张，压 `isQuad` / `unpairable` / `deadQuadKinds`） | 100 000 | **0** | **0** |
| `random-hands.txt`（均匀随机 + 随机副露数，0–4 副露各 20%） | 200 000 | **0** | **0** |
| `sanma-hands.txt`（只用三麻牌种集合的手牌，四麻规则集下比） | 100 000 | **0** | **0** |
| 合计 | **450 000** | **0** | **0** |

结构化那 5 万手里有 166 手是 `-1`、7 981 手是 `0`，**两边一个不差**，所以「和了 = -1」这条约定
不是读代码读出来的，是量出来的。

顺带的观察：`sanma-hands.txt` 用**我们的三麻牌种集合**算，与用四麻牌种集合算，
两边也是 0 差异——三麻手牌里根本不含 2m–8m，`1m3m` 这种要靠缺失牌种补齐的搭子无从出现，
`legal` 这一层在这组语料上碰不到。这不代表参数化没用（见 §5.2），只代表**这组语料证不了它**。

## 2. 怎么量的

`docs/research/shanten-search-alternatives.md` §1.2/§1.3 踩过的坑这次原样踩上了，方法照抄并加了两条。

### 2.1 两边共用的输入

`~/janpo-prototypes/libriichi-bench/structured-hands.txt`：12 188 局天凤鳳凰卓 mjai 牌谱里
取 60 个文件，重放并在每次摸牌后（3n+2）与每次打牌/副露后（3n+1）各存一份快照，
连副露数一起记，随机打乱后取 5 万手（`extract-hands.py`，纯解析，无引擎逻辑）。
**不用均匀随机手牌**——它把中盘那些贵的、一色化的手牌稀释掉了，会同时低估搜索的代价和剪枝的收益。

文件格式 `<副露数> <mjai 记法的暗牌...>`，两边各自解析成自己的表示：
Rust 侧 `([u8; 34], u8)`，.NET 侧 `HandShape`。

### 2.2 只计纯计算

两边都是「先把整份输入解析成内存里的手牌数组，再开表，再进计时区」。
I/O、解析、`HandShape.create` 的合法性校验全在计时区之外；libriichi 的表在计时前
`ensure_init()` 显式建好。

### 2.3 Rust 侧

- `cargo build --release`，profile 直接抄 Mortal 工作区根：`lto = true`、`codegen-units = 1`、
  `overflow-checks = false`
- `libriichi` 走 path 依赖 + `default-features = false`（跳过 `pymod` 与 `mimalloc`；
  向听那条路径不分配内存，分配器换不换无关）
- `std::hint::black_box` 同时套在**入参与返回值**上，防 LLVM 把整个循环折掉。
  这个形状与 libriichi 自己 `benches/bench.rs` 里的写法一致（它也是
  `black_box(tehai)` + `black_box(calc_all(...))`），所以不是我自创的量法

### 2.4 .NET 侧

- `dotnet fsi` 引编译好的 Release DLL 直调真实 API（`scripts/fsi/README.md` 的做法）。
  要量的是 17 票落地那一版，而本工作区的 `@-` 还在它前面，所以**把整棵树复制到 `/tmp` 改副本**，
  用 `jj file show -r noluowslmosn` 取那一版的 `Shanten.fs`，独立 `dotnet build -c Release`
- 计时前整跑 3 遍预热（分层 JIT 要把热路径升到 tier-1）
- **reps 按被测时长对齐，不按循环次数**：两边每一轮都落在 ~2 s。
  这是上一次调研写下的教训——快的一侧若按同样的循环次数跑，会在 tier-1 升上来之前就量完，
  量出「首轮 1.9 µs / 稳态 0.39 µs」这种假数。本次 Rust 侧 reps=400、.NET 侧 reps=30，
  正是这个对齐的结果（差 13 倍，与倍率同量级，不是巧合）

### 2.5 交错

两个进程没法真交错，于是**轮流起进程**：libriichi 一轮 → janpo 一轮 → …… 共 4 轮，
每轮进程内跑 2 次，两边各 8 个样本，报区间不报单值。
跑的时候机器 load average 4.3–6.6（另一个 agent 在跑 dotnet 测试），
所有辅助进程 `nice -n 19`，全程单进程串行。

## 3. 实测

### 3.1 主结果（结构化 5 万手）

| | µs/手 | 手/秒 |
|---|---|---|
| janpo `Shanten.calculate` | **1.356 – 1.389** | **720 K – 737 K** |
| libriichi `calc_all` | **0.091 – 0.093** | **10.75 M – 10.99 M** |
| **倍率** | **14.6 – 15.3×** | |
| janpo `Shanten.standard`（一般型） | 1.206 – 1.248 | 801 K – 829 K |
| libriichi `calc_normal`（一般型） | 0.039 – 0.040 | 25.0 M – 25.6 M |
| **倍率（一般型）** | **30 – 32×** | |

8 个样本的离散度：janpo ±1.2%，libriichi ±1.1%。区间宽度远小于倍率，结论不靠边界。

### 3.2 换输入：倍率相当稳

| 输入 | janpo `calculate` | libriichi `calc_all` | 倍率 |
|---|---|---|---|
| 结构化 5 万手（主基准） | 1.356–1.389 µs | 0.091–0.093 µs | 14.6–15.3× |
| 均匀随机 5 万手 | 1.042–1.116 µs | 0.066–0.067 µs | 15.6–16.9× |
| 最难 2 000 手（真实牌谱里搜索树最大的那批） | 0.790–0.946 µs | 0.049–0.051 µs | 15.5–19.3× |

三点值得记：

1. **剪枝之后「最难的手牌」不再最贵**——0.79–0.95 µs 反而比结构化平均还便宜。
   剪枝把搜索抹平了之后，成本主要由「工作集大小 + 每次调用的固定开销」决定，
   而这批只有 2 000 手，整个工作集进得了缓存。
2. 也正因如此，**倍率在小工作集上没有变小反而略大**——所以「.NET 侧数据布局散、缓存不友好」
   **不是**这 15× 的主因。这是一条能排除假设的实测，不是推测。
3. libriichi 在最难那批上只要 0.049 µs，比它在结构化上还快——查表法的成本几乎与手牌复杂度无关，
   这正是查表相对搜索的结构性优势。

## 4. 15× 是怎么来的

### 4.1 算法（查表 vs 剪枝搜索）：只值 1.6–1.9×

把上一次调研留下的**惰性表原型**（方向 3 的性能上界：按花色分解 + 五进制码缓存段内结果）
拿同一份输入、同样交错跑 3 轮：

| 结构化 5 万手 | `standard` | `calculate` |
|---|---|---|
| 剪枝搜索（现状） | 1.206–1.248 µs | 1.356–1.389 µs |
| 惰性表（.NET 上换算法） | **0.655–0.732 µs** | **0.796–0.886 µs** |
| 换算法买到的 | **1.6–1.9×** | 1.6–1.7× |
| 换完之后仍比 libriichi 慢 | | **8.6–9.7×** |

**这是本文最反直觉的一条**：15× 里属于「查表 vs 搜索」的部分只有 1.6–1.9×。
把算法换成和 libriichi 同一类，我们仍然慢一个数量级。
所以「libriichi 快是因为它查表」这个解释**是错的**——它至多解释了 1/8。

### 4.2 语言/运行时：同一段闭式扫描，1.6–2.3×

`Shanten.chiitoitsu` 与 `calc_chitoi` 是**同一个公式、同一批手牌、都没有搜索也没有查表**，
就是一遍 34 元素扫描。这是能拿到的最干净的「.NET vs Rust」对照：

| 结构化 5 万手 | janpo | libriichi | 倍率 |
|---|---|---|---|
| 七对子（`chiitoitsu` / `calc_chitoi`） | 0.117–0.151 µs | 0.066–0.074 µs | **1.6–2.3×** |
| 国士（`kokushi` / `calc_kokushi`） | 0.070–0.078 µs | 0.003–0.005 µs | 14–26× |

七对子那一行是**语言税的诚实估计**：1.6–2.3×。数组下标的边界检查混在这一项里，
本文没能单独把它剥出来（.NET 侧没有关掉边界检查的合法开关）。

国士那一行差 20 倍，但**它不是语言税，是写法**：我们用 `Array.sumBy` + `Array.exists`
两遍闭包遍历 13 个下标、外加一次 `Some` 装箱，libriichi 是 13 次定长下标读、返回 `i8`。
LLVM 能把后者压成十几条指令；前者是两次带虚调用的高阶函数。

### 4.3 残差 ~4–5×：脚手架，不是搜索

不碰引擎，单独量 FSharp.Core 那几个原语在 34 / 13 元素上的单次成本
（`prims.fsx`，3 000 000 次，取稳态）：

| 形状 | 谁在用 | ns/次 |
|---|---|---|
| `Seq.filter \|> Seq.length`（34 个元素） | `deadQuadKinds` | **112.2** |
| 同一件事写成 `for` 循环 | —— | 31.6 |
| `Array.copy`（34 个 int） | `standard` 每次调用一份 counts 副本 | **90.5** |
| `Array.sumBy` × 2（34 个元素） | `chiitoitsu` | 26.8 |
| `Array.sumBy` + `Array.exists`（13 个元素） | `kokushi` | 40.5 |
| `Some` 装箱 × 2 | `calculate` 收三型 | 4.5 |

于是：

- **`standard` 每次调用有 ~0.20 µs 是搜索之外的固定开销**（`Array.copy` 90 ns + `deadQuadKinds`
  的 Seq 管道 112 ns）。libriichi **整个** `calc_normal` 才 0.040 µs——
  也就是说，即使我们的搜索瞬间完成，光这两行也已经是它的 5 倍。
- `calculate` 上再加闭式那两支的 0.19–0.23 µs。**合计 0.39–0.43 µs / 手，占 1.37 µs 的 29–31%，
  一条搜索指令都不在里面。**
- `Some` 装箱 4.5 ns —— 一个听起来很像元凶的嫌疑，实测排除。

libriichi 那一侧对应的东西是**零**：`calc_normal` 是 4 次 base-5 编码（各 9 次乘加）、
4 次数组读、几十次 `u8::min`，状态是一个 10 字节数组，全程无分支、无分配、多半在寄存器里。

**合起来**：1.75 × 2.0 × 4.4 ≈ 15。前两项是实测，第三项是残差；残差里能直接指认的
（0.20 µs 脚手架）已经占掉一大半，剩下的是「表查询本身比任何搜索都短」这件事本身。

### 4.4 顺带：一条可以抄但不值得抄的

libriichi 的 `calc_all` 短路（一般型 ≤ 0 就不看七对子/国士）。我们无条件算三型。
结构化语料 16.3% 的手牌能吃到这条短路，闭式两支合计 0.19–0.23 µs，
**能省下的期望值约 0.03 µs（2%）**——在噪声带边缘，不值得为它改 `calculate` 的形状。

## 5. 顺带查的两件事

### 5.1 表是怎么来的：**离线生成、二进制资产入库、编译期嵌入、运行时惰性解压**

```
libriichi/src/algo/data/shanten_suhai.bin.gz   194 769 B   （数牌段，1 940 777 条）
libriichi/src/algo/data/shanten_jihai.bin.gz     5 715 B   （字牌段，   78 032 条）
```

- **不是 build.rs 生成的**。`libriichi/build.rs` 里只有一行 `pyo3_build_config::add_extension_module_link_args()`，
  与表无关。
- **不是编译期常量表达式**。`include_bytes!` 把两个 `.gz` 原样嵌进二进制。
- **运行时惰性解压**：`static SUHAI_TABLE: LazyLock<Vec<[u8; 10]>>`，首次使用时 `GzDecoder` 解开、
  按 nibble 拆成每条 10 个值。**实测解表 15.5–16.5 ms**（`ensure_init()`，4 次），
  常驻 **20 188 090 B ≈ 19.3 MiB**（2 018 809 条 × 10 B），进程 RSS 38.5 MB。
- **表本身谁生成的**：tomohxx 的 C++ 程序，**在 Mortal 之外跑，产物直接提交进仓库**。
  Mortal 的 FAQ 里承认这条血缘，并说明整个项目采用 AGPL 就是因为 shanten 算法 port 自 GPL 的
  tomohxx（`docs/src/ref/meta.md`）。**这条许可证血缘对我们是硬约束**——想抄它的表要连许可证一起抄。
- **构建耗时**：对 Mortal 的构建来说是 **0**（表不参与构建，只是 200 KB 的资产被嵌进去）。
  作对照：上一次调研里我们 naive 建同类表在 .NET 上要 **20.4 s**（405 350 条），
  node 上按比例约 60 s——所以「离线生成 + 提交产物」不是偷懒，是唯一合理的做法。

**对我们的意义**：我们否决查表方案的两条理由里，libriichi 只回避了第一条，没回避第二条。

1. 「要构建产物」——它确实是构建产物，只是把构建挪到了仓库之外，代价转成
   200 KB 入库 + 19.3 MiB 常驻 + 16 ms 启动。我们的同类表估算是
   gzip 251 KB / 6.08 MB 原始（编码更紧，因为我们每条只存 30 槽），量级相当，**这一关我们也能过**。
2. 「按规则集分表」——它**根本没有规则集这个维度**（见 §5.2），所以这个问题在它那里不存在。
   我们有 `TileKindSet`，问题仍在。

### 5.2 三麻：**不支持**

- 全仓库（`.rs` / `.md` / `.toml`）grep 不到 `sanma` / `three-player` / 任何三麻字样。
- 牌种是硬编码的 34（`MJAI_PAI_STRINGS` 里 3×9 数牌 + 7 字牌 + 3 赤 + 1 unknown），
  向听的两张表按 `5^9` / `5^7` 的密集五进制索引建（实际用到 1 940 777 / 78 032 条），
  **表结构本身就假定了「9 个连号的数牌花色」**。
- `calc_normal` 的签名是 `(&[u8; 34], u8)` —— **没有牌种集合参数**。
  想支持三麻要么另生成一套表，要么在表外做修正；两条路 Mortal 都没走。

也就是说：**我们的 `TileKindSet` 显式入参在 libriichi 里没有对应物。**
这是设计取向的差别，不是我们做多了——libriichi 是给天凤四麻训练 AI 用的单一规则集库，
而 arena 的 spec 要求规则集可配。查表方案要保住这个能力，就得把段内 `legal` mask 编进表的键
（或按规则集各存一份），这正是上次否决它的第 2 条理由，**libriichi 没有给出更便宜的答案**。

## 6. 够不够用

判据是产品路径，不是 benchmark 分数。

### 6.1 现在的路径：够用，差 5–6 个数量级

引擎在浏览器里一手一算，夹在 1–30 秒的 LLM 调用之间。向听函数被调用得最密的地方是
`RiichiState.tenpaiDahai`（立直合法性 + 宣言牌限制共用它，每回合对每种可打的牌各算一次向听）。
**实测（结构化语料里全部 3n+2 手牌 20 000 手，4 轮）：13.0–13.6 µs/回合。**
（一致性检查：14 张去重后约 11 个牌种 × 1.37 µs ≈ 15 µs，与实测同量级。）

| | janpo 现状 | 若有 libriichi 的速度 | 一次 LLM 调用 |
|---|---|---|---|
| 一个回合决策 | **13 µs** | ~1 µs | 1–30 s |
| 占回合总延迟 | **0.0000004 – 0.000013** | 忽略不计 | 1 |

浏览器侧会再乘一个常数（Fable 生成的 JS 用 `item(i, arr)` / `setItem` 函数调用做数组读写，
上次调研在建表这种数组密集负载上量到 node/.NET 是 1.9–2.9×），
即便按 3× 算也是 ~40 µs/回合。**结论不变：够用，不必优化。**

### 6.2 将来的路径：MCTS rollout 才是那个会疼的地方

粗估（明确标为外推，不是实测）：一局 kyoku 约 70 个打牌决策，每个决策的向听部分 13 µs
→ **每次 rollout 约 0.9 ms 的纯向听开销**（.NET），浏览器里 2–3 ms。
一万次 rollout = **20–30 秒，只算向听**。同样的工作量在 libriichi 那一侧是 1.5–2 秒。

所以 15× 在那个场景里是真的。但**该做的事不是把 F# 换成查表**：

- 换查表只值 **1.6–1.9×**（§4.1 实测），20–30 秒变成 12–18 秒，仍然不能用；
- 剩下的 8–10× 在语言、运行时和每次调用的脚手架里，**在 F#/Fable/JS 这条基底上拿不回来**;
- 真要做 in-browser MCTS，问题是「rollout kernel 跑在什么上面」（wasm？），
  而那是一次基底决策，不是 `Shanten.fs` 的一次重写。

**因此建议**：现在不动向听。等 MCTS 立项时，把这份数字当作「F#/JS 基底的性能天花板」的输入，
在那时一并决定基底，而不是现在为一个不存在的瓶颈预付复杂度。

## 7. 复现

全部材料在 `~/janpo-prototypes/libriichi-bench/`（harness、输入、原始日志、45 万手的逐手数值）。
`README.md` 里有完整命令。要点三条：

1. **先跑 `dump` / `verify` 对数值，0 差异之后再跑 `bench`。**
2. **reps 按被测时长对齐**（两边都落在 ~2 s/轮），不要按循环次数——按次数对齐会让快的一侧
   在分层 JIT 升上来之前就量完。
3. **交错起进程**，报区间不报单值；`nice -n 19`，串行跑。

Rust 侧的树在 `/tmp/libriichi-bench/`（Mortal 的 clone + bench crate），**易失**；
数字与 harness 已抄进归档目录，重跑只要重新 clone 那个 commit。
