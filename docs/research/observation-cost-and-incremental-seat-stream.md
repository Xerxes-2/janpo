**一句话**：问题不是「要不要造增量状态」，也不是「造它有多难」——**它已经造好了、是公开 API、牌桌在用**。
问题只是**决策路径没接上去**，而接上去是一个新入口加三个调用点。
**但收益的正当理由只有一个半**：浏览器主线程上每决策省 1.1 ms（产品路径，本来就够用）、
以及 `TablePage` 危险度面板每帧那 2.1 ms（这条是真的卡人）。
**CI 与扩语料这两个理由本轮被量掉了。**

## 2. `Observation.ofState` 的成本分布

### 2.1 掩蔽 / fold / 组装

`Observation.ofState seat state` = `ofEvents ruleset seat (GameState.events state)`
= `SeatStream.start |> SeatStream.advanceAll events |> SeatStream.observation`，
而 `advanceAll` 逐条做「`MaskedEvent.forSeat`（掩蔽）→ `SeatStream.absorb`（fold）」。
三段各自可以单独调，因此可以直接量：

| 段 | 怎么量的 | **.NET** µs/决策 | **浏览器** µs/决策 |
|---|---|---|---|
| ① 掩蔽 `MaskedEvent.stream`（= `Observation.stream`） | 只掩蔽不 fold | **1.6**（1.6–1.8） | **2.80**（2.79–2.95） |
| ② 掩蔽 + fold + 组装 `Observation.ofState` | 现状全价 | **287.0**（286.0–291.6） | **1247.2**（1234.7–1258.0） |
| ③ fold + 组装 `Observation.ofMasked` | 掩蔽预先做好，不计时 | 287.8（285.9–291.1） | 1251.5（1249.0–1273.4） |
| ④ 只组装 `SeatStream.observation` | 流已 fold 好 | **0.3**（0.3–0.3） | **0.07**（0.06–0.12） |
| ⑤ 只取历史 `SeatStream.events`（`List.rev`） | 流已 fold 好 | 1.7（1.7–1.8） | 0.83（0.82–1.06） |
| ⑥ 整包 `DecisionPackage.forSeat` | 现状全价 | **498.2**（495.8–502.3） | **2118.7**（2101.3–2125.4） |

**读法**：

- **fold = ② − ① − ④ = 285.1 µs（.NET，99.3%）/ 1244.4 µs（浏览器，99.8%）。**
  掩蔽与组装加起来不到 0.7%。「掩蔽贵不贵」这个问题可以永久划掉。
- `Observation.ofState` 占整包 **57.6%（.NET）/ 58.9%（浏览器）**，与票 55 §2.5 的 282.7/487.6 = 58%
  逐位吻合（那是同一台机器、同一份语料、改后树）。
- **浏览器比 .NET 慢 4.3×**（1247/287；整包 2119/498 也是 4.3×）。
  第 3 轮 §1.2 只有一个从「建表」这种负载上量的 1.9–2.9×，**这条路上的比值是 4.3×**，比那个大。
- `DecisionPackage.forSeat` 里**还有第二趟 O(n)**：`Observation.stream seat state`（历史）。
  它只值 1.6 / 2.8 µs（①），**不是问题**——但改造之后它跟着一起变成 `SeatStream.events`（0.83 µs）。

### 2.2 斜率：单次是线性的，O(n²) 是每手重来攒出来的

按决策点此刻的 n 分桶，各桶单独计时：

| n 区间 | 点数 | **.NET** `ofState` µs | µs/条 | **浏览器** `ofState` µs | µs/条 |
|---|---|---|---|---|---|
| [0,20) | 134 | 38.6 | 3.5 | 199.9 | 19.9 |
| [20,40) | 142 | 125.0 | 4.2 | 558.9 | 19.5 |
| [40,60) | 143 | 221.1 | 4.4 | 961.0 | 19.7 |
| [60,80) | 150 | 301.5 | 4.3 | 1323.0 | 19.2 |
| [80,100) | 133 | 354.3 | 3.9 | 1543.0 | 17.3 |
| [100,130) | 210 | 412.3 | 3.6 | 1853.4 | 16.2 |
| [130,200) | 167 | 486.5 | 3.2 | 2436.6 | 17.2 |
| （同一桶的掩蔽） | | 0.2 → 2.4 | | 0.5 → 7.5 | |

**单次调用对 n 线性**（每条事件的单价在整个区间上不涨，两侧都是）。
这一条值得写清楚，因为 `SeatStream.absorb` 里有一处**看着像 O(n)** 的东西：
见逃判据 `canRon` 会走 `yakuContext`，而它每次都要 `stream.Log |> List.choose MaskedEvent.publicEvent`
扫一遍已有的日志。按上表，那一项在 n≤160 的范围内**淹没在噪声里**（若它主导，µs/条会随 n 线性上涨，
而实测是平的甚至略降）。**同样地量了 `advance` 的单价随已吃条数的变化**：

| 已吃条数 | .NET µs/条 | 浏览器 µs/条 |
|---|---|---|
| [0,20) | 6.92 | 39.72 |
| [20,40) | 4.10 | 23.91 |
| [40,60) | 3.60 | 20.78 |
| [60,80) | 2.22 | 14.95 |
| [80,100) | 2.97 | 18.62 |
| [100,130) | 3.06 | 17.37 |
| [130,200) | 3.61 | 19.68 |

`advance` 实际上是 **O(1)**（头一桶偏高是因为 `start_kyoku` 那一条要把整份开局条件铺开）。
**因此增量维护是真的增量，不是「常数小一点的 O(n)」。**

### 2.3 票面点名的那两手：第 5 手与第 60 手

按**手序**而不是按 n 取样（种子 1–40，每局取第 k 手那个决策点）：

| 第几手 | 局数 | 平均 n | **.NET** `ofState` µs | 掩蔽 µs | **浏览器** `ofState` µs | 掩蔽 µs |
|---|---|---|---|---|---|---|
| **5** | 40 | 8.8 | **41.4** | 0.2 | **134.3** | 0.6 |
| 20 | 40 | 33.5 | 188.5 | 0.8 | 728.1 | 1.5 |
| 40 | 40 | 66.2 | 296.7 | 1.6 | 1183.4 | 3.4 |
| **60** | 40 | 101.4 | **401.8** | 3.0 | **1680.0** | 4.9 |
| 80 | 40 | 136.5 | 493.1 | 3.0 | 2130.4 | 7.5 |

**第 5 手 → 第 60 手：.NET 41.4 → 401.8 µs（9.7×），浏览器 134.3 → 1680.0 µs（12.5×）**，
而同期 n 涨 11.5×——**斜率就是 n 本身**。一局把这条线下的面积加起来，就是 §3 那个 Σn。
一局 88.6 手，后半局每一手都在付浏览器 1.5–2.1 ms。

## 3. 一整局里它被调多少次（判据：先问一趟做几次）

`Kyoku.run` / `Table.pending` 的问法是**每步只问合法动作集的第一家**；
响应阶段同时等多家时，每收一家答复就少一家，因此**每一家仍是各自一步被问到**。
`DecisionPackage.forSeat` 每步最多建一份包，**四家不是各建一份**。

种子 1–40，四家同一种选手：

| | 均匀随机 | 有主见 |
|---|---|---|
| **一局被问次数**（= `Table.pending` 次数 = 决策包次数上限） | **88.6**（80–101） | **76.9**（24–97） |
| 「合法动作集里每一家都建一份」的口径（上界） | 89.1（80–105） | 77.6（25–97） |
| 其中响应阶段（同时等 >1 家）的步数 | 0.5（0–4） | 0.7（0–4） |
| 一局的事件条数（终局那一刻） | 152.3（144–161） | 121.8（40–146） |
| 被问时事件流的平均长度 n | 75.6 | 65.5 |
| **Σn（一局所有被问点的 n 之和）** | **6703**（5738–8144） | **5035**（487–7370） |

按座位摊（均匀随机 40 局）：座位 0（亲）22.9 次，其余三家 21.8 / 22.1 / 21.9 次。

**Σn 就是 O(n²) 的那个和**：现状一局要 fold **6703 条事件**（只为被问的那一家）。
增量维护四家各一份是 **152.3 × 4 = 609 次 `advance`**——**少 11.0×**；
若只维护一家（真牌桌上常见：只有一个 LLM 座位）是 152.3 次，**少 44×**。

**牌桌上真正调几次**：`Table.decide` **只给 LLM 座位建包**（bot 座位当场就出手，不建包）。
所以四个 LLM 座位 ≈ 88.6 次/局，一个 LLM 座位 ≈ 22 次/局。

**还有一个不在决策路径上的调用点，它按帧调**：`TablePage.dangerPanels`（`TablePage.fs:1223`）
在**每次渲染**时对每个「摆得出危险度」的座位调一次 `DecisionPackage.forSeat`。
危险度开关默认关（`ShowDanger = false`），一旦打开，**每帧 2.1 ms 挂在主线程上**（浏览器实测，§2.1 ⑥）。
这是本轮找到的**唯一一处会被人直接感觉到的成本**。

## 4. 第 3 轮的「D 级」预估到底过没过时

**票面与登记册都把这件事记成「第 3 轮把这个方向叫 D 级并预估成大工程」。逐字核对之后，这个记法不准。**

第 3 轮 §4.4「D 级：增量状态 —— libriichi 真正的做法」那张表比的是**手牌的常驻表示**：

> | | janpo | libriichi |
> | 手牌的常驻表示 | `PlayerState.Hand : Tile list` | `tehai: [u8; 34]` |
> | 每次查询前 | `HandShape.create` 重建 34 长计数 + 全量校验 | 无——数组一直在那 |

结论那句是：「**D 级（把计数常驻进 `PlayerState`、事件驱动地维护）落在边界之外，是一次架构决策，
不该在性能票里顺手做**」。而同一份文档 §7「没做 / 没量的」自己写着：
「**`Observation` / `GameState` / `Paifu` 一行没读性能**」。

所以：

- **对「34 长牌种计数常驻进 `PlayerState`」这件事，第 3 轮的预估仍然成立**，本轮没有推翻它。
  那件事至今没做，也不该在性能票里顺手做。
- **「观测的增量维护也是那种大工程」这个读法是错的**，而它正是登记册与票 58 票面里的那句。
  错在两处：
  1. **它已经存在了**。票 29a（**早于**第 3 轮一天）就造好了 `SeatStream.start / advance / absorb /
     observation / events`，**是公开 API**，牌桌 `Table.Views` 每座位持一份在用。
  2. **它不越第 3 轮画的那条边界**。第 3 轮的边界是「纯度要守在 `GameState` / `PlayerState` 这一层」，
     而 `SeatStream` **是不可变记录、`advance` 是纯函数**（§7）：它不往任何地方常驻可变状态，
     它只是把一个**值**从调用方传进来。这与票 55 的 `ShantenScratch`「显式入参不是全局状态」是同一形状，
     而第 3 轮把那一类明确划在**边界之内**。

**因此本轮的正确说法是**：第 3 轮没估过这件事（它没读 `Observation`）；
把它的 D 级结论套到这件事上是一次张冠李戴，**本轮把它拆掉**。
真实代价见 §5：一个新入口 + 三个调用点。

**顺带一条**：`Observation.ofState` 的文档注释**自己就写着**

> **一次性全流 fold**：逐手推进的牌桌别每帧调它，拿 `SeatStream` 增量维护。

而 `DecisionPackage.forSeat` 每被问一手就调它一次。**这是「记录声称了一件事，而执行体不存在」的又一例**
（`docs/agents/judgments.md` 开头点名的那类错）：注释指了路，没有任何东西执行它。

### 5.1 新入口的形状

票 55 的先例（`Shanten.calculateWith (scratch) …`，公开的那一支原样保留）直接照搬：

```fsharp
/// 调用方已经持有这个座位的掩蔽流时走这一支：观测与历史直接取自它，不重头 fold。
/// **流必须是「这个座位、这个规则集、吃过 `GameState.events state` 全部事件」的那一份**——
/// 不是的话给出来的包是错的（见 §8 的闸门）。
val forSeatWith: SeatStream -> Seat -> GameState -> DecisionPackage option

/// 原样保留：内部就是「自己起一条流、吃完全部事件、再走 forSeatWith」。
val forSeat: Seat -> GameState -> DecisionPackage option
```

**签名边界一个字都没松**（20 号票立的那条）：`SeatStream` 是 F# 侧的值，
**不上 wire、不过 F#/TS 接缝**；跨界的仍然只有决策包的 JSON 与回来的一个动作 id。
`GameState` 仍然要传，因为 `legalActions` 与 `ruleset.TileKinds` 只有它给得出——
**而 `legalActions` 是免费的**（票 55 §2.5 实测 0.1 µs，合法动作集在 `step` 里就算好存进 `Phase` 了）。

### 5.2 新的失效模式：调用方给了一份「不是那一份」的流

这是这条路**唯一**新增的失效模式，三种形态：

1. **忘了推进**（流比局面旧几条）；
2. **给错座位**（流是别家的）；
3. **规则集不同**（`SeatStream.start` 收 `ruleset`，与 `GameState.ruleset state` 可以不是一份）。

三种都会**静默地**给出一份错包（不是异常、不是 `None`）。守法见 §8.3。

### 5.3 被否决的做法，与各自的理由

| 做法 | 为什么否决 |
|---|---|
| **把 `Observation` 缓存在 `GameState` 里**（每座位一份，`step` 时顺手更新） | 把座席投影塞回权威状态里，直接拆掉票 29a 的形态（「全项目只有一条掩蔽法则」），而那正是判据 9（一个投影里出现第二个「只能从历史算」的字段就是形态错了）当初把它推到现在这个形态的理由。而且它让四份观测跟着每一步走，比本文的做法**更贵**（同时维护四家无论有没有人问） |
| **模块级可变缓存**（键 = 座位 + 事件流，`ofState` 内部 memoize） | 属性测试开着 `Parallelism = 4/8`，共享可变缓存会真的坏掉。这正是第 3 轮否决「方向 4（记忆化）」与票 55 选择「缓冲是显式入参」的同一条理由 |
| **让 `forSeat` 收「上一次的 `Observation` + 新增事件」** | 那就是 `SeatStream` 的定义，只是把它拆成两个参数。`Observation` 不够用：`absorb` 还要 `PendingRon` / `HoraEnded` / `Opening` / 倒序的 `Log`——这些都不在 `Observation` 里。**重造一个已经存在的类型** |
| **只优化 fold 里最贵的那一段（见逃判据 `canRon`），保留从头 fold** | 单次仍然是 O(n)、一局仍然是 O(n²)，只是常数小一点；而且 29a 已经加过一次短路（`PlayerState.isAgariWith`，一局 0.93 → 0.56 ms，出处见 §10），还能再拧出来的不多 |
| **只改 `TablePage.dangerPanels` 一处**（那是唯一人感觉得到的） | **这是真正的最小备选，写下来备查**：改动面三行、风险最小，但它仍要 `forSeatWith` 这个入口才做得了（否则面板只能继续调 `forSeat`）。一旦入口建了，`Table.decide` 那一行是白送的。**否决理由：省下的不是钱，是一行** |
| **把决策包的 JSON 缓存起来** | 答非所问：每一手的包都不同，缓存命中率是 0（与第 3 轮对「整副手牌作键」的判断同形） |

### 8.3 三条结论

1. **A（回归守卫）是真的，而且正是这条路需要的那道保险的一半**：它守住「fold 出来的观测 = 引擎的权威状态」。
   29a 报告说它「比闸门更硬」，本轮实测证实了这句话。

2. **C 是恒真式，永远红不了。** 逐字看：

   ```fsharp
   // 测试这一侧
   (SeatStream.start ruleset seat, events) ||> List.fold (fun s e -> SeatStream.advance e s) |> SeatStream.observation
   // 被比的那一侧：Observation.ofEvents = start |> advanceAll events |> observation
   // 而 advanceAll = (stream, events) ||> List.fold (fun current event -> advance event current)
   ```

   两侧是**同一个 fold**。它不是弱闸门，是**没有闸门**——判据 3 说「一条永远执行不到的断言与一条从不失败的断言，
   危害相同」，这条属于后者。它顶着「增量维护与一次性全流 fold 给出同一份观测」这个名字，
   而**真正在守这件事的是 B**，B 只在 Web 侧、只有一颗种子、是 `Fact` 不是属性。

   **注意：不许删它、不许放宽它**（`AGENTS.md` 硬约束 3）。要动只能往硬里改（§8.4 的 G2）。

3. **B 是真的，但覆盖面太窄**：一颗种子、一局、四家均匀随机、Web 测试工程。
   决策路径要走增量之后，**引擎侧需要一条同形的属性**（§8.4 的 G1）。

### 8.4 实现票要立的三道闸门

| # | 闸门 | 为什么 | 反向自证怎么做 |
|---|---|---|---|
| **G1**（必须） | 引擎侧属性：**任意可达对局、逐手推进维护 `SeatStream`，`forSeatWith` 建出的包与 `forSeat` 建出的包逐字段相同**（两种选手、每一手、每个座位） | 这正是新失效模式（§5.2）的定义。它**不是恒真式**：左侧吃的是 `step` 吐出的 `produced`，右侧吃的是 `GameState.events state`，两者是不同的列表 | 把某一步的 `advanceAll produced` 去掉 → 必须红；把流换成别家的 → 必须红 |
| **G2**（便宜） | 把 C 那两条从恒真式改硬：被比的那一侧换成 `Observation.ofMasked ruleset seat (MaskedEvent.stream seat events)`（先掩后 fold 的**另一条代码路径**），并在注释里写明它守不住 `absorb` 里的错（那是 A 的活） | 判据 2：写下不变量先问谁执行它。现在这条只有名字没有执行体 | 弄坏 `MaskedEvent.stream` 的 `List.choose` 那一支 → 必须红 |
| **G3**（顺手） | B 从一颗种子扩成一批种子 × 两种选手 | 覆盖面 | 同反向自证二 |

**外加一条可选的运行时守卫**：给 `SeatStream` 加一个 `Absorbed: int` 私有字段，
`forSeatWith` 在开头核 `Absorbed = List.length (GameState.events state)`，不等就**退回从头 fold 的 `forSeat`**
（不是返回 `None`——静默降级好过静默出错）。代价：一次 `List.length`，
按 §2.1 ⑤ 的量级约 0.1 µs（.NET）/ 0.8 µs（浏览器），**相对 228 / 980 µs 可以忽略**。
它挡不住「给错座位」和「规则集不同」，那两条只有 G1 挡得住。

## 9. CI 与语料：这两个理由本轮被量掉了

登记册的第 4 条规矩说「产品路径上不做没量过的优化；做优化的正当理由通常是**别的**——
例如 CI 的 CPU 总量、或扩大语料的可行性」。**本轮把这两个理由分别量了一次，两个都不成立。**

### 9.1 CI：≈ 0.33%

**做法**：在 `/tmp` 的树副本里给 `Observation.ofState` / `Observation.stream` / `DecisionPackage.forSeat`
各加一个 `Interlocked` 计数器（`ofState` 顺带累加它 fold 的事件条数），
注册 `ProcessExit` 把数字写到文件，然后跑**全量** `dotnet test`（818 条全绿）。

| 进程 | `ofState` 次数 | fold 的事件总条数 | `forSeat` 次数 | `Observation.stream` 次数 |
|---|---|---|---|---|
| Janpo.Web.Tests | 1 126 | 83 450 | 778 | 778 |
| Janpo.Engine.Tests | 4 587 | 279 464 | 1 700 | 2 698 |
| **合计** | **5 713** | **362 914** | **2 478** | **3 476** |

`ObservationProperties`（33.7 s）/ `DecisionPackageProperties`（34.4 s）这两个模块的钱
绝大部分花在 **FsCheck 的局面生成器**上（生成器要真打对局），不在观测本身。

### 9.2 扩语料：0

牌谱回放与对拍那条路（`src/Janpo.Engine/Replay.fs`、`tests/Janpo.Engine.Tests/PaifuDifferential.fs`、
`PaifuReplay.fs`）**一次 `Observation` 都不建**（`grep` 只命中一个同名不同物的 `HoraObservation`）。

> **`Observation.ofState` 的 O(n²) 不是扩语料的天花板。** 登记册里那句「O(n²) 是它的天花板之一」
> 应当删掉——票 57 那条路上根本没有这一段。

## 11. C 级（段级缓存）顺带估一下

第 3 轮 §4.3 的 C 级是：把手牌按万/筒/索/字分成四段，缓存**（花色段、段内五进制码）→ 段内搜索结果**，
缓存随批创建随批销毁。它的依据是「一批里的候选两两只差一张牌 ⟹ 只差一段 ⟹ 4 段里 3 段可复用，
一次 `Ukeire` 内命中率 ~75%」，粗算批级约 **1.7×**，**第 3 轮自己写着「必须按批实测，不能按比例推」**。

拿票 55 的实测把两条路放在同一张表上（浏览器口径，每决策）：

| | 现状 | 只做 C 级 | 只做本轮这条路（记作 D′） | **两条都做** |
|---|---|---|---|---|
| `Observation.ofState` + 历史 | 1250 µs | 1250 | **~104** | ~104 |
| `Scaffold.calculate` | 860 µs | **~506**（1.7× 的乐观上限） | 860 | ~506 |
| 其余（动作 label、`Danger`、组装） | ~48 µs | ~48 | ~16 | ~16 |
| **整包** | **2158** | **1804** | **980** | **626** |
| 倍率 | — | **1.20×** | **2.20×** | **3.45×** |

| | C 级 | D′（本轮这条路） |
|---|---|---|
| 改的是什么 | **算法**：花色段分解 + 跨段 DP + 缓存键 | **接线**：一个新入口 + 三个调用点 |
| 语义风险 | 高：换搜索结构，一色化手牌上第 3 轮量到方向 2 单次要 7.7 µs（可能批摊之后仍输给方向 1） | **零**：观测的每一个字段都由同一份 `absorb` 算出来，本轮已在 .NET **14 340 个（座位×手）点**与浏览器 **7 248 个点**上逐字段对过，**分歧 0 处** |
| 前置 | 需要先立一个测量票（第 3 轮 §6 实验 3），拿不到 ≥2× 就永久钉死 | 本轮就是那个测量，**已经拿到 2.2×** |
| 收益 | **1.20×**（乐观上限） | **2.20×**（实测） |
| 能不能同时做 | **能**：两者代码上完全不相交（一个在 `Observation`/`DecisionPackage` 的接线，一个在 `Shanten`/`Ukeire` 的搜索）。做完 D′ 之后 `Scaffold` 占 88%，C 级的分母反而更干净 | 同左 |

**建议**：**先做 D′，C 级仍然按第 3 轮说的先立测量票**。理由不是「C 级不好」，是顺序：
D′ 便宜十倍、风险低一个数量级、收益大一倍，而且做完之后 C 级要打的靶子（`Scaffold` 占 88%）更清楚。
