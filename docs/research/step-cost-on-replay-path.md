# 重放路径上 `GameState.step` 的 37µs 花在哪（引擎性能第 6 轮，票 64）

**一句话结论：37µs 里七成二是两批「向听类试算」在白跑——打牌后的振听簿记
（`refreshFuriten` → `AgariShape.waits`，34 次试摸，占 55%，而其中 83.6% 的手根本不听牌）
与每手的立直合法性检查（`RiichiState.canDeclare` → `tenpaiDahai` 逐张试打，占 17%）。
两条都能用「先花一次向听计算把不听的手挡掉」换掉，**语义逐字节不变**（已在 /tmp 树副本预验证：
129,179 局真牌谱重扫差异输出逐字节相同、721 条测试全绿、20 万手采样零反例），
引擎重放实测 2.06×。重放确实也在付「合法动作集只被 `List.contains` 消费」的钱（约三成），
但**最大的两笔在对局路径上同样是白花的**——修引擎本体比开重放专用道便宜，且两条路径都受益。**

本轮遵守登记册五条规矩：只量不改（`src/` 零改动，实验全在 /tmp 树副本）；先问一趟做几次；
回答上一轮挂的「step 是黑盒」；语义不动（预验证三道闸都过了）；本文落地时登记册同步更新。

## 2. 一趟做几次（先于一趟多贵）

**60.3 次 step/局**（893 局实测；票 62 的 61 次/局复核通过）。构成：

| 动作 | 次/局 | 未改 µs/次 | ms/局 | 占 step 总时 |
| --- | ---: | ---: | ---: | ---: |
| 打牌·手切 | 29.00 | 51.1 | 1.482 | 63.8% |
| 打牌·摸切 | 17.81 | 36.8 | 0.656 | 28.2% |
| 「过」·收齐那一家 | 9.27 | 17.3 | 0.161 | 6.9% |
| 「过」·中途各家 | 0.56 | 0.4 | ~0 | 0.0% |
| 立直宣言 | 0.76 | 8.7 | 0.007 | 0.3% |
| 碰 / 吃 / 大明杠 | 1.95 | 3.6–11.5 | 0.007 | 0.3% |
| 和了（自摸 + 荣和） | 0.86 | 9–12 | 0.008 | 0.4% |
| 暗杠 / 加杠 / 九种九牌 | 0.12 | 6–17 | 0.002 | 0.1% |

**打牌一种动作占 92% 的 step 时间**（票面猜的「打牌大概率是大头」成立，且比猜的更极端）。
手切比摸切贵 14µs：手切的下一手往往还带响应阶段的构造差异，且两者都全额付下述三笔账。
「过」只有**收齐的那一家**贵——裁决与下一手摸牌后阶段的构造都记在它头上；中途的「过」
只是列表里删一项（0.4µs）。鸣牌便宜是因为鸣完那家门清已破、又没摸牌：
下一手动作集里最贵的几笔（自摸和检查、立直检查）都走了便宜分支。

## 3. 37µs 的账：段级拆解

插桩趟 step 合计 2.319 ms/局（38.5µs/次）；未插桩锚点 ≈2.10 ms/局（≈35µs/次，
与票 62 在忙机器上的 37µs 一致）。占比按插桩趟：

| 段（嵌套关系用缩进表示） | 次/局 | µs/次 | ms/局 | 占 step |
| --- | ---: | ---: | ---: | ---: |
| **`refreshFuriten`（打牌后振听簿记 → `waits` 34 次试摸）** | 46.8 | 27.4 | 1.281 | **55.2%** |
| **`awaitDahaiIn`（下一手合法动作集的枚举）** | 48.0 | 14.8 | 0.712 | **30.7%** |
| ├ `canRiichi`（`tenpaiDahai` 逐张试打） | 44.4 | 9.05 | 0.401 | 17.3% |
| ├ 自摸和检查（`horaWith` 于每张摸进的牌） | 48.0 | 3.21 | 0.154 | 6.6% |
| ├ 暗杠候选 | 48.0 | 1.17 | 0.056 | 2.4% |
| └ 其余（手切列表、加杠、九种、上下文） | | | ≈0.10 | ≈4.3% |
| **`responsesTo`(谁能响应这张牌) ** | 46.9 | 5.28 | 0.248 | **10.7%** |
| ├ `canRon` × 3 家（`isAgariWith` 型预判 1.0µs×140.4/局） | 140.8 | 1.11 | 0.156 | 6.7% |
| │ └ 全量 `Score.best` 只在型成立后跑 | 0.55 | 8.96 | 0.005 | 0.2% |
| └ 鸣牌候选枚举 | 140.8 | 0.26 | 0.037 | 1.6% |
| 校验（`rejectDahai` + `List.contains`） | 58 | ~0.1 | 0.007 | 0.3% |
| 事件追加进 `Log`、`acceptRiichi`、途中流局检查、`firstTurnFor`、宝牌指示牌读取等 | | | ≈0.08 | ≈3.4% |
| 和了 / 荒牌收尾（`applyHora`、听牌料） | 0.98 | | 0.006 | 0.3% |

三个此前没人写下过的事实：

1. **振听簿记是单一最大项**。每次打牌重算永久振听要 `AgariShape.waits`——34 种牌逐种试摸问
   `classify`——而实测**只有 16.4% 的打牌后手牌真在听牌**（6,836/41,799），其余 83.6% 的
   34 连问全部返回空。`classifyIn` 因此一局被调 1,874 次，其中约 1,595 次来自这里。
2. **立直合法性是第二大项**。每一手（44.4 次/局）都跑 `canDeclare`，门清、点数、牌山三条
   便宜判据先过，然后 `tenpaiDahai` 对每种手牌逐张试打算向听（~10 次 `Shanten.calculateIn`）
   ——而一局只有 0.76 次真的立直。
3. **`canRon` 的型预判已经很好**：140 次/局的 1µs 预判把全量判役压到 0.55 次/局。
   票 29a 那次优化的形状是对的，本轮无账可算。

## 4. 重放路径与对局路径：是同一份钱，多付的是哪份

`step` 没有重放专用分支——`Phase` 携带合法动作集，每次迁移都当场算齐
（`janpo.slnx` 侧 `Janpo.Engine.fsproj` 里写着设计决定：「回放不是另一套代码路径，就是
`GameState.step`」）。逐段问「谁消费它」：

| 段 | 对局路径消费者 | 重放路径消费者 | 重放多付了吗 |
| --- | --- | --- | --- |
| `refreshFuriten` | 后续 `canRon` 的振听判据 | 同左 | **否**（语义承重）——但两条路径都在为不听牌的手白付 |
| `awaitDahaiIn` 的动作集 | UI 按钮 / LLM schema / soak | **只有 `List.contains` 校验** | **是**（≈30%） |
| `responsesTo` | 决定问谁 + 见逃簿记（`couldRon`→同巡振听） | 同左 | **否**（语义承重） |
| 校验本身 | 同一份 | 同一份 | 否（合计 0.3%，票面问的「校验走没走全量判定」——校验本身便宜，贵的是**构造那份被校验的清单**） |

所以「重放别付那份钱」理论上有 ≈30% 可拿（把 `Actions` 变懒或开受信入口），但：

- 它顶着上引的设计决定（回放就是 `step`，快照/旁路不存在——ADR-0002 一脉）；
- 惰性求值要过 Fable（`lazy` 在两个编译目标上语义与开销都要重新验证）；
- **最大的两笔（55% + 17%）它根本拿不到**——那两笔在对局路径上同样是白花的，
  修在 `AgariShape.waits` 与 `RiichiState.canDeclare` 里则两条路径同时受益。

**判定：不开重放专用道（被否决，见 §8），改引擎本体。**

## 5. 实验 E2：`waits` 的向听前置闸（预验证通过）

**改法**（/tmp 副本，两行）：`AgariShape.waits` 在建好 `ShantenScratch` 之后、34 次试摸之前，
先 `Shanten.calculateWith` 问一次向听，非 0 直接返回空表。

**根据**（P1，非循环论证——右侧走 `classify` 暴力逐种拼手，不经过被测的 `waits`）：
13−3n 张手上 `向听 = 0 ⟺ ∃ 牌种补上成和了型`。20 万随机手采样（三种偏置：全池 / 限花色 /
强插四张同种以打死听边界，naki 0–3），**反例 0**（其中听牌 2,760 手）。`Shanten.standardIn`
里的 `deadQuadKinds` 修正正是这条等价式在「听自己抓完了的牌」上仍成立的原因。

**验证**：全套 721 条引擎测试绿；87 场固件对拍差异 0；**2026 整包 129,179 局重扫，
差异输出与改前逐字节相同**（改前改后都是 6 处、全是票 57 归的 D 类上游缺口），
覆盖计数断点行也逐字节相同。`refreshFuriten` 27.4µs → 2.07µs，听牌手计数逐次相同（6,836）。

## 6. 实验 E3：`canDeclare` 用一次向听换掉逐张试打（预验证通过）

**改法**：`RiichiState.canDeclare` 第四条判据从 `tenpaiDahai ≠ []` 换成
「手牌成 3n+2 形 且 整手向听 ≤ 0」。`tenpaiDahai` 本身保留——立直**宣言后**选宣言牌
（`Declared` 分支）仍要它给出「打哪几张保持听牌」，那是 0.76 次/局的事。

**根据**（P2′）：3n+2 手上 `tenpaiDahai ≠ [] ⟺ 向听 ≤ 0`。第一版命题（`= 0`）被采样
**当场否掉**——5 个反例全是向听 −1（已成和了形的手，打一张必然回到听牌；规则上这种手
可以放弃自摸宣立直，引擎现状也允许）；修正成 `≤ 0` 后 20 万手（naki 0–3，向听 ≤0 的 22,652 手）
**反例 0**。这一来一回正是「可证伪实验」的价值：命题错在哪当场暴露。

**验证**：与 E2 叠加后同一套三道闸全过（721 测试、固件差异 0、129k 局重扫逐字节相同）。

**合计效果（干净构建，无插桩，安静机器）**：

| 指标 | 改前 | E2+E3 | 倍数 |
| --- | ---: | ---: | ---: |
| 引擎重放（固件 893 局，`paifu-cost`） | 2.259 ms/局 | 1.099 ms/局 | **2.06×** |
| 2026 整包流式扫描（2 进程） | 3.3 分/分片 | 1.6 分/分片 | **2.06×** |
| `Shanten.calculateIn` 次数 | 402/局 | 90/局 | 4.5× 少 |
| `AgariShape.classifyIn` 次数 | 1,874/局 | 543/局 | 3.5× 少 |

改后 step 内部剩下的大头：自摸和检查 19%、`canRon` 预判 19%、residual `refreshFuriten` 13%
——都已是语义承重或已有预判护着的段，没有下一个同量级的免费午餐。

## 7. 票 55 的暂存缓冲手法适不适用：不适用（churn 不是 .NET 侧的杠杆）

34 长数组新建 882 个/局（14.6 个/step，约 160B 一个 ≈ 140KB/局），E2+E3 后 778 个/局。
分配速率折合 ~60MB/s——.NET gen0 的零头。**批内共用早已就位**（`waits` 与 `tenpaiDahai`
进批前建一个 `ShantenScratch`，正是票 55 的形状）；把缓冲再上提到 step 级或 `GameState` 级
属于 D 级架构决策（第 3 轮判过、第 5 轮核过，仍然成立：不动）。票 55 的 45× 数组开销
是 V8 的事实，.NET 侧不成立；重放是 dotnet 离线作业（票面边界），浏览器侧本轮不问。

## 8. 被否决项

| 提案 | 否决理由 |
| --- | --- |
| 重放专用 `step` / 受信校验入口 | 顶撞「回放就是 `step`」的设计决定；只拿得到 ≈30% 且两笔大头拿不到；基线已够用（§0） |

| step 级 / 状态级缓冲常驻（D 级） | 第 3 轮的判断未被推翻：架构决策，收益如 §7 所示已不显著 |

## 9. 顺带：`pendingKanDora ≤ 1` 那条 nitpick（59 号转来）

`KanProperties.杠数与新宝牌` 里的 `pendingKanDora state <= 1` 合取**确实是恒真式**——
它比对的 `pendingKanDora` 是测试自家从事件流 fold 出来的，而那个 fold 结构上只吐得出 0 或 1。
本轮做了 live-fire：把 `completeKan` 的「杠成立时先还欠账」故意去掉（欠账可攒到 2），
**KanProperties 9 条全绿**（生成器跑不到「连杠夹欠账」的局面，判据 3 的「执行 0 次」形态）；
同一处破坏被 `KanTests.连着两次明杠…`（票 59 的固件用例）与 `PaifuDifferentialTests`
（真牌谱对拍）当场抓红。**结论：不值得在 KanProperties 上单独加强——执行体已存在于另两道
闸门且验证过会开口**；要记账的话，按判据 4 把「属性生成器到不了连杠」写成显式事实即可。
