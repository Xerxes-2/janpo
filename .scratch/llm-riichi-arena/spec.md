# SPEC: LLM 日麻对战平台（第一版）

状态：ready-for-agent
语言决策：F# 核心（Fable → JS），TypeScript Agent 层与 UI
日期：2026-08-15

---

## Problem Statement

作为一个对函数式编程和 LLM 能力都感兴趣的开发者兼雀士，我想要一个能让多个 LLM（以及 Mortal 这类强 AI 基线）同桌打日本麻将、且每一步决策都附带可读推理过程的 Web 平台，但目前这个东西不存在：日麻 AI 生态全是不可解释的 RL 模型（Mortal/Suphx/kanachan），LLM 游戏竞技场（TextArena/Poker Arena 等）又都绕开了日麻；现有工具（Mortal 本地部署）安装门槛极高，无法分享给普通人围观。同时我希望这个项目本身的编写过程是愉悦的（静态强类型 FP），并且架构上为未来的联机、天梯、RL 保留后路。

## Solution

一个纯 Web 应用：日麻规则引擎用 F# 编写、经 Fable 编译为 JS 在浏览器内运行；对局以 mjai 风格的事件日志驱动；用户自带各家 LLM API key（key 仅存浏览器本地，请求由浏览器直发 provider），配置四个座位的选手（LLM / 随机 bot / Mortal 基线 / 本地真人）后开局观战或亲自下场；每一手 LLM 的推理以"思考气泡"展示，对局可回放、可通过 URL/JSON 分享；引擎向 Agent 层提供向听数、有效牌、危险度等信息脚手架，脚手架强度作为可玩配置项（裸奔 / 信息辅助 / 工具搜索三档）。Mortal 通过一个可选的轻后端容器以 mjai over WebSocket 接入。

## User Stories

### 观战与对局

1. 作为访客，我想打开一个 URL 就看到一桌 LLM 麻将在走（首页自动播放内置 Demo Paifu，分享链接则回放该牌谱），所以我既不需要安装任何东西、也不需要 API key。（live 观战不在本期，见 ADR-0003）
2. 作为围观者，我想看到标准的四人日麻牌桌（各家手牌数、河、副露、宝牌指示牌、点数、场风/自风、本场与供托），所以我能像看雀魂直播一样理解局面。
3. 作为围观者，我想点击任意一名玩家查看其当前完整手牌（上帝视角开关），所以我能评价它的选择。
4. 作为围观者，我想在每次 LLM 打牌时看到它的推理理由（思考气泡），所以我能理解并嘲笑/佩服它的决策。
5. 作为围观者，我想点击历史上的任意一手打牌展开当时的完整思考记录与局面快照，所以复盘不依赖记忆。
6. 作为围观者，我想看到对局以正确的日麻规则推进（含立直、副露、杠、流局、连庄、点数授受），所以结果可信。
7. 作为围观者，我想选择跳过/加速演出动画，所以我可以按自己的节奏看完一个半庄。

### 配桌与选手

8. 作为主持人，我想为四个座位分别选择选手类型（LLM、随机 bot、追加的规则 bot、Mortal、本地真人），所以我能组织任意对照实验或亲自下场。
9. 作为主持人，我想为 LLM 座位选择 provider（Anthropic / OpenAI / 兼容 OpenAI 协议的自定义端点，含本地 Ollama/LM Studio）与具体模型，所以我能测试任何模型。
10. 作为主持人，我想填入自己的 API key 且它只保存在我的浏览器本地、绝不上传到平台服务器，所以我能放心使用且平台零推理成本。
11. 作为主持人，我想为每个 LLM 座位选择脚手架档位（裸奔 / 信息辅助 / 工具搜索），所以我能观察同一模型在不同信息质量下的段位差。
12. 作为主持人，我想为 LLM 座位配置是否启用扩展思考（extended thinking / reasoning budget），所以推理预算成为对照变量。
13. 作为主持人，我想选择对局长度（东风战 / 半庄战）与基本规则开关（红宝牌有无、食断有无），所以规则可配置但不失控。
14. 作为主持人，我想在某个 LLM 持续超时或报错时看到明确的状态提示与自动兜底行为，所以一场对局总能打完。

### 回放与分享

15. 作为用户，我想在对局结束后获得完整牌谱（mjai 事件流 + 每步思考记录）的 JSON 导出，所以数据归我所有。
16. 作为用户，我想通过一个 URL 分享某场对局的回放（含思考记录），所以"名局"可以在社交媒体传播。
17. 作为用户，我想在回放中沿时间轴自由拖动、逐事件步进，所以复盘粒度到每一手。
18. 作为用户，我想导入他人分享的牌谱 JSON 进行回放，所以分享是双向的。

### 引擎正确性（开发者故事）

19. 作为开发者，我想让四个随机 bot 在命令行/无头模式跑完完整东风战（East-only 对局）且点数正确（Milestone 0），所以引擎正确性先于一切 UI 得到验证。
20. 作为开发者，我想用属性测试验证引擎不变量（如全局 136 张牌守恒、任意时刻合法动作集非空或局终、打掉再摸回同张牌向听数不变），所以边界情况被系统性覆盖。
21. 作为开发者，我想用真实牌谱（天凤/雀魂格式转换后）对拍点数与和牌判定，所以符点计算的长尾特例被真实数据检验。
22. 作为开发者，我想让同一份 F# 引擎源码同时被 dotnet 编译（跑 FsCheck 与对拍）和被 Fable 编译（部署到浏览器），所以测试基础设施留在最成熟的一侧。

### Agent 层

23. 作为主持人，我想让 LLM 的动作选择通过单轮 tool call 完成（合法动作列表作为工具参数 schema 注入），所以非法输出被结构性抑制。
24. 作为主持人，我想在 LLM 输出非法/解析失败/超时后看到有限次重试与最终兜底（默认摸切；信息辅助档下为不退向听的安全打），所以对局永不卡死。
25. 作为主持人，我想让信息辅助档的 prompt 附带引擎算出的向听数、有效牌种类与枚数、逐张试打的进退向标注、基于现物/筋/壁的对手危险度排序，所以 LLM 的短板（数值计算）被引擎补上。
26. 作为主持人，我想让工具搜索档的 LLM 可以调用"模拟打出某张后的局面"工具做多步查询，所以 neuro-symbolic 形态可被实验。
27. 作为研究者，我想让每步决策的完整输入（prompt/工具定义）、输出（含 thinking）、延迟与重试次数都落盘到牌谱中，所以事后可做任何分析。

### 本地真人坐席

28. 作为雀士，我想亲自坐上一个座位与 LLM/Mortal 同桌对局，所以我能直接检验"它打得比我强吗"。
29. 作为真人玩家，我只想看到我这个座位的合法观测（自己的手牌、公开信息），且界面在结构上无法泄露他家手牌，所以对局是公平的。
30. 作为真人玩家，我想通过点击手牌打出、通过按钮响应鸣牌/立直/和了，且这些按钮只在动作合法时出现，所以我不可能犯规。
31. 作为真人玩家，我想在有真人参与的对局中让 AI 的思考气泡在终局前隐藏、复盘时解锁，所以 AI 的推理不会向我泄露它的手牌。
32. 作为真人玩家，我想选配思考时限（默认不限时），所以我可以按自己的节奏打，也可以模拟竞技压力。
33. 作为新手真人玩家，我想选配与 LLM 同款的信息辅助（向听/有效牌/危险度提示），所以脚手架机制同时是我的新手辅助轮。
34. 作为真人玩家，我想在终局后得到针对我每一手的复盘（含 Mortal 对照标注，Mortal 可用时），所以这个平台也是我的练习工具。

### Mortal 基线

35. 作为主持人，我想让 Mortal 坐上任意座位作为强度参照系，所以 LLM 的雀力有锚点。
36. 作为围观者，我想在复盘面板中看到"此手 Mortal 会怎么打"的对照标注（Mortal 在场时），所以分歧点成为复盘素材。
37. 作为主持人，我想在 Mortal 后端不可用时仍能正常开没有 Mortal 的桌，所以后端是可选依赖而非单点。

## Implementation Decisions

### 接缝（Seam）决策 —— 最重要的一条

全项目唯一的核心接缝是 **mjai 风格的 JSON 事件协议**：引擎对外只暴露"事件流 + 当前合法动作集"，所有选手（LLM 适配器、随机 bot、Mortal 客户端、回放器、UI）都只面对这一个接口。测试也架在这条接缝上：驱动引擎的是事件序列，断言的是事件序列与终局状态。此决策同时保障：选手类型可插拔、Mortal 免翻译接入、回放 = 重放事件前缀、未来 Rust 重写引擎时上层零改动。

### 引擎（F# / Fable）

- 引擎是零依赖纯函数库，核心签名形如 `step : GameState -> Action -> Result<GameState * Event list, IllegalAction>`；不可变状态，事件溯源。
- 仅使用 Fable 兼容的 F# 子集与核心库；JSON 序列化用 Thoth.Json（双目标兼容），不用 System.Text.Json。
- 双目标：dotnet 侧跑 FsCheck 属性测试与牌谱对拍脚本；Fable 侧产出浏览器模块。CI 两侧都编译。
- 状态机对"阶段"使用类型区分（非法状态不可表示）：摸牌后阶段与他家打牌后响应阶段是不同类型，各自携带各自的合法动作集。
- 必须正确处理的规则清单（作为验收范围）：同巡多家荣和优先级（采用头跳还是双/三响作为规则开关，默认头跳）、大明杠责任支付、四类特殊流局（四风连打、四杠散了、九种九牌、四家立直）、振听（永久/同巡分别维护）、一发与岭上/海底/河底/抢杠的上下文标志、连庄与本场/供托、切上满贯开关。
- 向听数与有效牌计算内置于引擎（立直合法性与振听判定依赖它，Agent 脚手架与复盘标注复用它）；算法采用标准分解搜索，允许实现为"丑但快"的独立模块并以纯接口包裹；正确性以现成实现为 oracle 对拍。
- 危险度估计作为引擎的分析附件模块（现物/筋/壁/宝牌周边的规则化安全度排序），供脚手架与复盘使用，不参与规则判定。
- 观测投影为引擎一等能力：提供"全局状态 → 某座位合法观测"的纯函数，LLM prompt 构建与真人 UI 渲染共用同一投影，隐藏信息的保护在结构上而非纪律上成立；旁观者的上帝视角是独立投影，且在有真人参与的对局中默认禁用。

### Agent 层（TypeScript）

- prompt 与思考气泡第一版用中文；语言是渲染层参数（ADR-0001），第一版不向 UI 暴露开关。
- 多 provider 抽象优先采用 pi-ai（@mariozechner/pi-ai）；前置验证其浏览器可用性，不可用则按其接口设计自写浏览器薄封装（各家官方 SDK 均支持浏览器直连）。
- 动作决策 = 单轮 tool call：向模型注册 choose_action 工具，参数 schema 由当前合法动作集动态生成（enum 约束）；解析失败重试上限 2 次，之后执行兜底策略。
- 脚手架三档为座位级配置，类型名 `ScaffoldTier`：Bare 裸奔（仅原始局面文本）、Assisted 信息辅助（附 Shanten/Ukeire/进退向标注/Danger 排序）、ToolSearch 工具搜索（追加局面模拟查询工具）。真人坐席复用同一类型。
- 每步决策记录完整审计信息（输入、输出、thinking、延迟、重试），并入牌谱 JSON；会话落盘格式参考 pi 的 session 设计。
- API key 仅存浏览器（localStorage/IndexedDB），请求浏览器直发；自定义端点配置项支持本地模型（需在文档中说明 CORS/mixed-content 的已知限制）。

### Mortal 接入（可选后端）

- 轻量容器承载 Mortal，经 WebSocket 讲 mjai 与前端牌桌通信；前端将其视为与 LLM 适配器同级的一种选手实现。
- 平台在无后端时全功能可用（除 Mortal 座位）；Mortal 的 WASM 化明确不做（见 Out of Scope）。

### UI（React 底座，具体形态 M1 定夺）

- React 为底座，两个候选形态：A）原生 TS + React，与 Agent 层同语言、生态摩擦最小；B）Feliz + useElmish（F# 的 React 封装）写牌桌核心组件，MVU 的 update 循环与引擎的事件溯源同构，回放时间轴近乎免费，配置表单等杂活仍用普通 hooks 风格。倾向 B，M1 实测后定夺；两者底层同为 React，先 A 后迁 B 的成本可控。
- 牌桌为确定性渲染：UI 状态 = fold(事件前缀)，无独立游戏状态。
- 渲染用 DOM，不用 Canvas；雀魂级演出动画若未来要做，仅替换牌桌单个组件为 Canvas，外壳不变。
- 思考气泡与复盘面板为一等公民；第一版无动画（纯状态跳变），动画预算后置。
- 回放分享：唯一可分享物是 Paifu（事件流 + 可选 DecisionRecord）；URL 走压缩后的事件流（不含 thinking），JSON 文件走全量导入导出，两者共用同一解码器与同一回放路径，不存在局面快照格式（见 ADR-0002）。
- 真人坐席是选手抽象的一种实现：其"决策函数"渲染动作输入 UI 并等待交互，引擎与编排层不区分真人与 AI；动作按钮由引擎给出的合法动作集驱动渲染（合法性驱动 UI，而非 UI 自行判断）。
- 有真人参与的对局：AI 思考气泡终局前隐藏、复盘解锁；思考时限为座位级配置，默认不限时。

### 里程碑切分

- M0：无头引擎，四随机 bot 打完东风战，点数正确，属性测试与对拍通过。此里程碑不含 Fable、不含 LLM、不含 UI。
- M1：Fable 编译进浏览器 + 最小 React 牌桌（本里程碑内定夺 UI 形态 A/B，见 UI 决策）+ 单 LLM 座位（信息辅助档）+ 兜底闭环，能完整看完一个 Kyoku（验收下限；不设上限，引擎在 M0 已能跑完整场）。
- M2：四 LLM 同桌 + 思考气泡 + 回放导出/导入/URL 分享 + 首页 Demo Paifu 自动播放。
- M3：本地真人坐席（观测投影、动作输入 UI、可见性规则）+ Mortal 容器接入 + 复盘对照标注 + 脚手架三档完整化。

## Testing Decisions

- 好的测试只断言外部行为：给定事件/动作序列，断言产出事件、合法动作集与终局点数；不测内部分解结构或私有函数。
- 引擎（dotnet 侧）：FsCheck 属性测试为主力。核心不变量：牌数守恒；`step` 对非法动作总返回错误而非异常；回放确定性（同一事件序列 fold 出同一状态）；向听数在"打 X 摸 X"下不变、任何单步摸打变化幅度 ≤1。
- 对拍测试：以现成向听实现为 oracle 随机对拍向听数；以真实牌谱批量对拍和牌判定、役种集合与最终点数（符点为重灾区，样本量优先）。
- Fable 侧冒烟测试：同一批黄金用例（输入事件序列 → 期望输出）在 JS 侧跑一遍，防双目标语义漂移（重点：数值与集合语义）。
- Agent 层：以录制/回放的 LLM 响应做确定性测试，覆盖合法输出、非法牌、格式跑偏、超时四类路径的兜底行为；不在 CI 中调真实 API。
- 先例：本项目为绿地，无内部先例；属性测试风格以 FsCheck 官方模式为准，对拍脚本风格以 Mortal 生态的牌谱工具为参考。

## Out of Scope

- Rust 重写引擎（保留为 F# 版验证规则后的可选二期，接缝已保障其零上层成本）。
- RL 训练、自对弈数据管线、Mahjax/Mjx 集成。
- Mortal 的 WASM 化/浏览器内推理。
- 天梯/排行榜及其防伪后端（TrueSkill/Elo 留待平台跑起来之后）。
- 联机多真人对战、房间系统、服务器权威状态与断线重连（BEAM/Elixir 路线明确不在本期；本地单真人坐席在 scope 内，见 M3）。
- 三麻、古役、地方规则；规则开关仅限本 SPEC 列出的项。
- 精细动画演出（雀魂级）；第一版接受纯状态跳变。
- 移动端适配优化（不刻意破坏，但不作为验收项）。

## Further Notes

- 语言决策背景：作者同时掌握 Rust/F#/TS，本期选 F# 以最大化"写规则的愉悦感"并把 F# 版当作可执行规格说明；若项目存活且需要上规模，按接缝决策以 Rust 重写核心，届时规则歧义已被 F# 版全部踩平。
- 对 LLM 雀力的现实预期已在设计中内化：平台可玩性不押注 LLM 的绝对棋力，而押注"可解释推理 + Mortal 强度锚点 + 脚手架对照实验"的组合；裸 LLM 的低段位表现本身是内容。
- pi-ai 浏览器可用性验证是 M1 前唯一的技术前置作业；其结论只影响 Agent 层是否需要薄后端，不影响其它任何决策。
- 危险度模块第一版为规则化启发式（现物/筋/壁），不做统计模型；其输出文案将直接进入 prompt，措辞需与牌桌术语表一致。
- 本地真人坐席所需的全部机制（观测投影、输入 UI、可见性规则、计时器）恰好是未来联机版的前置积木，本期投入在联机路线上不会浪费。
- 术语表见根目录 `CONTEXT.md`（唯一权威）；牌记法与标识符语言的决策见 `docs/adr/0001-mjai-notation-and-romaji-identifiers.md`。要点：牌用 mjai 记法 `1m-9m/1p-9p/1s-9s/1z-7z`，人类可读形式仅存在于渲染层；"局"指单局（东1局），整场叫"对局"，长度叫"东风战"（East-only）/"半庄战"（East+South），"东风局"一词因歧义已废弃。
