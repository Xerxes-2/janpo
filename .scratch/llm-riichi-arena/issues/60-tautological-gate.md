# 60 — 一条永远红不了的闸门：增量维护与一次性 fold 的一致性

**What to build:** 票 58 在量成本时顺手发现：`MaskedStreamProperties` 里那条
「逐条推进与一次性 fold 给出同一份观测」**是恒真式**——两边展开后都是 `List.fold advance`，
**它永远红不了**。而票 29a 当年真正守这件事的 `MigrationGate.fs` **已经退役（文件不在了）**。

也就是说：**「座席的历史与观测同出一源」这条 M1 的核心不变量，现在的守卫只有 Web 侧
`TableTests` 里的一颗种子。** 这正是判据 1（闸门的证据是它失败过）与判据 3
（它在真语料上执行过几次）说的那种情形，而且是在**最不该失守的地方**。

**Blocked by:** None

**Status:** ready-for-agent

## 要做的

- [ ] **先证实它真是恒真式**：把 `absorb` / `advance` / `advanceAll` 逐个临时弄坏，
      看那条属性**是否仍然绿**（58 号已判断如此，你要拿红/绿的原始输出证明）
- [ ] 把它改成**真的能红**：断言的两边必须是**两条独立的实现路径**——
      一边是增量维护（牌桌那条：`start` → 逐步 `advance`），
      另一边是从头一次性算（`Observation.ofState` / `ofEvents`）。
      **两边不许在实现上归并到同一个 fold**，否则又是恒真式
- [ ] **逐个反向自证**：弄坏增量那侧要红、弄坏一次性那侧也要红、
      只弄坏掩蔽（`MaskedEvent.forSeat`）也要红。三份红输出抄进报告
- [ ] 覆盖面：随机对局 × 随机座位 × **每一手**（29a 的原始要求就是这个），
      并给出**每条断言在一次 CI 里执行了多少次**（判据 3；为 0 或极少要说明）
- [ ] 顺带看 `ObservationProperties` 那两条（58 号说它们是真的、弄坏 `absorb` 会红）——
      **确认一下**，并在报告里写清「现在到底有哪几条在守这件事」

## 边界

- [ ] **不改 `src/Janpo.Engine/` 的语义**。若为了让两侧成为独立路径必须动 `src/`
      （例如某个入口只有 internal 版本），**先在 `DECISIONS.md` 说清再动，且不许改行为**
- [ ] 不碰 `tests/fixtures/paifu/` 与 `PaifuDifferential.fs`（票 59 正在那边修两个真 bug）
- [ ] 不做性能改动——票 58 的实现建议（`forSeatWith`）**已判为不做**，理由见 `DECISIONS.md`
- [ ] CI 墙钟涨幅 ≤15%（基线 41.9s）；属性用例数**只许增不许减**

## 为什么这一票值得单开

29a 当年是**故意**让那条迁移闸门退役的（它说「守完这一次就退役」）。**那个判断当时是对的**——
它守的是一次迁移。错的是**没有人接手守「长期不变量」那一半**，于是留下一条看起来在守、
实际恒真的属性。

**这是本项目「记录声称了一件事、执行体不存在」的第六例**，而且它是**唯一一次「执行体存在但空转」**
——比前五例更难发现，因为测试列表里它是绿的。
