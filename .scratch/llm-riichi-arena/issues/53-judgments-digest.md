# 53 — 把散在 DECISIONS 里的判据沉淀成一份 agent 读得到的清单

**What to build:** M1 与 M2 的跑批里攒下了一批**可复用的判据**——它们不是某一张票的决定，
而是「下次遇到同类情形该怎么判」的规则。现在它们散在 `DECISIONS.md` 三千行里（那份文件是**日志**，
按时间追加，没人会为了写一张票去通读），于是调度器只能每次手抄进派工单。
把它们收成**一份短清单**，让派工单指过去就行。

**Blocked by:** None

**Status:** ready-for-human

## 一、清单本身

放在 `docs/agents/` 下（与既有的 `fsharp-style.md` / `issue-tracker.md` / `triage-labels.md` 同侧）。

- [x] 通读 `.scratch/llm-riichi-arena/run/DECISIONS.md` 里所有标着**「教训」/「判据」/「规矩」/「新规矩」**
      的段落，以及 `M2-SCHEDULE.md` 末尾那份「M1 传下来的规矩」
- [x] 收成一份清单：**每条一个短标题 + 一句判据 + 一个真实案例的指路**（案例只给一句话与出处，
      别把整段抄过来）。已知至少这些，**但要自己通读补全**：
  - 闸门的证据是「它失败过」，不是「代码里有这一行」
  - 闸门还要问「它在真语料上执行过几次」——永远执行不到与从不失败，危害相同
  - 一个投影里出现第二个「只能从历史算」的字段，就是形态错了
  - 相对方位（上家/对家/下家）在多主体渲染里必须显式声明参照系
  - 写下一条不变量时，要问「谁来执行它」
  - 查当下事实（版本号、API 形状）问权威源，不用搜索转述
  - 给出「因为 X 所以慢」这类因果判断前，先量 X
  - 一条决策的前提被后续票拆掉时，回头重问那条决策
  - 并行跑批时看到红，先怀疑基础设施再怀疑代码
  - 票号由调度器分配；票文件先提交再派工
- [x] **写给 agent 看**：照 `/home/xerxes2/.pi/agent/skills/writing-for-agents/SKILL.md` 的要求——
      短、可执行、没有寒暄与励志话。**目标是「读完就能用」，不是「读完很感动」**
- [x] 从 `RUNBOOK.md` 与 `M2-SCHEDULE.md` 指向它（**只加指路的一行**，别把两份文件重写）
