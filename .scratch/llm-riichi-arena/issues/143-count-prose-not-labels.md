# 143 — 那道字数闸门该数散文，不该数控件名

**What to build:** 重定 `?table=1` 那一屏的字数上限——**只数说明性文字，不数控件名与牌桌上的数**——
并把票 138 为了挤进 168 而藏起来的那两个标签摆回页面上。

**Status:** ready-for-agent（主人 2026-08-30 裁：**可以重定**。
原话：「核心目的是人读起来怎么样，会不会信息过载」）

## 为什么重定（前提变了，不是把闸门放宽）

票 120 那 168 是**对着一屏散文**砍出来的（486 字 → 178 字，那一票的名字就叫「减法」）。
今天那一屏**一句散文都没有**：122 字全是控件名（座位 0…3 / 上帝视角 / 导出牌谱 /
复制分享链接 / 剩余摸牌 / 宝牌指示牌）与牌桌上的数（手牌 13 / 东1局 0 本场 / 69 张 / 25000 / 第 1 巡）。

∴ **这道闸门今天数的东西，与它想守的东西不是一回事**——同「量点要落在被关心的那件事上」那条判据。
它已经开始产生反效果：票 138 为了挤进 168，把一行式开桌前两格的控件名挪进了
`aria-label` + `placeholder`；而 provider 是个 `<select>`、模型那格有默认值，
**两格都不空 ⇒ placeholder 永远不显示**，头一回来的人看到「deepseek」「deepseek-v4-flash」
两个没有标签的框。**那一票的全部意义就是「头一回来的人一步就能开桌」，它恰恰对着新人失去了名目。**

## 主人给的判据（照它定，不要照一个更大的数定）

> 核心目的是**人读起来怎么样，会不会信息过载**。

∴ **别只是把 168 改成 190**。要的是**把量点挪到散文上**：
控件名与数字是「界面本身」，人扫一眼就跳过去了；真正会造成过载的是**成段的说明文字**。
