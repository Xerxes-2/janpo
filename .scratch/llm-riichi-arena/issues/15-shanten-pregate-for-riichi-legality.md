# 15 — 立直合法性的 Shanten 前置闸门

**What to build:** 让 `RiichiState.canDeclare` 里的 `tenpaiDahai` 只在**可能成功时**才跑。它现在枚举 14 张打法、每张算一次 `Shanten`，在结构化手牌上要 **2.1ms**；而中盘绝大多数手牌离听牌还远，这 14 次注定全部失败。若「14 张手牌 shanten = 0」⟺「存在一种打法使打完仍听牌」成立，则**一次 Shanten 就能挡掉 14 次**。

**Blocked by:** 14

**为什么阻塞于 14**：这是引擎热路径上的优化，且改的是立直合法性——有正确性风险。M0 应当先用现有引擎完成验收（14 票的 soak 与两类对拍），再动优化。反过来做的话，一旦 14 票发现立直行为异常，就分不清是 soak 暴露的老问题还是本票引入的新问题。

**Status:** ready-for-agent

## 先证伪，再优化

**核心等价性尚未证明**，只有调度器测的一个数据点支持它：

```
14 张 `1m1m1m 2m3m4m5m6m7m8m9m 9p9p 5z`  shanten = 0
13 张（去掉 5z）                          shanten = 0
```

**第一步必须是把这条等价性当假设去证伪**，而不是当前提去实现：

- [ ] 用 FsCheck 属性直接对打这条等价性：对任意合法的 14 张手牌（含各种副露数），
      `Shanten.calculate` 为 0 ⟺ `tenpaiDahai` 非空。**跑够量**（这条属性很便宜，可以开大 `MaxTest`）
- [ ] 若属性被证伪，**本票立即停止并写清反例**——闸门不成立，改为寻找别的（如「shanten ≤ 1 才枚举」这种保守闸门）
- [ ] 若成立，再实现闸门，并保留那条属性作为回归测试

## 实现约束

- [ ] 闸门必须**保持 `&&` 的短路**：现有顺序是「门清 → 点数 → 牌山剩余 → 枚举打法」，闸门插在枚举之前（见 `docs/agents/fsharp-style.md` 限制 B——那条限制正是在这段代码上发现的）
- [ ] 不许改 `canDeclare` 的对外语义：同样的输入必须给同样的答案。用 `dotnet fsi` 对改前改后跑同种子对局比事件频次（备注 N-13 的做法）
- [ ] 附带量一次收益：改前后各跑一次 `RiichiProperties` 的墙钟

## 附带的第二个候选（同一热路径，可一并做或另开）

- [ ] `GameState.horaOf` 在每个响应者身上算和了型。若也有便宜的前置闸门（例如手牌未听牌就不可能荣和），同样值得挡——但**同样要先证伪等价性**

## 背景数字（备注 N-19）

| 输入 | 单次 `Shanten.calculate` |
|---|---|
| 随机手牌 | 5.8 – 13.7 µs |
| 结构化的 14 张 | **150 µs** |
| 枚举 14 张打法 | **2100 µs** |

**注意随机手牌的数字不具代表性**——真实对局中手牌会变得结构化，成本高 25 倍。本票的收益要用结构化手牌的数字估。

**产品影响很小**：M1 在浏览器里每回合算一次合法动作集，2ms 相对 LLM 的 1–30 秒是噪声。本票的真实价值在**测试与 soak 的速度**，以及将来若要做大规模模拟（如危险度的蒙特卡洛）时的地基。别把它当紧急项。
