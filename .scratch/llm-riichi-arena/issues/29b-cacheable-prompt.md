# 29b — 前缀可缓存的 prompt：固定 preamble + append-only 历史 + 尾部现况

**What to build:** 让 prompt 变成「**固定 preamble + append-only 的观测历史 + 尾部的现况与动作**」。
现在的 prompt 是当前局面的快照，每手几乎每个字都变，前缀零复用；改完之后同一局内前一手的 prompt
是后一手的**字节前缀**，provider 的前缀缓存因此能吃到。

历史从哪来：29a 已经把座席的唯一投影做成掩蔽事件流，这一票**只管渲染与账单**。

**Blocked by:** 29a

**Status:** ready-for-agent

## 零、两种客观事实各就各位（主人 8/16 裁定）

客观事实有两种形态，**都给**，但位置不同：

| | 时间上的事件流 | 空间上的场况 |
|---|---|---|
| 真人怎么得到 | 亲眼看到每件事发生，记不记住是他的本事 | 物理上摆在桌面，免费呈现 |
| 在 prompt 里 | **前缀，append-only，可缓存** | **尾部，每手重算，每手付全价** |
| 关系 | 本体 | 它的 fold 结果，严格冗余 |
| 给它的理由 | 「什么没发生」（见逃し）只有流能表达 | 免掉上百条事件的心算记账 |

- [ ] 尾部给**完整场况**（照现在的样子：四家河全列、副露、点数、宝牌、巡目、剩余牌数），
      重复度高是**故意的** —— 记账负担不是我们想测的能力
- [ ] 巡目、剩余牌数、本场供托这类「从流里数得出来」的量**照给**。判据是「真人不用动脑子就拿得到」，
      不是「严格不可推导」
- [ ] **可见牌按牌种归并的统计不进 Bare 的尾部**（那是数出来的，按判据属于 Assisted）
- [ ] 两种形态必须**构造性一致** —— 尾部场况就是刚才那条流的 fold（29a 已保证一条掩蔽法则）。
      加一条测试：尾部渲染的场况 ≡ fold(前缀里那条流) 的渲染，**不许出现两个来源**

## 一、prompt 翻转

- [ ] 形态定死为三段：**固定 preamble**（规则与任务，逐字不变）→ **【到目前为止你看到的】**
      （append-only，永不重写既有行）→ **【现在】+【可选动作】+（脚手架）+（重试原因）**
- [ ] **属性测试（前缀稳定）**：同一局内，第 n 手的完整 prompt 是第 n+1 手 prompt 的**字节前缀**。
      这条自动守住「前缀里不许出现会被重算的量」（巡目、剩余张数、序号、任何聚合数）
- [ ] 载体是**单条不断增长的 user message**（裁决），不是多轮对话——不把模型自己的旧理由锚进上下文
- [ ] 脚手架（向听 / 有效牌 / 进退向 / 危险度）**全部在尾部**；两档的差异仍然只有那一节
- [ ] 事件流带来的东西在 prompt 里**真的可见**：立直宣言牌与宣言巡目、加杠宣言与抢杠窗口、
      以及**河与鸣的时序对齐**——哪张牌在第几巡被谁鸣走。这是「28 号那两项补丁被正当抽掉」的验收，
      缺一样这票就没做完
- [ ] 注意手切摸切**本来就有**（`Dahai` 事件的 `tsumogiri`，prompt 里缀 `*`，被鸣走的那张仍留在河里
      因为现物与振听要求它留着）。这一票要补的**不是这个标记，而是它的时间轴**：
      快照里河是一串牌、副露是另一串组，两条串接不上；细心的牌手记的是「第几巡手切了什么」，
      早巡手切中张与终盘手切中张是完全不同的两件事
- [ ] 录制固件重录；Bare 与 Assisted 两档都跟着改

## 一之二、历史怎么过 F#→TS 接缝（主人 8/16 裁定，解 29a-A）

**裁决：引擎只给结构化的掩蔽事件，中文短句由 TS 渲染。**
理由是一致性——`prompt.ts` 的尾部现况本来就在 TS 侧用 `KAZE`/`RIICHI`/`RELATIVE` 这些常量渲染河与副露；
若前缀由引擎渲染、尾部由 TS 渲染，**同一份 prompt 里会出现两套措辞风格**。而且这样才真兼容「prompt 降为数据」
（措辞可由模板定制，票 31）。

- [ ] 给 `MaskedEvent` 写 encoder（`Public` 那一半**复用 `Event.encoder`**，wire 形状与 mjai 一致，
      不新造第二种事件记法）；只需 encoder，不需 decoder
- [ ] 决策包多一段历史（掩蔽事件的数组）；`DecisionPackage` 的既有字段与语义不动
- [ ] TS 侧把每条事件渲染成一行中文短句，术语照 `CONTEXT.md`，牌用 mjai 记法
- [ ] **每条历史行只依赖那一条事件本身**（不依赖它之后发生的任何事），否则前缀稳定性守不住
- [ ] 黄金用例会因决策包多一段而变动：照 28 号票的逐字段流程重录，diff 里只多那几行

## 二、把缓存变成可观测的数字

- [ ] `DecisionRecord` 记 `cacheRead` / `cacheWrite`（pi-ai 的 `usage` 已有这两个字段，
      `openai-completions` 适配器已经在读 DeepSeek 的 `prompt_cache_hit_tokens`，不用自己拼）
- [ ] 报告给出真跑一局的：**缓存命中率**、账单对比（快照式 vs 事件流式）、单手延迟对比
- [ ] 报告给出**最坏情况**的账单：原始 token 数随手数线性增长（快照式每手近似恒定），
      命中失效时（换模型、改 preamble、改渲染措辞）比现在更贵。把这个数字摆出来
- [ ] 记一条运维含义：**改渲染 = 废缓存**，而 CI 不会因此变红（前缀属性测试只保证同一次运行内单调，
      不保证跨版本一致）。考虑把渲染版本号写进 DecisionRecord，让 M2 能解释命中率为什么掉

## 三之三、顺手清一笔挡路的债：无头脚本的写死端口

`web/scripts/verify-{tracer,golden,llm-seat,export}.mjs` 各写死一个端口（4179–4182）且 `strictPort: true`。
**两个工作区同时跑 `ci.sh` 会撞端口**，失败信息还长得像用例挂了——调度器 8/16 集成票 30 时被这个坑
误导过一次（第一遍红、第二遍绿，实际是 29a 的 agent 在另一个工作区同时跑 CI）。跑批是并行的，
这个假红迟早会掩盖一次真失败。

- [ ] 端口改为**临时端口**（bind 0 后读回实际端口）或允许环境变量覆盖，`strictPort` 相应放开
- [ ] 撞端口时的报错要一眼看得出是端口问题，不要伪装成用例失败
