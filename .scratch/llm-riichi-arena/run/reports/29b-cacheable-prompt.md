# 29b — 前缀可缓存的 prompt：固定 preamble + append-only 历史 + 尾部现况

**Status:** done　**fixed point:** `35fad8f0`（change `ywuyxvqo`）　**工作区:** `janpo-ws-a`

## 一句话

prompt 从「当前局面的快照」翻成「**固定 preamble + append-only 的观测历史 + 尾部现况**」三段，
同一局里连续两手的 prompt 逐字节共享前 51%–74%，**DeepSeek 真跑一局的缓存命中率 48%（末尾几手 67%–70%）**。

```
① 固定 preamble          规则与读法，逐字不变        ┐
② 【到目前为止你看到的】   掩蔽事件流，一条事件一行      ├─ 前缀，append-only，provider 缓存吃这两段
                          既有的行永不改写            ┘
③ 【现在】+【可选动作】+（脚手架）+（重试原因）          ── 尾部，每手重算，每手付全价
```

## 交出去的接口（票 31 直接用）

| 想要什么 | 怎么取 |
|---|---|
| 三段各自一份 | `promptSections(decision, tier, note) : { preamble; history; present }`（`web/src/agent/prompt.ts`） |
| 整份 prompt | `renderPrompt(...)` = 三段用 `"\n\n"` 拼起来 |
| 可缓存的那一段 | `cacheablePrefix(decision, tier)` = ① + `"\n\n"` + ② |
| 固定 preamble 的正文 | `PREAMBLE`（导出的常量，31 号把它换成模板） |
| 历史逐行渲染 | `historyLines(decision, naming)`（`web/src/agent/history.ts`） |
| 措辞常量（风/相对座位/立直/副露/流局） | `web/src/agent/wording.ts`，**前缀与尾部共用一份** |
| 座席历史（引擎侧） | `DecisionPackage.history : MaskedEvent list`，wire 上是 `"history"`，排在 `"observation"` 之前 |
| 掩蔽事件的 wire | `MaskedEvent.encoder`（`Public` 那一半直接复用 `Event.encoder`） |
| 这一手的账单 | `DecisionRecord.Usage : Usage option`（`Input`/`Output`/`CacheRead`/`CacheWrite`） |
| 这一桌累计的账单 | `Table.usage : Table -> Usage`，页面上是 `table-usage` 那一行 |

**槽位要插在哪**：只能插进 `present`。动 `preamble` 或 `history` 的措辞 = 换一份前缀 = 那一局
之前攒下的缓存全废（见下面「运维含义」）。人格 / system 文本若要每局不变，放 `preamble` 是安全的
（它在前缀的最前面，改了只影响那一次实验的全部对局，不会在一局中途失效）。

## 一、历史怎么过接缝

**引擎只给结构化的掩蔽事件，中文短句由 TS 渲染**（主人第六次裁决）。

- `MaskedEvent.encoder`：`Public` 那十四条**逐字节就是 `Event.encoder` 的产物**（有一条具名用例拿
  一整局的流对过）；掩掉的两条仍是 mjai 的形状——他家摸的那张写 `"pai": "?"`（mjai 服务端发给各家的
  就是这个写法），`start_kyoku` 只带自家那一手，写作 `tehai` 而不是四家的 `tehais`（他家那三格
  **没有字段装得下**，`MaskedStartKyoku` 从 29a 起就是这样）。只有 encoder，没有 decoder。
- `DecisionPackage` 多一段 `History`，由 `Observation.stream seat state` 取——**与 `observation`
  同源**（`ofState` 内部就是「掩蔽 + fold」）。既有字段与语义一个字没动。
- TS 侧一条事件一行：`historyLines`。**每一行只由那一条事件本身决定**（外加一局之内恒定的视角称呼，
  与它**之前**那些事件数出来的巡目），绝不依赖它之后发生的任何事。

九项历史事实在 prompt 里长这样（前六项摘自下面那两份真 prompt；立直、杠与宝牌那三项
那一局没出，样子取自 `history.test.ts` 里逐项钉住的具名用例）：

| 事实 | prompt 里的样子 |
|---|---|
| 每条打牌的巡目 | `你 第3巡 打 2m*` |
| 跨家先后 | 行的先后顺序本身 |
| 手切摸切及其时序 | 摸切缀 `*`，且写在它自己那一巡上 |
| 河与鸣的时序对齐 | `上家 第4巡 碰 你打的 2z（亮出 2z 2z）` 紧接着 `上家 第4巡 打 7m` |
| 立直宣言牌与宣言巡 | `你 第6巡 宣言立直` 紧接着 `你 第6巡 打 4z` |
| 立直之后通过的牌 | 宣言之后每一条别家的 `打` |
| 见逃し | 打牌那一行之后**直接是摸牌**——读法写在固定 preamble 里，不造新事件、不加解释行 |
| 杠宝牌的揭示时机 | `翻开新的宝牌指示牌：8m` 排在流里的位置（暗杠当场翻，明杠等打牌） |
| 加杠宣言与抢杠窗口 | `上家 第7巡 加杠 1m（原来碰的 1m 1m 1m）`，窗口就是它后面那一条 |

措辞与尾部同一套：副露顺手也从 `pon 鸣3m[3m 3m]（来自座位 3）` 改成
`碰 3m（来自对家，亮出 3m 3m）`——种类照术语表写中文、来源写相对位置、牌照 mjai 记法。

## 二、前缀字节稳定性（这一票的题眼）

`web/tests/agent/prefix.test.ts`，跑在**同一局连续 12 手**的真决策包上
（`decision-sequence.json`，`janpo decide 7 --seat 1 --sequence --steps 12`）：

- 第 n 手的 `cacheablePrefix` 是第 n+1 手**整份 prompt** 的字节前缀（两档各一条）
- 前缀 append-only：第 n 手写下的行第 n+1 手不许改写，且只会长
- 整份 prompt 以它自己的前缀开头；重试那一句接在最尾，前面一个字节不变
- 两档共用同一段前缀（脚手架整个在尾部）
- 前缀里不许出现「此刻的量」（`牌山剩余` / `当前向听数` / `危险度排序` / `id=` / `刚摸进：`）
- 可缓存的占比随手数上升

**票面那句「第 n 手的完整 prompt 是第 n+1 手的字节前缀」按字面是做不到的**：尾部每手重算，
第 n 手的尾部不可能出现在第 n+1 手里。落成的是它能成立的最强形式——
**「第 n 手的可缓存前缀 ⊑ 第 n+1 手的整份 prompt」**，这正是 provider 缓存吃得到的那一段。
记在 DECISIONS 29b-3。

**这条测试真的抓得住回归**（做完之后专门验过）：把 `【到目前为止你看到的】` 的抬头改成
`【到目前为止你看到的】（第 N 巡为止）`，两档的前缀属性当场变红，而其余 78 条用例全绿。

## 三、尾部就是前缀那条流的 fold（不许出现两个来源）

两层守着：

- **引擎侧（构造性）**：`DecisionPackageProperties` 两条属性——任意局面下，包里的
  `history` 用 `Observation.ofMasked` fold 出来的就是包里那份 `observation`；且
  `history` 就是那条唯一的掩蔽流（`Observation.stream`）。
- **接缝之后（TS 侧）**：`prefix.test.ts` 拿前缀那条流数一遍，与尾部逐座位对照——
  四家的河（逐条 `{pai, tsumogiri}`）、巡目、副露组数、宝牌指示牌全部相等；
  再加一条**比渲染**的：尾部写出来的那行 `牌河：…`（含摸切的 `*`）与从流里数出来的逐字相同。

### 改前 vs 改后（同一种子、同一模型、同一档位）

「改前」= 把 `renderPrompt` 临时改成只拼 ① + ③（快照式，等价于 29b 之前的形态），
重跑一遍同样的验收脚本；那个改动**没有提交**，量完就撤了。

| | 改前（快照式） | 改后（事件流式） |
|---|---:|---:|
| 那一座位打了几手 | 18 | 21 |
| prompt 首手 / 末手（字） | 914 / 1,053 | 1,078 / **2,429** |
| prompt token 合计 | 19,265 | 38,637 |
| 其中命中缓存 | 8,960（46%） | **18,560（48%）** |
| 实付全价 token | 10,305 | 20,077 |
| 每手平均 prompt token | 1,070 | 1,839 |
| 每手平均付全价 | 572 | 956 |
| 延迟中位数 / 均值 | 1,780 / 1,787 ms | 1,814 / 1,823 ms |

**要诚实的三件事**：

1. **贵了，不是便宜了。** 事件流是**加在**完整场况之上的（两种形态都给是主人的裁决），
   因此每手付全价的 token 约 1.7×。缓存把「历史越来越长」这件事的边际成本吃掉了，
   但没有、也不可能把尾部那份场况吃掉。
2. **快照式本来就有 46% 命中**——固定 preamble 那一段它也在复用。所以「命中率」这个数
   单独看不说明问题，**要看的是它随手数怎么走**：改后从 21% 一路涨到 70%（末手 prompt 2,479 tok
   里 1,664 tok 是命中的），改前恒在 46% 上下（能命中的只有那个恒定的 preamble）。
3. **命中不是单调的**。第 25、39、43 手掉回 11%–21%（`cacheRead` 退回 256）。
   命中的 token 恒是 256 的整数倍，说明 DeepSeek 按块缓存、且写入是异步的；
   连着几秒里问的几手偶尔会赶在写入之前。这不是我们这侧的 bug，但它意味着
   **命中率是统计量，不能拿单手的数去下结论**。

### 最坏情况的账单

- **命中全废时**（换模型、改 preamble、改任何一行历史的措辞）：改后这一局要付
  **38,637** 全价 token 而不是 20,077，**多 92%**；而且**原始 token 随手数线性增长**
  （首手 1,183 → 末手 2,479，约 +6%/手），快照式则近似恒定（914 → 1,053 字）。
  一局二十手还好，M2 若要打整场（四局起）且不改 preamble，这条线会长到 4,000+ tok/手。
- **改渲染 = 废缓存，而 CI 不会因此变红**：前缀属性测试只保证**同一次运行内**单调，
  不保证跨版本一致。渲染版本号的事见「留给人的」第 2 条。

## 六、顺手清的债：无头脚本的写死端口

`web/scripts/verify-{tracer,golden,llm-seat,export}.mjs` 各写死一个端口（4179–4182）且
`strictPort: true`，两个工作区同时跑 `ci.sh` 必撞，报错还长得像用例挂了（调度器 8/16 被误导过一次）。

- 新增 `web/scripts/serve.mjs`：四个脚本共用 `startPreview` / `startDevServer` / `pageUrl`。
  **默认不指定端口**（vite 因此从默认端口起往后找空的，`strictPort: false`），
  真实端口从 `server.resolvedUrls` 读回来——脚本自己不再拼 URL。
- `JANPO_PORT=4179` 可以钉死一个端口（调试用），**那时才 `strictPort`**，撞了当场说
  「端口 X 被占用（多半是另一个工作区在同时跑 CI）……这不是用例失败」。
- 顺带修了一个**真的假红**：dev server 头一次加载时 vite 可能因依赖预打包让页面整体重载，
  playwright 报 “Execution context was destroyed”，长得像黄金用例挂了（跑批期间撞见过一次）。
  `retryOnReload` 重试一次并打一行说明。
