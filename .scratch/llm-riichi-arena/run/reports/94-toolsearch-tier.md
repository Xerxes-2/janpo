## 1. 这一档到底是什么：Bare + 一个工具，不是 Assisted + 一个工具

**这是这一票最要紧的一个判断，票面没写死，我按 `CONTEXT.md` 裁的**（硬约束 5：术语表是唯一权威）：

> **ToolSearch 加的是自己去问的能力，不是又一批算好的数值**，因此不落在这条判据的两端上。

「不是又一批算好的数值」这半句直接排除了「Assisted + 工具」：那一读法下尾部里**已经**摆着
一整张算好的表，工具是死的（模型没有任何理由去问一个它已经看得见的数），这一档就退化成
「Assisted 加一笔看不见的账」。因此落地是：

- **ToolSearch 的正文 = Bare 的正文**——一次都没问的时候，它的尾部与裸奔档**逐字节相同**（用例钉着）；
- 前缀里多一段工具说明，`tools` 里多一个 `what_if`；
- **它自己问出来的那几条**写进尾部，一条一行，与 Assisted 那张表里同一个 id 的那一行**逐字节相同**。

被否决的另一读法与理由记在 `DECISIONS.md` 的 94-1。**这条判断会影响票 89（真人的信息辅助）与
票 93**，因此也写进了简报。

### 1.1 preamble 里多出来的那一段（第③段之后、第④段之前）

```
【打之前你可以先问】
除了 choose_action，你还可以调用 what_if 工具：给它一条打牌动作的 action_id，
引擎会按这一手真实可见的牌算出「打完它之后」的向听数、有效牌与危险度，原样回给你。
它给的是事实，不是建议，也不替你选牌；不问也可以，直接出牌完全允许。
一手最多问 4 次，问满之后这个工具就不再给你，那时直接调 choose_action 出牌。
问过的每一次都会写在下面那一节里（同一个 action_id 问两遍也算两次）。
```

它在**可缓存前缀**里（一场只付一次全价），位置由 `preambleFor` 定：插在模板给的
`labels.history` 那一句之前——也就是第④段（三段结构说明）的第一句之前。
**锚点不在的模板**（有人整份换掉 `system`）走的是「接在 system 末尾」那一支：
宁可位置不如意，也不能让这一段消失——消失了模型就不知道自己能问，而工具真的在 `tools` 里。
两条路各有一条用例钉着。

### 1.2 尾部里那一节（只有问过才写）

```
【引擎算好的数】（下面这几个数是引擎算出来的事实，不是建议）
你查过 3 次，还可以再查 1 次：
- id=0（打 1m）：打完 3 向听，进退向 0，有效牌 27 枚 8 种：2m(4) 5m(4) 2p(4) 1s(3) …
- id=2（打 4m）：打完 3 向听，进退向 0，有效牌 23 枚 7 种：2m(4) 2p(4) 1s(3) …
- id=11（打 3z*）：打完 3 向听，进退向 0，有效牌 30 枚 9 种：1m(3) 2m(4) 4m(3) …
```

（真跑那一局里抄下来的一手；模型那一手的理由是「打刚摸的 3z 保持最大有效牌数（**30 枚 9 种**）」
——它读的就是自己查出来的那一行。）

**抬头用的是 Assisted 那一节的同一个槽位 `labels.scaffold`**：两档不会同时有这一节，
而那句「引擎算出来的事实，不是建议」两边一样成立。**模板的槽位因此没有变多**
（`CONTEXT.md` 的 `PromptTemplate` 写着八项抬头，一项没加），多出来的只是段内那几行
——那本来就归渲染器（术语表明写的切分）。**这一票没动 `CONTEXT.md` 一个字，也不需要授权。**

危险度那一行连**名次**一起给（`- 第11位 id=3（打 5p）：无依据 —— 宝牌 7p 周边`）。
名次是一个「相对全部打牌」的量，给它等于顺带透露了一点排序信息；**仍然给**，
因为票面的硬判据是「同一个函数、不许为工具另算一遍」，裁掉名次就是另算一遍（记在 94-3）。

## 2. 「同一个函数」怎么做成硬事实

引擎的 `Scaffold.calculate`（`DecisionPackage.forSeat` 里那一行）**恒随包过界**，与档位无关
——档位从来只决定「渲不渲染」（票 24 的裁决 24-1）。因此工具的答案不需要任何新的计算：

```ts
// prompt.ts：Assisted 那一节与 what-if 的答案，读的是同一份 view、走的是同一个 trial/dangerLine
const lines = [trial(entry, label, id)];
if (danger != null) lines.push(dangerLine(danger, label, id));
```

三条证据，从强到弱：

1. **逐字节相同**（`what-if.test.ts`）：18 份固件 × 2 模板 × 每一条打牌动作，
   工具答出来的每一行都必须在 Assisted 那一节里找得到**逐字相同**的一行。这一趟比了 **1,296 行**。
   「同一个函数」于是成了一条等式，不是一句承诺。
2. **与 dotnet 侧逐字段对拍**（新的第三道对拍 `scaffold-crosscheck.ts`）：把渲出来的那几行
   **解析回数**，与决策包里 `scaffold` 那一段（dotnet 的 `Scaffold.calculate` 算的）逐字段比
   ——向听 / 进退向 / 有效牌 / 危险度名次 / 档位 / 理由六类。真语料上对拍了 **42,621 个字段**。
3. **结构上**：`SCAFFOLDS` 那张表里 `assisted` 与 `tool_search` 两支读同一份 `readScaffold`
   与同一张 `dahaiById`。

**口径说清楚**（判据 18）：第 2 条左边是「文本解析回来」、右边是「dotnet 出的 JSON」，
两侧是两份互相独立的实现，但**同一个数据源**——它证的是**转录忠实**（抄的时候没串行、没抄错数、
没把甲的危险度挂到乙头上），不是「这个数算得对」。后者由引擎自己的用例守着，不在这一层。

## 3. 上限：为什么是 4，以及它是怎么被执行的

**`WHAT_IF_LIMIT = 4`，三个理由缺一不可**（写在 `what-if.ts` 的文件头上）：

1. **手牌张数**：一手最多 14 张打得出去。问满 14 次拿到的**就是 Assisted 那张表本身**
   ——那不是「自己去问」，是换条路把同一批算好的数拿全，这一档的自变量当场没了。
   4 次是「先排掉明显要留的，再在剩下的候选里挑」这一步的规模。
2. **账单**：每多问一次就多发一次请求，前缀按折扣价、**尾部每次全价**。封在 4 次，
   单手最坏 5 次请求，账单的上界因此是一个有限的常数（实测那一局：请求 ×3.67、输出 tok ×6.0）。
3. **延迟**：票 79 实测直觉档单手中位 1.7 s，5 倍是 8.5 s——仍在思考档（同一份实测 11.8 s）之下，
   一场东风战因此还跑得完（实测 48.7 分钟，§5.1）。

**执行它的是 `loop.ts` 那一行**，不是 prompt 里那句话：

```ts
const offered = whatIfExhausted(queries) ? [] : discardIds;   // 空表 = 这一轮不把 what_if 放进 tools
```

问满之后模型**根本调不出来**（constrained sampling 那一侧连单子上都没有它），因此
「到上限就停、这一手照常打完」是结构上的事实。**它红过**（§4.4 的阴性对照 D）：
把这一行拆掉，「能查就查」那一席当场卡在第 1 手不动。

三处顺带的边界：

- **响应那一手（碰 / 吃 / 立直宣言 / 过）一轮都不给工具**：那几条没有「打完之后」可算，
  摆一个空 enum 出去等于邀模型烧掉一次额度。
- **同一个 id 问两遍算两次**，答两遍——去重会给模型一个「问了没反应」的循环。
- **问满了它还硬调 `what_if`**（端点不听 schema 的那一种）：落回 `judge` 的「模型调了别的工具」，
  走重试那条老路。总请求因此恒 ≤ `上限 + 重试轮数`，**有界**。

## 4. 闸门逐条交代（一条不许少、一条不许放宽）

**改前**：12 条不变量 + 2 道对拍、20 个反向自证，扫语料时**渲两档**。
**改后**：**13 条 + 3 道对拍、26 个反向自证**，扫语料时**渲三档**。
**原来那 12 条一条没删、判据一个字没改**，20 个自证一个没少。

### 4.1 「Bare / Assisted 一个字都没变」是怎么守的

一条摘要断言（`what-if.test.ts` 的头一条）：18 份 committed 决策包 × 2 档 × 2 模板 ×
2 种重试原因 = **144 份渲染**，拼起来取 `fnv1a` = **`21bab6bf`**。

**这个数的来历要说清楚，否则它就是「当前代码等于当前代码」**：它是在**动第一行代码之前**，
把 `@-`（`soxmwnpp`，= `main`）那一版 `web/src/agent/*` 抽到 `/tmp` 里、按同一个顺序渲一遍算出来的；
改完之后当前代码算出来的仍是它。也就是说这一条证的是**「这一票没碰那两档」**。

阴性对照（判据 1）：把 `trial()` 里的「进退向 0」改成「进退向 零」——

```
✖ Bare 与 Assisted 渲出来的字节，与这一票动手之前逐字相同
  AssertionError: Bare / Assisted 两档渲出来的字节变了——票 94 只许动 ToolSearch 那一档
  + '50b193bf'   - '21bab6bf'
```

### 4.2 「可缓存前缀不许分叉」是怎么守的

`CONTEXT.md` 那句「档位只动得了尾部：两档共用同一份前缀」写于只有两档的时候，
而**第三档的差别恰恰是「它多一个调得动的工具」，那件事必须写给模型看**：
不写它就不知道可以问，写给另两档则是告诉它们一个不存在的工具（那会把它们送进兜底）。
于是只剩两条路——放尾部（每手全价，而它一个字不随局面变），或者放前缀。取后者，
**并把「分叉只有这一段」钉成断言**（这就是那条判据在第三档上还说得出口的形态）：

```ts
const block = `\n\n${WHAT_IF_PREAMBLE}\n`;
assert.equal(mine.split(block).length, 2, "那一段在前缀里恰好出现一次");
assert.equal(mine.replace(block, ""), assisted);       // 剪掉它 ⇒ 与 Assisted 逐字节相同
```

外加两条：`cacheablePrefix(bare) === cacheablePrefix(assisted)`（既有那条，照旧全绿）、
以及**位置**那条（工具那一段排在【怎么读这份 prompt】之后、三段结构说明之前）。
两个阴性对照都当场红：

```
（把那一段也发给 Assisted）
✖ Bare 与 Assisted 的前缀照旧逐字节相同（这一票没碰它）
✖ ToolSearch 的前缀 = Assisted 的前缀 + 恰好那一段工具说明
（把那一段挪到 system 末尾）
✖ 那一段的位置：【怎么读这份 prompt】之后、三段结构说明之前
  AssertionError: 工具那一段排在三段结构说明之前
```

**查过的那几条一条也不在前缀里**（另一条用例）：它们是这一手、这一轮的东西，与重试那句话
同一个性质——写进前缀等于每问一次就把这一局攒下的缓存废一次。

### 4.3 新增：第十三条不变量 + 第三道对拍

**第十三条 `算好的数那几行与可选动作对得上`**（`invariants.ts` 的 `checkScaffoldEchoes`）。
**它不是一条只为第三档存在的断言**：【引擎算好的数】那一节从来没被解析回来检查过，
而它正是模型拿来选牌的那几个数——**把数挂到别的 id 上，比数本身算错更阴**：
每一行单看都通顺，模型照它选完却打了另一张牌。三个方向：

1. 试打那几行（`- id=N（L）：打完 …`）：N 得在【可选动作】里，且 L 与那一行**逐字相同**；
2. 危险度那几行（`- 第R位 id=N（L）：…`）：同上；
3. 【你查过】那一行（ToolSearch 档才有）：**已查 + 还能查 = 上限**，且已查次数 = 下面摆了几条答案
   ——**写给模型看的预算不许与真上限对不上**。

前两个方向在 **Assisted 档上同样成立**（两档那几行本来就是同一个函数渲的），
因此它不会因为语料里没有 ToolSearch 而空转：真语料上执行 **15,255 次**。

**第三道对拍 `算好的数 ↔ 决策包里那一份`**（新文件 `tests/agent/scaffold-crosscheck.ts`），
理由与做法见 §2 第 2 条。真语料上对拍 **42,621 个字段**，六类各 6,349–7,858 次。

### 4.4 六个新反向自证，全在真语料上当场红

第十三条那三个（`invariant-proofs.ts`）：

```
[算好的数那几行与可选动作对得上] …assisted 档：这一行说 id=0 是「打 9s」，【可选动作】里同一个 id 写的是「打 1m」

    原文：- 第1位 id=997（打 1m）：现物 —— 对家现物
[算好的数那几行与可选动作对得上] …tool_search 档：已查 1 + 还能查 4 ≠ 上限 4：写给模型看的那句话与真上限对不上
    原文：你查过 1 次，还可以再查 4 次：
```

第三道对拍那三个（**三种都是纯文本那十三条按设计看不见的错**，脚本里对这一点有阳性断言）：

另外两个是浏览器那一趟的阴性对照（不在 26 个之内，是我手动按红的）：

```

  座位 1 一条决策记录都没有——底下几条断言在空转

  座位 0 第 0 条记录查了 0 次，该是 2 次（这一手有牌可打）
  座位 0 第 0 条记录的输入 tok 是 4070，该是 814（1 次请求 × 814）
```

**D 那一条正是票面「不许卡死」的执行体**：拆掉那一行，卡死就当场发生。

### 4.6 浏览器侧新增的第十六趟

`web/scripts/verify-toolsearch.mjs`：两个本机假端点各演一种模型（**`fake-endpoint.mjs --what-if N|inf`
看 `tools` 行事**——单子上没有 `what_if` 就直接出牌，正是 constrained sampling 下真模型的样子），
第三席是 bare 档的对照，座位 3 是 bot。走 24 手之后读**导出的牌谱**：

```
座位 0（tool_search）：记录 6 条、每手查 2 次、答案 2 条、兜底 0、输入 tok 2442
座位 1（tool_search）：记录 7 条、每手查 4/0 次、答案 4/0 条、兜底 0、输入 tok 4070/814
座位 2（bare）：记录 6 条、每手查 0 次、答案 0 条、兜底 0、输入 tok 814
```

四件事：① 链路走通且**这一手是它自己决出来的**（0 兜底、`applied` 有值）；
② **到上限就停**（「能查就查」那一席恒是 4 次，且照常出牌）；
③ **账单真的算了几倍**（假端点每次回同一份 usage，因此 `usage.input = (查询次数 + 1) × 814` 是个确定的等式）；
④ bare 那一席一行查询都没有、preamble 里那一段只有 ToolSearch 席才有。
「这一手有没有牌可打」两条路**各有各的期望**（响应那一手工具一轮都不给，查询数该是 0），
不揉成一条宽断言。

**它是全仓唯一一条真过 pi-ai 适配器的 `what_if` tool call**：`node --test` 那一层喂的是构造出来的回答
（拿录制固件 `ask-legal` 换掉工具名与实参——「一条 tool call 长什么样」那一半仍由录制产物证），
而这一趟走的是真的 HTTP SSE。

### 5.2 模型实际问几次：**它几乎每手都问到上限**

「给过工具的手数」= 这一手【可选动作】里有牌可打（响应那一手工具一轮都不给）：

| 一手问了几次 | 0 | 1 | 2 | 3 | **4（上限）** |
|---|---|---|---|---|---|
| 手数 | 7 | 12 | 35 | 49 | **206** |

- 给过工具 **309 / 395 手**，其中 **302 手真去问**（97.7%）；
- **中位 4、p95 4、最多 4**；四席逐席都是中位 4、p95 4（人格不同也一样）；
- **只有 7 手一次都没问**（2.3%）。

**「它一次都不问」这条被彻底否掉了**，而且方向反过来：**上限是紧的**——三分之二的手打满了 4 次，
它显然还想问更多。这件事有两层含义：

1. 上限那三条理由（§3）都不是空谈：不封的话这一局会问出几千次查询；
2. **它拿到的其实是一张「自己挑 4 行」的 Assisted 表**。这一档与 Assisted 的差别因此不是

**它真的在用那几个数**：395 条理由里 **298 条（75%）**引到了「N 枚 / 向听 / 有效牌 / 进张面」
这几个只可能来自查询结果的说法。对照：票 79 那一场（assisted，数是推给它的）是 **82%**。
两个数接近，说明**推给它与让它自己问，接收侧看不出差别**——差别全在账单与墙钟上。

**中位 ×3.4（5,970 / 1,780）**，与「每手平均 3.67 次请求」对得上——**多轮往返的代价基本就是往返次数本身**，

### 5.4 账单：**缓存命中率不但没掉，还翻了一倍（36% → 73%）**

票面担心的是「工具往返会不会把命中率打下去」。**答案是相反的，而且理由是形状而不是运气**：

| | 票 79 assisted | 票 95 assisted | **本票 tool_search** |
|---|---|---|---|
| 付全价输入 | 928,134 | 1,314,477 | **1,084,415** |
| 缓存命中 | 435,968 | 753,536 | **2,903,168** |
| **命中率** | 32% | 36% | **73%** |
| 输出 | 47,952 | 62,894 | **237,911** |
| 每手总输入 tok | 2,940 | 3,288 | **10,095** |
| **每手付全价输入 tok** | 2,000 | 2,100 | **2,745** |
| **每手输出 tok** | 103 | 100 | **602** |

一手里的第 2..5 次请求，**前缀与上一次逐字节相同、尾部只多了一两行查询答案**——
于是那几次几乎整份都命中缓存。分手看得更清楚：

| | 每手付全价 | 每手命中 | 命中率 |
|---|---|---|---|
| 问满 4 次那 206 手 | 3,837 | 10,169 | **73%** |
| 一次没问那 93 手 | 1,267 | 1,137 | 47% |

**三个乘数要分开读**（这是这一节最该被下一票记住的一件事）：

- **请求数 ×3.67**；
- **总输入 tok ×3.1**（10,095 / 3,288）——但其中大头是折扣价的；
- **付全价输入 tok 只 ×1.31**（2,745 / 2,100）；
- **输出 tok ×6.0**（602 / 100）——**多轮往返最贵的一项在输出侧**，每一轮都要吐一次 tool call。

**没换算成钱**（判据 14：这台机器上没有 `deepseek-v4-flash` 的价目表）。要算的人拿上面四个数
配自家的输入 / 缓存 / 输出三档单价即可；**结论会随「输出比输入贵几倍」而变**，
因为这一档的放大集中在输出上。

### 5.5 打法有没有变：**这一局说不了**（判据 13）

5 局、0 立直、2 和了、3 流局、29 副露。与票 95 那一局（7 局、3 立直、3 和了）比，
折成每局是「立直 0.43 → 0、和了 0.43 → 0.40」。**一局对一局证明不了因果**——
局数、走向、模型输出的随机性全在里面。
唯一硬的观察仍在接收侧（§5.2 那 75%）：**它读到了自己查出来的数并把它写进了理由**。

值得记一句的是与**裸奔档**的对照：票 79 实测裸奔档两场 8 局 **0 立直 0 和了 1 听牌**，
而这一场（正文与裸奔档逐字节相同、只是它能自己去问）**5 局里和了 2 次**。
**这仍然是一局对一局**，但方向对得上「这一档给的是拿得到那些数的能力」。
要判因果得同配置各跑十几场比分布，那是另一票的规模（票 95 §11 已经提过同一件事）。
