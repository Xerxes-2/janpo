## 3. 第二节：「文本说法 ↔ 决策包里的绝对座位」搬上批量语料

十一条只读文本，因此它们**按设计**抓不住「碰的来源指错了人」——只有「吃」在规则上钉死了来源，
碰 / 大明杠 / 加杠谁都鸣得了，一句指错人的话在纯文本里完全自洽（票 41 报告 §8-1）。
票 40 加的那道对拍能抓，但**只跑 15 份 committed 固件**。

判据抽进 `web/tests/agent/naki-crosscheck.ts`（**固件那一档与批量那一档共用同一份**，
两处说法因此一致），参照系取**副露方**（票 40 的裁定）。它自己走一遍座位环（`distance`），
**不调渲染器用的那份 `wordsFor`**——两边错成同一个样子的话这道对拍就白写了。
逐组比三件事：这一组挂在谁名下、写的是哪一种副露、来源那个词。

```
「副露来源 ↔ 决策包座位」对拍了 4682 组副露：
  他家的副露・「他的X」     2188      吃・他家       1816     碰・他家     1040
  自家的副露・相对观测者    1114      吃・自家        600     碰・自家      374
  鸣了你打的那张・写「你」  1088      大明杠・他家    134     加杠・他家    286
  暗杠・无来源              292       大明杠・自家     48     加杠・自家     92
  视角・座位 0 1118   视角・座位 1 1146   视角・座位 2 1138   视角・座位 3 1280
```

**四种来源与四个座位视角每一格都被走到**，且每一格都是 CI 的硬闸门：**少一格当场退出码 1**
（`branches` 那份名单）。三个换算分支（写「你」/ 自家相对观测者 / 他家「他的X」）分开数，
因为**它们各自会独立坏**。

## 4. CI 耗时：前后

| | 语料 | 逐条执行次数 | 对拍 | 实测（同一台机器、同一批负载下交替各跑三趟） |
|---|---|---|---|---|
| 掺之前（`7d3e19c0`） | 6 颗 × 4 座位 = 529 手 / **1,058** 份 prompt | 不知道 | 15 份固件 | **4.50 / 4.54 / 4.56 s** |
| 掺之后 | 9 颗 × 4 座位 = 801 手 / **1,602** 份 prompt | 逐条印 + 0 次喊停 | **4,682 组副露** | **3.69 / 3.67 / 3.67 s** |

语料多了 51%、还多了一整道对拍，**反而快了 0.85 秒**。省出来的是子进程：原来每一手语料要
`dotnet run --project … --no-build`（每趟仍过一遍 MSBuild 求值，实测 **0.66s**），
现在先 `dotnet build` 一次、向 MSBuild 要 `TargetPath`，之后**直接跑编出来的那个 dll**（**0.27s**）。
36 次子进程因此从 ~5.9s 降到 ~2.4s。并行度仍然**显式封顶 4**（RUNBOOK 的资源预算）。

因此**没有动用「超了就减种子」那条**：不变量一条没减，均匀那六颗种子一颗没换。

## 7. `janpo decide --opinionated`：CLI 那一处改动

`--sequence` 原来写死 `Kyoku.randomPlayer`。加一个开关，**改动集中在 `runDecide` 那一段**
（票 50 可能也要动这个文件）：`DecideArguments` 多一个 `Opinionated: bool`、
一个五行的 `decidePlayer`、参数表多一行、`decideSequence` 多收一个 `player` 参数。

**默认那一档一个字节都没动**：不写开关仍是 `Kyoku.randomPlayer`，因此
`janpo decide <种子> --steps N` 的第 N 手仍与 `janpo kyoku <种子>` 的第 N 手是同一手，
已录的全部固件与黄金用例都不受影响（`dotnet test` 802 条全绿）。

没有把 `BotChoice`（`game` / `soak` 共用的那三选一）拉过来：`decide` 只需要两种，

（前者是 `RandomPlayer.uniform`，后者是 `Kyoku.randomPlayer`，两者不是同一个选手）。
记在 `DECISIONS`「## 49」的 49-3。

## 9. 留给人的

1. **有主见那三颗种子里没有杠也没有吃**（碰 368、其余 0）。三种杠与吃全靠均匀那六颗。
   若哪天要换均匀那批种子，**先看 §1 那张表的「均匀」一列**——吃那一条会当场归零。
2. **「立直后全摸切」的执行次数是随手数二次增长的**（每一份 prompt 都把整条历史读一遍），
   1,470 这个数不该被读成「验了 1,470 个不同的局面」。它验的是 **272 手 × 各自历史里
   立直之后的那几张**。同一口径下的相对变化（0 → 1,470）才是这一票的证据。
3. **对拍的「视角・座位 N」四格在固件那一档只有座位 1 与座位 3**（committed 固件就那两个视角），
   四格齐全靠的是批量那一趟。哪天批量那一道被跳过（`JANPO_NO_BROWSER=1` 不影响它，但别的跳法会），
   固件那一档补不上另外两个视角。
4. **`--getProperty:TargetPath` 是 .NET SDK 的 CLI 形态**（本机 10.0.111）。哪天换 SDK 而它不认，
   那一道会在 `找不到编出来的 janpo` 上当场停，不会静静地退回慢路径——这是故意的。
5. 票 41 报告 §10-4 那条仍然成立：十一条不变量的名字是中文字符串，没有稳定 id。
   本票的执行次数表也按名字聚合，**若 M2 要按不变量做统计，那件事要一起做**。

### 判断题（记录，未改）

1. **`naki-crosscheck.ts` 里的 `renderedNaki` 是第三份「把 prompt 解析回来」**
   （另两份：`invariants.ts` 的 `parse`、渲染器自己）。**故意的**：这一份只认副露那一行，
