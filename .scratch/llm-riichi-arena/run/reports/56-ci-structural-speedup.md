## 2. 那处浪费：实测确认过程（判据 13）

票面说的是**九条**轨迹，实际是**十条**（`Gen.frequency` 那张表里有十项，权重
4/4/4/4/2/1/1/4/1/1 = 26）。判断的方向对，数字差一条。

### 2.1 数一数 `traceFrom` 被调了多少次

给 `GameStateFixtures.traceFrom` 与取样点各挂一个 `Interlocked` 计数器（进程退出时写盘，
**临时探针，不进提交**），跑一个属性模块：

```
$ dotnet test --filter FullyQualifiedName~ScaffoldProperties
已通过! - 失败: 0，通过: 4，总计: 4
traceFrom=4000 samples=400 states=28523
```

**4 条属性 × 100 个样本 = 400 个样本，却跑了 4000 条轨迹——每个样本 10 条，用 1 条。**
整份引擎测试：

```
$ dotnet test tests/Janpo.Engine.Tests   （改前）
traceFrom=60236 samples=5900 states=445467      wall=53.74 user=397.82 sys=89.07
$ dotnet test tests/Janpo.Engine.Tests   （改后）
traceFrom=7136  samples=5900 states=447294      wall=12.47 user=112.92 sys=22.28
```

**取样次数一次没少（5900 = 5900）**，轨迹从 60,236 条掉到 7,136 条
（7,136 = 5,900 个样本 + 1,236 条具名用例自己调的）。**53,100 条轨迹是白算的。**

### 2.2 十条轨迹各自多贵

`dotnet fsi` 直调编译好的测试 DLL（`scripts/fsi/README.md` 的规矩），每条量 20 次：

| 轨迹 | 权重 | 毫秒/条 | 局面数 |
|---|---:|---:|---:|
| 随机 | 4 | 12.45 | 84 |
| 听牌 seeking | 4 | 7.55 | 97 |
| 副露 seeking | 4 | 4.30 | 83 |
| 杠 seeking | 4 | 5.35 | 82 |
| 立直 seeking | 4 | 4.30 | 79 |
| 摊好·三暗杠 | 2 | 2.55 | 77 |
| 摊好·大明杠 / 暗杠 / 自摸和 / 荣和 | 1 各 | 0.10–0.25 | 3–8 |

改前每样本 **37.2ms**（十条全跑），改后按权重平均 **5.45ms**（只跑选中那条）——6.8×。

### 2.3 改法与「取样分布不许变」的证据

```fsharp
// 改前：Gen.constant 的参数即时求值，十条全跑
4, Gen.constant (GameStateFixtures.trace Kyoku.randomPlayer seed)
// 改后：选中之后才求值
4, Gen.fresh (fun () -> GameStateFixtures.trace Kyoku.randomPlayer seed)
```

先在 fsi 里验了 `Gen.fresh` 的语义（600 个样本、权重 1:2:3）：三个计数器合计 600
（每样本只求值一条），分布 88 / 205 / 307 与权重相符。

**分布没变的硬证据**：同一颗 FsCheck 种子（`Rnd(20260817UL)`、size 50）取 400 个样本，
每个样本印「事件条数 + 结构化哈希」，改前改后**逐行相同**：

```
$ diff /tmp/56-dist-before.txt /tmp/56-dist-after.txt   → 无差异
改前：取样 400 个用了 9922 ms，traceFrom=4000，states=29551
改后：取样 400 个用了 1934 ms，traceFrom= 400，states=29551
```

`states` 是**被选中那条轨迹**的局面数，两侧同为 29551——选中的是同一批轨迹，取出的是同一批局面。
道理也说得清：`Gen.fresh` 与 `Gen.constant` 都不消耗随机流，`Gen.frequency` 的抽签逻辑没动。

### 2.4 记忆化：量过之后决定**不做**

票面让顺带看 `(脚本, 种子)` 的记忆化。量了两件事：

- **命中率**：5900 个样本里 20/26 落在五条带种子的轨迹上（每条 ≈908 次抽签摊在 400 颗种子上），
  期望只有 359 颗不同 → 能省掉约 60%，折合 **≈18.5s CPU**（占改后 126.4s 的 15%）。
- **代价**：`dotnet fsi` 实测缓存 200 条轨迹（17,628 个局面）堆增长 **36.4 MB**，
  按 5 种选手 × 400 颗种子外推 **≈364 MB**——常驻峰值会从 251 MB 翻到 600 MB 上下。

**不做**。三条理由：① 属性模块开着 `Parallelism = 4/8`，缓存是一份跨测试的可变共享状态，
而这一票的全部收益都来自「少算」，不该顺手引入一份新的共享物；② 364 MB 常驻换 15% CPU，
在 4 核远端上是拿内存换一件已经不贵的事；③ 现在的形态一眼看得懂——一个样本跑一条轨迹。
（若哪天真要做：值是不可变的 F# 列表，`ConcurrentDictionary` 就够，风险只在内存。）

## 3. 浏览器七趟：合并 + 把往返砍掉

### 3.1 先量「一趟的固定开销」是多少

```
startPreview（托管 dist/）      17.4ms → 5.5ms（第二次）
startDevServer（源码形态）      16.6ms → 5.9ms
chromium.launch                75.8ms → 61.9ms
newPage                        74.8ms → 49.0ms
goto（preview / dev）        23–188ms
```

七趟合计省得下 **3.15s**（单跑之和 9.80s → 合并一趟 6.65s）。这就是「共用一个浏览器」的
全部价值——票面估的「20s → 一半以下」不是从这里来的。

### 3.2 真正的大头：每走一手四次跨进程往返

从前走一手要问一次「单步灰没灰」、读一次「上一手」、点一次、再等一次 DOM 变。
`--to-end` 那趟走 785 手 ≈ 三千多次往返。同一台机器、同一颗种子 447、走 200 手：

| 走法 | 200 手 |
|---|---:|
| 每手一次往返（原写法） | **6680 ms** |
| 页面内一次走完 + `requestAnimationFrame` 轮询 | 3329 ms |
| 页面内一次走完 + `setTimeout(0)` 轮询 | 943 ms |
| **页面内一次走完 + 微任务轮询**（现在用的） | **279 ms** |

于是 `table-drive.mjs` 把「走一手」整段搬进页面（`page.evaluate` 一次走到底），
轮询策略是**先微任务、后宏任务**：Elmish 的 setState 落在微任务里，但等模型回话的那一档
（`verify-export --llm`，人工跑）非得让宏任务跑起来不可，一路 `Promise.resolve()` 会把
setTimeout 与网络回调饿死。**页面读的还是同样的 DOM，闸门的断言一条没动。**

一处有意的差别：原来的循环在某一手超时后**接着往下走**（4000 手 × 600s 预算 = 永远跑不完），
现在超时就停下并报 `第 N 手没走动`——**同一条断言，早一点开口**。

### 3.3 三趟原样的输出

改完先逐趟与改前的输出**逐字节对拍**（`diff`）：tracer / board / export×3 全部
「输出逐字相同」；redaction 只差随机端口号那两行（端口本来就是内核给的）。

### 3.4 单跑没弄丢

每个 `verify-*.mjs` 仍是可执行入口（`isEntry(import.meta.url)`），`pnpm run verify:board`
之类照旧；合并跑红了的时候，报告里直接把单跑那条命令抄给人：

```
【牌桌上人看得见的八项 + 副露的位置就是来源（真对局）】红了。单独重跑它：node scripts/verify-board.mjs
```

`JANPO_NO_BROWSER=1 ./scripts/ci-web.sh` 照样跳过这七趟、其余六道照跑（实测 rc=0）。
