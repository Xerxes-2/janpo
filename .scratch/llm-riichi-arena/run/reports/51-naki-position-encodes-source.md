## 1. 位置怎么算的：判据一处，参照系是**副露方**

```fsharp
// src/Janpo.Web/Board.fs
let private takenSlot (ruleset: Ruleset) (owner: Seat) (target: Seat) (count: int) : int =
    match position ruleset owner target with
    | Position.Kamicha -> 0
    | Position.Toimen -> 1
    | Position.Shimocha -> count - 1
    | Position.Self -> 0        // 鸣不到自己打的牌；真走到这里闸门当场红
```

**它读的是票 44 那个 `Board.position`，只是 `anchor` 传的不是观测者而是副露方**。
三件事值得写下来：

1. **参照系是参数，不是隐含的全局。** 同一个函数两处调用、两个参照系：牌桌布局传观测者
   （`seating.Anchor`），副露槽位传 `owner`。票 40 那个「吃来自对家」的病根正是
   「参照系从调用点隐含地拿」，因此这一层的注释把两处并排写在 `position` 的文档里。
2. **座位算术仍旧全交给引擎**（`Seat.distanceFrom` / `Seat.toimen`）。三麻没有对家时
   `Position.Toimen` 根本出不来，这一层不重写一份 `(seat + 2) % 4`。
3. **`Position.Self` 那一支走不到**，但它不是「不可能」的注释就完事——闸门那条
   「槽位 ↔ 绝对座位」会把它当场逮住（§5 的 A/B 两次自证就是这条在说话）。

`NakiView.Tiles`（逐张）换成了 **`Slots: NakiSlot list`（逐格，每格一到两张，从下往上）**。
「一排格子、加杠那格摞两张」就是真牌桌的形状，而**加杠必须能与大明杠分得开**——
这不是审美，见 §3。

### 1.1 屏幕左右与副露方左右，在这一版里方向相同（但判据不同）

票面写着「票 44 让上家/对家的副露行整体翻转过」。**我核了 `styles.css`：并没有。**
票 44 只用 `align-self`（河贴桌心、副露贴外侧）表达朝向，四家的牌一律不转、不镜像，
**每一行都从屏幕左边往右读**。所以这一版里「副露方的最左」画出来就是「屏幕的最左」。

这不代表参照系那条要求是空的——**判据仍然必须从副露方算起**，否则同一组副露在
四个座位视角下会摆出四个样子（那正是 §5 的 A 次自证的红）。因此位置断言拆成两条独立的：

- **槽位 ↔ 绝对座位**（`data-naki-from-seat` 与副露方座位号算出来的第几家）；
- **五个视角看到的位置逐字相同**（位置不是屏幕左右，换个人坐不该翻过来）。

第二条在这一版的布局下**恒真**，但它守的是将来：思考气泡那一票若真把左右两家的牌转 90°、
或某天给某个方位加了 `row-reverse`，第一条仍可能全绿而画面已经反了——所以还加了第三条：
**每一格的屏幕横坐标必须与 DOM 顺序同向**（§5 的 G 次自证按红的就是它，一句 CSS 就能触发）。

## 3. 大明杠与加杠的画法：依据在哪儿

**不是自创。** 两条都引得到明文：

| 画法 | 依据 | 原文 |
|---|---|---|
| 大明杠：上家最左、**对家左起第二**、下家最右 | **M 联盟公式规则第 6 条第 3 款**（`m-league.jp/about/`，`riichi.wiki/M.League_rules` 有对照英译） | 「（3）明槓子(大明槓によるもの) カンした牌を横向きにし、手牌から開示した暗刻に加える。**上家からは左、対面から左2番目、下家からは右に並べる**」 |
| 同上（二次来源，口径一致） | 维基百科「槓」 | 「下家からカンした場合は右端の牌、**対面からの場合は中央の牌（いずれか1枚）**、上家からの場合は左端の牌を横にする」 |
| 加杠：加上去那张**叠在**横放那张上 | **M 联盟公式规则第 6 条第 4 款** | 「（4）加槓子 **加槓牌を指示牌の上に並べて重ねる**」 |
| 加杠为什么必须叠、不能摆到末尾 | 维基百科「槓」 | 「もしかりに正しい晒し方をせず、隣にくっつける形で〔…〕のようにしてしまったら、**「上家からのポン」であったものが「対面からの大明槓」になってしまう**」 |

「対面からの大明槓」两家资料略有出入（M 联盟钉死**左起第二**，维基允许中间两张任一），
**取更严的那一份**（M 联盟）：它是明文规则、且与三张时的「真ん中」在直觉上连续
（都在左起第二格）。这也让 `takenSlot` 只有一行 `Position.Toimen -> 1` ——三张四张同一条。

**一处有意的偏离**：真牌桌上加杠那两张**都是侧着的**，我们只把底下那张横放，上面那张立着。
理由是票 38 那条记号的维度：**「横放 ＝ 从他家那儿来的」**。把加上去的那张也转过来，
这条记号就得重新定义（它出自自家手里）。二维平面上「叠在上面 + 一枚『＋』」已经说清了
「这张是后加的」，而来源仍由**底下那张所在的格**读出来。

## 7. 无障碍：删了可见文字之后

**做了**：来源那句话（`来自上家` 等）仍在 DOM 里，挂 `.naki-from.sr-only`（position:absolute + 1px + clip-path
的通行写法，**不是 `display:none`**——那两种读屏也读不到）。闸门两头都核：文字必须在、且必须看不见。

**代价（如实记）**：

1. **读屏用户读不到「位置」这一半信息**——他们读到的是「碰 来自对家 西 西 西」，
   而看得见的人读到的是位置。两者信息量相同（来源都在），但**画法不同**，
   因此若将来位置编码出错而文字仍对，读屏用户看不出异常。闸门那条「槽位 ↔ 绝对座位」是这条的兜底。
2. **横放/叠放/牌背这几个记号本来就没有读屏形态**（票 38 起就如此，本票没有把它变坏也没有修好）：
   `sr-only` 只说了「来自谁」，没说「哪一张是鸣来的」「哪张是后加的」。
   要补的话应当是一句完整的替代文本（例：`碰，来自对家，鸣来的是西`），
   那会与 `.naki-kind` 那枚可见标签重复朗读，得连着一起改——**超出本票，记在 §9 第 1 条**。
3. 桌心那行参照系说明是**可见文字**，读屏也读得到（它是普通段落），因此「位置怎么读」这条约定两边都拿得到。
