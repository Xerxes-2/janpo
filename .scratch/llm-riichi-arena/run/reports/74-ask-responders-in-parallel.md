## 2. 形状：一席一份在飞，落子沿引擎的顺序

### 2.1 `Awaiting` 变列表，回执按「座位 + 票号」各判各的

```fsharp
type Awaiting = {
    Ticket: int                    // 全局递增，因此跨席唯一
    Package: DecisionPackage       // 问的是哪一席写在它身上（Awaiting.seat）
    Config: LlmSeat                // 「在想」的上限秒数也读它（TimeoutMs / 1000）
    Answer: AgentAnswer option     // 回来了、还没轮到落的那份回执（见 2.2）
    WaitedSeconds: int             // 已等几秒（Waited 一秒一跳，回执到了就停）
}
// LiveTable.Awaiting : Awaiting list   LiveTable.Agent : AgentStatus list（每席一项）
// TableMsg.Answered of seat * ticket * answer      TableMsg.Waited of ticket
```

`AgentStatus` 的 case **不再带座位**（Idle / Asking / `Spoke of reason * latency` /
`Troubled of reason`）：哪一席由它在列表里的位置说了算（与 `Pinned` 同一个做法），
再带一份就表示得出「第 1 项写着座位 2」这种对不上的状态。

`step` 一步把**所有**待答而没在飞的席问出去（打牌阶段恒只有一席，与从前无异）；
决策包全部取自这一刻的局面——§1 的地基断言保证别席先答不动它们。
同一席在飞时绝不问第二次（票 23 那条用例一字没放宽，红-8 按红过它）。

### 2.2 关键取舍：**回执按到达顺序收，按引擎问答的正序落**（`drain`）

先回来的回执存进自己那份 `Awaiting.Answer`，真正**落**要等引擎待答头一家的回执到了才逐个放行
（bot 席排在头一家时也在 `drain` 里落）。理由：回放重建响应阶段的提交就是按「每次取头一家」
重建的（`Replay.stepResponse`，「过」不产出事件、只能按既定顺序补回来），按到达顺序落会让
决策记录的手序号与回放逐帧对不上——而到达顺序不归任何人管。红-4 就是把 `drain` 改成
「谁答了先落谁」，`回执到达的先后不改结果` 那条当场红在牌谱字节上。

**这一等不改墙钟**：引擎收齐才裁决，整轮的墙钟恒是最慢那一席。它买来的是一个更硬的性质：
**倒序到达打出的牌谱与正序（= 串行的落子时序）逐字相同**——票面那条「终局点数与顺位
逐项相同」只是它的推论（§4 的用例直接比整份牌谱 JSON）。

### 2.3 「在想」显示已等秒数与上限（72-3 裁决明写的代价）

`Bubble.Thinking` 带上 `waitedSeconds * limitSeconds`，气泡上那句话是
「正在等它回话……已等 N 秒 / 上限 M 秒」，`data-waited` / `data-wait-limit` 给闸门读
（**testId 仍是 `seat-{N}-bubble`**，`data-bubble="thinking"` 时多这两个属性）。
秒数的钟是一条自续的 `Waited of ticket` 链：一秒一跳，回执到了/那票作废了链就自己断，
不会像 `setInterval` 那样越积越多。上限取**单次请求的超时**（重试会更长，但「最迟什么时候
会有下一条消息」就是它）。`AgentLine` 把在飞的几席合成一句
「正在等座位 1、2 的模型回话（已等 5 秒 / 上限 240 秒）……」，说过话/兜底的席各一句、分号隔开；
`data-agent` 取 troubled > asking > spoke（与从前单席时的读法兼容，CI 里四道读它的闸门全绿）。

## 3. 墙钟：并发的两组数（票面闸门①）

`verify-bubbles` 第二程：座位 0/1/2 共用一个**固定延迟 700 ms** 的本机假端点、座位 3 是 bot，
种子 48（fsi 探针挑的：第一局第 2 手就有一轮多席响应）。MutationObserver 记录
「几个 thinking 气泡同时在场」的每次变迁，取第一轮 ≥2 席的窗口：

| | 墙钟 |
|---|---|
| **2 席同时在飞的那一轮（实测）** | **708–713 ms**（三次跑：708 / 710 / 713） |
| 串行要付的（2 × 700 ms） | **1400 ms** |

断言钉的是 `墙钟 < 2 × 延迟`（并发）且 `≥ 0.4 × 延迟`（延迟真的发生了，不许量空）。
红-W1（把 `step` 改回「一席在飞就不问第二席」）时它红成
「等了 45000 ms 也没见到 ≥2 席同时在想」，log 里满屏 `count≤1`——正是串行的指纹。

## 4. 其余闸门

- **并发只改问的时机、不改结果**（dotnet）：`回执到达的先后不改结果：倒序到达打出的牌谱
  与正序逐字相同`——四席模型打完**一整场**（正序 = 串行时序、倒序 = 最坏错位），
  整份牌谱 JSON 相等 + 终局点数相等；两趟各自断言「真遇到过 ≥2 席在飞」（判据 3）。
- **回执错位**：三条用例——`票号对不上的回执一律丢掉`（原有，改到新 API）、
  `座位对不上的回执同样丢掉：票号是那一票的也不行`（新）、
  `回执错位：座位与票号各来自一份在飞的问话，一律丢掉`（多席在飞时甲席座位配乙席票号，
  连「先记下」都不许）；「在飞时重开一桌，迟到的回执落不进新牌桌」原有用例照旧绿着。
- **一席超时/报错不拖累别席**：dotnet（坏席先回「交不出来」、其余席倒着回：坏席兜底、
  别席各正好一条不带 Fallback 的记录）+ 浏览器（座位 0 换到只回越界 id 的端点后变「兜底」态，
  其余三席的气泡照样往前走、没有一席跟着变红）。
- **四席四端点各说各的**（票 76 交代的扩法）：四个端点各回一句只可能从它那儿来的话，
  MutationObserver **全程**盯着有没有哪一席的气泡写过别席端点的话（只在暂停后抽查最新一条
  抓不住几十毫秒的串线窗口——红-W2 的第一版就没抓住，见 §5 红-W2）。
  票 76 的原有断言（矩形不相交、点开九样、收起来逐字回到现在、兜底同源）一条没拆。

  坏席不拖累、秒数按席各记。票 23 那条「同一手不许有两个请求在飞」**一字没改**，语义收窄为
  「同一**席**不许有两个」，红-8 证明它仍然咬人。
- **「不做取消」在形状里**：一家宣言荣和不产生任何事件（引擎收齐才裁决），`Awaiting` 里
  其余席的请求照飞、回执照收——代码里根本没有一条「取消」路径可走。

### 记录但没改的 nitpick

1. `AgentLine` 四席都说过话时那一行会很长（四句拼一行）。「好看是票 76 的事」，
   本票只保证列得全；要收就折进悬浮或换行，留给做面板的票。
2. 回执**已到但还没轮到落**的席，气泡仍是「在想」、秒数停走。语义上它是「答了、等前席」，
   另立一态要多一个 case 与一套文案，而这个窗口通常只有毫秒级；没做。
3. `verify-bubbles` 3.9s（原 2.1s），大头是第二程 700 ms × 若干轮的真延迟。再压就得缩延迟，
   而延迟太短会让「一份 vs 几份」的信噪比变差；没动。

## 9. 留给人的待审项

1. **落子顺序的取舍**（§2.2）：为了牌谱与回放逐帧对得上，先回来的回执要在 `Awaiting` 里
   等引擎的头一家。若将来想让 UI 即刻显示「它答完了」（不等前席），改的是气泡三态加一态，
   不动落子顺序。
2. **上限显示的是单次超时**（240 秒），重试最坏 3 × 240 秒。要显示「含重试的总上限」，
   改 `Awaiting.limitSeconds` 一处（乘 `Agent.retryLimit + 1`）；没做，理由见 §2.3。
3. 真跑只有 40 手、响应轮零星（§6 第 2 条）：**flash 档四路并发的整场收益要票 79 的真跑来量**，
   拿 1907 ms 中位与 39% 缓存命中当基线。
