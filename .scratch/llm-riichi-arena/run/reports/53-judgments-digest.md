## 1. 清单最终目录

前言（3 段）：它是什么与不是什么、怎么用（开工过一遍 / 收工再过一遍你动过的那几条）、
往里加一条的门槛（**没有案例的漂亮话不进**）、以及一个当词记的框架——
**「记录声称了一件事，而那件事的执行体不存在」**（已抓到五例，判据 1/2/3/18 都是它的分支）。

**一、证据（谁在守，它守得住吗）**

1. 闸门的证据是「它失败过」
2. 写下一条不变量，先问「谁来执行它」
3. 闸门还要问「它在真语料上执行过几次」
4. 覆盖不到的，做成代码里的一个值
5. 断言红了，只许往补强的方向改
6. 新断言第一次报红，先怀疑断言自己
7. 「看得见」这类验收，要有人真的把图打开看
8. 渲染出来的自然语言要有语义闸门

**二、形态（是不是一开始就建错了）**

9. 一个投影里出现第二个「只能从历史算」的字段，就是形态错了
10. 相对方位必须显式声明参照系
11. 要读规则才做得出的决定，归引擎
12. 拒绝理由各有各的 case，别落进兜底分支

**三、事实与因果**

13. 查「当下事实」问权威源
14. 说「因为 X 所以慢」之前，先量 X
15. 前提被后续票拆掉时，回头重问那条决策

**四、给调度器（派工与集成）**

16. 并行跑批时看到红，先怀疑基础设施
17. 票号由调度器分配
18. 票文件先提交，再开工作区、再派工

末尾一节「**不在这份清单里的**」：硬约束在 RUNBOOK / AGENTS.md、F# 写法与性能基线那条教训在
`fsharp-style.md`、领域词在 `CONTEXT.md`、一票一议的取舍在 DECISIONS 与各票报告。
它在那里是为了**挡住后来者把这份清单写成大而全的开发规范**。

**编号是稳定的**（只往后追加），所以派工单可以写「按判据 3 与 10 做」。

## 4. 自查：调度器能不能只写「照 `docs/agents/judgments.md` 的判据做」

**能，但有三处边界要在派工单里补一句话。**

能的部分：18 条每条都能脱离案例独立执行（案例只解释「凭什么」），编号稳定，
四节按「证据 / 形态 / 事实 / 调度器」分开，实现 agent 读 §1–§3 就够；
末节「不在这份清单里的」把它与 RUNBOOK / `fsharp-style.md` / `CONTEXT.md` 的分工写死了，
所以指过去不会让人以为它取代 RUNBOOK。

缺的三处（派工单仍要写，或下一轮补进清单）：

1. **它不含硬约束**。「只用 jj、不许 git、资源预算、不许问人、park 的做法」全在 RUNBOOK，
   派工单指清单**不能替代**指 RUNBOOK。现在的写法是清单末节明说了这件事，但那要读到最后一节才知道——
   派工单最好仍写「RUNBOOK → 你的票 → judgments」。
2. **它不含这一票的验收**。判据是「同类情形怎么判」，票面的验收项、禁改清单、fixed point 仍要逐票写。
3. **§4 那三条是给调度器的**，实现 agent 读到会困惑（票号谁分配、先提交再派工与它无关）。
   现在靠节标题隔开；若将来 §4 长到五六条，值得拆成单独一份 `dispatch.md`。

另有一处**已知会腐坏的地方**：多数条目的案例指向 `DECISIONS.md` 的小节标题（如
「教训：视觉证据必须真的用眼睛看」）。DECISIONS 是按时间追加的日志、标题不改，所以现在指得准；
但它没有稳定锚点，将来若整理过就要回头核一遍。**没有为此改 DECISIONS**（本票边界）。
