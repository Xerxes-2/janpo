## 2. 口径怎么定的：**引擎里谁是权威**

票面要求「别用『哪个数看起来对』来决定」，也要求**自己验一遍**「引擎是对的、错的是显示」这个假设。

### 2.1 引擎自己怎么说（注释即契约，`src/Janpo.Engine/Game.fs`）

```fsharp
/// 当前各家点数，按座位升序：还没终局就是下一局的**局初**点数，
/// 已终局就是精算后的最终点数。
let scores (game: Game) : int list = …

/// 场上还堆着几根供托；已终局则为 0（精算时已经归属完毕）。
let kyotaku (game: Game) : int = …

/// 最终各家点数，按座位升序。**场上剩下的供托已经归属完毕**，
/// 因此它们之和恒为 `Ruleset.startingTotal`。   ← GameResult.Scores 的注释
```

于是口径只有一条，**并且是分段的**：

| 什么时候 | 权威 | 理由 |
|---|---|---|
| 局中 / 一局刚终、还有下一局 | 那一局的 `GameState` | `Game.scores` 此刻给的是**这一局局初**的点数（`Progress = NextKyoku ctx` 里那份），局内的授受它还不知道 |
| 终局（`Game.result` 有值） | `Game`（`GameResult.Scores` / `Game.kyotaku = 0`） | 供托归属、罚符结转都做完了；`GameState` 只认最后一局，它压根不知道精算这回事 |

**这不是「哪个数好看」，是「哪个函数在这一刻答得出这个问题」。**

### 2.2 亲手验一遍「引擎没错」

`janpo game 447`（dotnet CLI，**完全不经页面**）：

```
{"type":"ryukyoku","reason":"fanpai","tenpais":[…],"deltas":[0,0,0,0],"scores":[24000,27000,24000,24000]}
{"type":"end_kyoku"}
{"type":"end_game"}
kyokus: 5
scores: 24000 28000 24000 24000
juni: 2 1 3 4
display: 1位 座位1 28000  2位 座位0 24000  3位 座位2 24000  4位 座位3 24000（东风战）
```

两个数**都在**，而且各在各的位置上：事件流里最后那条 `ryukyoku` 带的 `scores` 是**局末**的
24000/27000/24000/24000，`end_game` 之后 CLI 报的是**精算后**的 24000/28000/24000/24000。
**牌谱本身没有二义**——含糊的只有「牌桌该画哪一个」。

守恒也对得上：99000（四家局末）+ 1000（1 根供托）= 100000 = 起手总点。

引擎侧还有现成的用例守着这条（这一票一行没动它们）：
`GameTests.终局时场上剩下的供托归点数最高的那家，总点数不变`、
`GameProperties.终局精算只换供托的归属，不改变点数与供托的总和`、
`任意时刻四家点数与供托之和恒为初始总点`。

**结论：27 号报告的判断成立——规则是对的，错的是显示层读错了量。** 因此没有动引擎，
也没有需要先记 DECISIONS 再动手的情形。

## 3. 三处各怎么修

### 3.1 座位卡与供托跟着精算走（`src/Janpo.Web/Board.fs`）

投影（`Observation` / `GodView`）是 `GameState` 的换装，它按定义只知道一局。所以在
**牌桌视图这一层**加一道：终局那一刻把点数换成 `GameResult.Scores`、把供托换成 0。

```fsharp
let private settled (result: GameResult) (board: BoardView) : BoardView = { board with
    Kyotaku = 0
    Seats = board.Seats |> List.map (fun view -> { view with
                Score = Seat.tryItem view.Seat result.Scores |> Option.defaultValue view.Score }) }

let ofTable (viewpoint: Viewpoint) (table: Table) : BoardView option =
    let projected = …（原来那两支：坐席取掩蔽流，上帝视角取 GodView）
    match Table.result table with
    | None -> projected
    | Some result -> projected |> Option.map (settled result)
```

三件事跟着它一起对：立直棒那排图元本来就跟着 `board.Kyotaku` 走（0 就整个字段不画，票 32 定的），
两个视角走的是同一个出口，而**页面上没有第二份点数**——座位卡与终局精算面板从此是同一份数。

顺带在终局精算面板里补一行「场上剩下的供托 N 根（M 点）已归 1 位」（`Board.final`
给的 `FinalView`）：供托归零、立直棒收走之后不说一句，那几根就成了「凭空不见」。
票面允许「归零」或「标明已归 N 位」二选一，**两样都做了**。

### 3.2 末局的结算面板不再邀人「进下一局」（`Board.fs` + `TablePage.fs`）

`Settlement` 多一个字段 `Ended`（CONTEXT.md 的 `GameProgress`：`NextKyoku` 还是 `Ended`），
取自 `Table.result table |> Option.isSome`——这一局终了那一步 `Game.advance` 已经把它收进这一场了，
所以此刻就答得出来。面板那一行改成三选一：

| `Ended` / `Renchan` | 文案 | `data-progress` |
|---|---|---|
| 终局 | **终局：这一场到此打完，下面是终局精算** | `ended` |
| 还有下一局 + 连庄 | 亲连庄 | `renchan` |
| 还有下一局 + 不连庄 | 亲流局，进下一局 | `next` |

用词照 CONTEXT.md（`GameProgress.Ended`＝**终局**、`GameResult`＝**终局精算**、`Renchan`＝**连庄**），
没有自创词。`data-progress` 是给无头闸门读的，免得它去分析中文。

**`Ended` 不是 `Renchan` 的反义**：东风战东 4 局的亲连庄照样终局（不做西入，05 票的 Out of Scope），
所以是两个字段而不是一个。

### 3.3 那条假红的闸门（`web/scripts/verify-export.mjs` + `scripts/ci-web.sh`）

断言本身**留着**，但它现在名副其实。要点三条：

1. **比的是同一个量了。** `report.scores` 报的是「事件流走到哪，点数就报到哪」
   （`PaifuCheck`：还在打的那一局取 `GameState.scores`，正好在某局收尾处结束的取 `Game.scores`）——
   这正是 §2.1 那条分段口径。牌桌现在照同一条口径取数，于是**两边在局中与终局都相等**。
   注释里把这层理由写在了断言旁边。
2. **它能走到终局了。** 原来的循环一局打完就 `break`，永远碰不到终局那一屏；
   现在一局打完就点「下一局」接着打（终局那一刻「下一局」是灰的，于是停在那一屏）。
   新增 `--to-end`（打完整场为止，手数上限默认 4000）与 `--seed N`（开跑前换种子重开一桌）。
3. **终局那一屏另加三条断言**：供托必须是「0 根」、`table-bou` 必须一处都没有、
   `table-renchan` 的 `data-progress` 必须是 `ended`。
4. 顺带补一条兜底（改循环带出来的）：引擎拒掉某一手时「上一手」那行不会变，
   原来的写法当场 `break`，新写法会白等一个预算（默认 600 秒）。所以等待条件里
   一并认 `table-fault`，跑完再显式查一次它——牌桌停住了要说出来，不是慢慢红。

CI 里加了一道（`scripts/ci-web.sh`，第九道）：

```bash
node scripts/verify-export.mjs --to-end --seed 447
```

**与上面那道 `--turns 40` 不是重复**：那道停在局中（两边都读 `GameState`），
这道走到终局（两边都改读 `Game`）。种子 447 是**终局时场上还剩供托**的那种场——
只有这种场里「局末点数」与「精算后点数」才真的不同，不同才验得出口径。
本机实测一整场 **16 秒**，仍然一个网络请求都不发。

## 5. 用例（`tests/Janpo.Web.Tests/BoardTests.fs`，+6 条，dotnet 侧每次 CI 跑）

票面点名「口径那一处该有单元测试：终局时座位卡与精算栏读同一个来源」。落成六条：

| 用例 | 钉的是 |
|---|---|
| 终局那一屏：座位卡与终局精算是同一份点数 | 两个视角（坐席 / 上帝）的座位卡都等于 `GameResult.Scores`；**前置断言**先验明「局末点数 ≠ 精算后点数」，否则这条用例什么也没验 |
| 终局之后桌上不再剩供托：它已经归了头名 | `board.Kyotaku = 0`；前置断言先验明最后一局手上确实还剩着供托 |
| 还没终局时点数与供托照旧读这一局的局面 | **另一半口径**：局中不许被改坏 |
| 最后一局的结算说的是终局，不是进下一局 | `Settlement.Ended = true` |
| 不是最后一局的结算仍然有下一局 | `Settlement.Ended = false`（东 1 局） |
| 终局精算那一屏说得出供托归了谁 | `Board.final`：根数取自最后一局的局面，点数守恒（头名多出来的正好是那几根） |
| 还没终局就没有终局精算那一屏 | `Board.final = None` |

用的种子一律是 **447**——它是唯一能把这个口径区分开的那种场（27-B 的实测：1..2000 号种子里
只有 3 场供托结转到下一局）。
